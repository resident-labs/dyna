# Dyna v2 specification

This is the current design for `next/`. Spec changes land in reviewed PRs, and only the owner can change a settled owner decision. [decisions.md](decisions.md) records the decisions made since the v2 rewrite and where the rewrite's full history is.

## 0. Settled decisions

Only the owner can reopen a settled owner decision.

1. **Events.** Posts and system events are SQLite rows. Transcripts and large outputs stay files.
2. **Box budgets.** Each box has its own top-level slice and hard size limit. Admission counts a smaller request, and the engine accounts for the room limit. The session tree carries authority, close order and routing, not resources. The owner accepts slowdown under pressure, not kills of healthy boxes. A build can exit 137 if RAM and swap fill; its box and session stay.
3. **Model credentials.** CLIProxyAPI holds and refreshes model credentials. Engine code and PiG do not read them; the engine adds only the proxy client key. The proxy stores tokens in its own table in `store.db`. The Accounts page drives proxy sign-in and quota reads.
4. **PiG only.** A session runs on PiG (github.com/MichaelKinsy/PiG), the Go port of Pi, embedded in the box agent's own process. Dyna pins an exact commit of `resident-labs/PiG`'s `dyna` branch, which is a PiG release plus small additive patches recorded in its `PATCHES.md`. There is no Claude Code fallback adapter. Claude uses Pi's `anthropic` provider through CLIProxyAPI's Claude Code cloaking; ChatGPT uses `openai-responses`. The owner accepts that cloaking may flag an account or cause extra billing. An Anthropic request that marks effort changes mid-conversation still sends the session's effort at the top level, where upstream sends `high` (the fork's patch P8).
5. **Dormancy.** A dormant session stops its container, keeps its volume, and no longer counts its host request. Wake starts it.
6. **Host exec.** Only the owner grants it. Root's default grant covers all hosts, including the control plane, without approval. Root can therefore reach model sign-ins and the GitHub token. This is the exception to the no-secret-in-a-box goal. A control-plane grant gives full owner power, including owner-only API calls (owner, 2026-10-31, msg_462f3f1d210856c2).
7. **Root.** Root is a position in the tree. An ancestor can start, move or close descendants. Root's extra powers are the ask-owner and host-exec grants and the engine-notice subscription.
8. **Self-hosting.** Dyna develops itself in its own room. v2 replaced v1 at the cutover; v1's last source is tag `v1-final`.
9. **Scope.** Voice is not ported yet. The library is cut for now; the frozen v1 backup keeps its feature map.
10. **Node jobs.** Do not port them. GitHub Actions runs CI, with Dyna's self-hosted runners of the size each job asks for, placed as boxes are on hosts with ci on (the default, except on the engine's own host) ([CI runners](ci-runners.md)). Host-specific work uses host exec or a room restricted to a suitable host. Admission does not yet select hosts by device needs.
11. **Proxy process.** Vendor CLIProxyAPI in `next/third_party/cliproxyapi`. The engine supervises a child of the same binary over a Unix socket.
12. **Cuts.** Keep subtree moves, `Run` subscriptions and `show_pty` requests. Defer box growth, cross-host restart, checkpoints, relocation commands, bundle data for issue watches and room MCP servers, one cgroup per shell job, `node_modules` reflink seeding and external members. Ship `box.pressure`; use process groups for shell jobs and a manual relocation procedure. A restart of a box whose creation failed may be placed on another host, because a failed creation has no volume to relocate; deferring the relocation of existing boxes still stands.
13. **GitHub.** GitHub is the source of truth for PRs, merges and CI. Dyna stores PR ownership and the approved head, not review records. The owner, an ancestor of the author, or another child of that ancestor may approve; the author and its children may not. A new head clears approval. Dyna merges only with green CI, passing the approved head SHA so GitHub rejects a moved head. It uses GitHub's merge queue where configured. Self-hosted runner boxes get single-job just-in-time tokens; outside PRs use GitHub-hosted runners or wait for the owner. Room policy chooses approvers. Drop comment trust, merge trials, CI time budgets, conflict radar and room PR views.
   - Text that reaches an agent through Dyna from outside the room sits in one wrapper, `contract.Outside(source, author, text)`: `<outside source="github" author="@octocat">`, the text, `</outside>`. The source says where the text came from (`github`, `web`, `subscription <id>`, `mcp <server>`) and the author, when known, who wrote it; an empty author leaves the attribute out. The engine turns `<outside` and `</outside` inside the text, in any letter case, into `‹outside` and `‹/outside`, so the text cannot close the block or fake another. The wrapper carries no warning: the box's startup prompt says once what it names. It covers GitHub text from anyone other than the owner's account in notices and in `pr status` and `issue status`, a subscription Run's output, each web search result's title and snippet (author: the result's domain), and the tool results of the `github` MCP server and of other MCP servers, which the box wraps with the same function (author unknown, so omitted); the `dyna` server's own tools are not wrapped. The box wraps a model's direct calls only: a codemode script reads the raw result of its own calls, and its output reaches the model as it wrote it. The tag is escaped also with spaces or zero-width characters after `<` or `/`, and `"`, `<`, `>` and line breaks are dropped from source and author. An MCP server name has letters, digits, `-` and `_`, with no `_` at either end and no `__`, so a tool name `mcp__<server>__<tool>` names one server. The owner accepts that this does not stop prompt injection.
   - Agents use the real `gh` through the engine without a token in the box. Box calls share the quota, and direct merge calls are refused in favor of `dyna pr approve`. The engine records new PR ownership. The owner accepts that other writes have no approval or repository-scope check, responses are not wrapped, and other APIs can still move a base branch.
14. **Always-on engine.** The control plane runs on an always-on host, which may also host boxes. The web listener binds loopback; SSH forwarding is used until paired remote access. The owner CLI uses the forwarded owner socket or runs on the host. The GitHub token remains in the host's `gh` store. A reboot restarts the engine and boxes restart on wake.
15. **Agent surface.** The box agent serves Dyna operations through MCP. PiG's context update puts the snapshot in the system prompt on first run and compaction, and sends changes to sections, tools and skills as one user-turn update on every provider. The CLI remains. Section 7.9 specifies the mechanism and phase plan.
16. **Tests.** Use one or two integration tests per important owner-facing feature and no repository end-to-end tests. v1's room history was not carried over, and no archive reader is planned.

## 1. Goals and non-goals

### Goals

1. **Agents never load the owner's machine.** Every session runs in a box on a capacity host. The control plane runs no agents, builds or tests.
2. **One contract.** Events, operations, grants, the API and the migration bundle are defined once in `contract/`. The engine, the CLI, the box agent and the web app use the same types. TypeScript is generated.
3. **No secret in a box, with one exception by owner decision.** Model calls, git, GitHub writes and host commands go through the engine. The engine knows the caller by its socket. The exception is root: its default host exec includes the control plane, which holds the model sign-ins and the GitHub token (settled decision 1).
4. **Small and legible.** Under 60,000 Go lines without tests, in nine top-level packages, with no compatibility code. v1 had about 260,000 in 138 packages.
5. **Fast, honest tests.** The repository holds fast unit tests, plus one or two fast integration tests for each important owner-facing feature. Real harness, GitHub and browser behaviour is checked by hand (10.1).
6. **A clean cutover (done).** Rooms were rebuilt by hand, with no import and no rollback. The store guard (8.4) protects every other install.
7. **Useful to any owner (r9).** Any repository and toolchain (images saved in the room), any Linux host with rootless Podman and SSH, and every model account that CLIProxyAPI supports.

### Non-goals

- No v1 compatibility in `next/`: no v1 store reader, no v1 wire fields, no legacy shims, no rollback path.
- No harness other than PiG. Claude Code is not ported (section 0, decision 4).
- No agent work on the control plane: no host worktrees, host shells, host browsers, room slices or test-slot wrapper.
- No root seat and no attach or detach of outside CLIs.
- No shell hooks. Hooks are typed event subscriptions.
- No JSON state files. JSON stays for settings and config.
- No new web framework. The Svelte app has the quiet, dense look of 5.13.
- No shared or untrusted hosts. Boxes run only where only we have admin.
- No end-to-end tests in the repository, and only one or two fast integration tests per important owner-facing feature (10.1).

## 2. Layout

```text
next/                    module github.com/resident-labs/dyna (go 1.26), no go.work
  go.mod
  cmd/dyna/              main: the one binary
  contract/              shared types; imports only the standard library
  engine/                the control plane: store, API, approvals, model route, git, timers
  box/                   hosts, images, budgets, boxes, and the box agent
  harness/               the PiG adapter and the fake harness
  room/                  pure room rules: tree, addresses, delivery, reply channels, wake
  web/                   the ported Svelte app; types generated from contract/
  docs/                  this spec and the guides
  third_party/cliproxyapi/  vendored CLIProxyAPI fork: its own Go module, our patches, DYNA.md
```

Main has no v1 tree. The old module (`dyna-agent`) and `cmd/dyna-export` exist only at tag `v1-final`.

**One binary, three roles.**

| Command | Where it runs | What it does |
|---|---|---|
| `dyna engine` | control plane | serves the API, owns the store, supervises CLIProxyAPI and runs the engine timers |
| `dyna box-agent` | in each box | turn runner, shell jobs behind the `bash` tool, the `dyna` MCP server (7.9), transcript stream, model and git routes into the box |
| `dyna <noun> <verb>` | anywhere | the CLI. In a box it uses the box socket. On the control plane it uses the owner socket. On the owner's desktop it uses the owner socket through an SSH forward (`--socket`, decision 14). |

**Dependency direction.** `contract` imports nothing from the module. `room` imports only `contract`, and it does no I/O: it decides, and the engine acts. `harness` imports only `contract`. `box` imports `contract` and `harness`, because the box agent runs the adapters. `engine` imports `room`, `box`, `harness` and `contract`. `engine/runtime` also imports `web`, which only embeds the built assets. `cmd/dyna` wires them. `engine/store` imports `contract`, `room` and `box`, and nothing else from the module. A unit test enforces this with `go list -deps`.

Sub-packages are the builder's choice. The expected ones are `engine/store`, `engine/api`, `engine/approve`, `engine/model`, `engine/git`, `engine/sched`, `engine/lifecycle`, `box/podman`, `box/fakehost`, `harness/pig` and `harness/fakeharness`.

`engine/lifecycle` is the box reconciler (5.3). It holds the reconcile loop, box admission (5.5) and the box steps. It imports `engine/store`, `box` and `contract`. It reads the engine only through a small interface: `OpenTerminal(session)`, `Connected(session)` and `Stale(session)`. `engine` imports `engine/lifecycle`, never the reverse. API methods in `engine` write box rows and call `Kick()`; they do no host work.

Third-party Go dependencies are allowed only with a reason in the PR. Expected: `modernc.org/sqlite` (pure Go, as in v1), `github.com/spf13/cobra` for the CLI, and the vendored CLIProxyAPI with the modules it needs (5.7). The web app keeps Svelte 5, Vite and strict TypeScript (r7).

## 3. Contract

### 3.1 Rules

`contract/` owns types crossing process boundaries or stored as typed bodies. It uses named closed sets and validates unknown values once at the API boundary. Times use `time.Time`; durations use integer milliseconds. `go generate ./contract` generates union codecs and the TypeScript client; CI checks freshness. Within v2 the API is additive for release skew.

### 3.2 Identifiers and principals

Room and session names contain 1–64 ASCII letters, digits, dots, underscores or hyphens, starting with a letter or digit. Contract types distinguish room, session, box, event, operation, grant, turn, device, subscription, goal, host, repository and profile identifiers. The engine derives the principal from the connection, not the request body. Principal kinds are owner, session and engine. Root is the session without a parent, not a special principal.

### 3.3 Event

An event is one stored fact, with a sequence, ID, time, room, principal and registered typed body. One generated discriminated union covers each body. Wake is a delivery decision, not an event property. Typed failure causes and notice kinds drive owner-facing views.

`turn.activity` is a live, unstored event with sequence 0. The box reports its current tool call at most once a second. Each carries a closed `kind`, `tool`, `compaction` or `model`, set by the harness beside the label, and `SessionSummary.activityKind` carries the kind of `activity`. A report with no kind, from a box agent that predates kinds, reads as `tool`; any other kind is invalid. The engine streams it and clears it when the turn ends. It does not change a resume position.

### 3.4 Delivery and reply channels

The engine stores an event once and creates one delivery per recipient. A delivery records its source surface, reply channel and wake decision, and, when it went up past a parent that could not receive, that parent and why. The pure `room` package computes the mapping in section 7.5, and the store's `receiver` applies the chain of command. Final replies target a principal and conversation; an already-posted response is delivered quietly with a link. A turn can owe replies to more than one distinct target and home.

### 3.5 Operation and grant

Agent writes that need a decision are typed operations. The engine registry supplies the class, card, check and executor. The owner's own operations and `auto` operations run at once; `owner` operations wait for the owner, including for root. A kind may also let the room's root decide it when a room setting allows. Each setting is a `RootApproval` kind in `rooms.root_approves`, a JSON set that is empty by default: `hostexec` lets the root decide `hostexec.grant`, `addons` `addon.global`, `hosts` `room.hosts`, and `pools` `pool.add`. Only the owner changes them, with `room.set` (`rootApproves`, kind to on or off; an omitted kind stays) or `dyna room set <room> --root-approves-KIND on|off`, and `room.list` shows the set. The room's root sees the kinds that are on in its `dyna_room` section (7.9), so a switch the owner flips reaches it as a section change at its next turn; no other session has the section and no notice is sent. With a kind off the operation waits for the owner as before; with it on the root decides it with `op decide` as the owner can, including its own request, and the owner can still decide. The request still waits for a decision, and its card says who can approve. No setting covers CI switches (`repo.ci.set`, `host set --ci`), which are owner-only calls with no request to decide, or merging, which Dyna does not do (7.6). The engine rechecks before execution and fails stale cards without running. Pending operations expire after 24 hours by default, except `hostexec.grant`, which waits until it is decided or its session closes, across engine restarts; identical pending requests from the same caller return the existing operation. Waiting, decision and execution emit typed events.

Grants add powers outside the session tree. A new room grants root `ask-owner` and `hostexec` on all hosts, with no expiry, and subscribes it to notices. Only the owner grants host exec, unless the room's `hostexec` root-approves setting lets its root decide too (3.5). Section 6 describes the rules.

### 3.7 API

HTTP/1.1 serves typed `POST /v1/<method>` calls and typed errors. The owner Unix socket has mode 0600. Each box has its own Unix socket. The web listener binds loopback; paired devices use remote access. The listener identifies the principal and applies device scopes. Event streams use server-sent events and resume by sequence. The owner stream spans rooms; box traffic uses a persistent channel.

Owner-only `session.work` returns a newest-first page of turns, each with its start, optional end, input events and posts sent during that turn. The cursor is a turn ID. The default page has 30 turns and the maximum is 100.

Visual cards use stable IDs and versioned posts. Only the author or owner updates a card, within its room. The server checks file access and serves the HTML in a sandbox with a default-deny content security policy; interactive submissions require owner confirmation.

Owner-only search covers sessions and posts. Owner-only shell watch and terminal routes expose box output and terminals. Owner-only `box.stats` reads a running box's CPU, memory and disk while a panel shows it: the engine asks over the box channel, and the agent answers from its cgroup and a `du` cached for five minutes. Limits come from the box's size, because a box cannot see its slice. Nothing polls boxes in the background, and no reading is stored. The owner advances conversation read positions; room and session lists provide their current read and activity state. Session stop and refresh are available to the owner or an ancestor, and a session can refresh itself. Owner or room root can pause delivery and box wakes while active turns finish; resume dispatches waiting wakes. Standing-instruction reads and writes are owner-only, with hash-based stale-write protection (section 7).

The contract package is the authority for method names, fields, body variants and generated client types.

## 4. Store

### 4.1 Rules

The engine holds one SQLite `store.db`, protected by an exclusive `store.lock`. It uses WAL, `synchronous=NORMAL`, foreign keys and incremental auto-vacuum. `schema.sql` is the current schema; fresh stores run it, while existing stores run numbered steps from their version. The engine refuses a live schema that differs from it. Stores below the upgrade floor get `store_too_old` and the commit to update through (r17). The guard refuses a v1 `dyna.db` without `store.db`, and a store without the v2 format marker.

One writer commits each state change and its events in one transaction, then publishes events in sequence order. Reads use a read-only pool. A separate connection checkpoints the WAL; commits never wait for a checkpoint. Typed body columns hold JSON, but queried state is not kept in JSON files. Settings and other configuration may use JSON. Transcripts are append-only JSONL; attachments and large outputs are files addressed by SHA-256, per room (4.3).

The engine keeps no backups: no daily copies, no copy before an upgrade and no off-host archive. Relocation uses a fresh snapshot after writes stop (5.10). After cutover, measured growth may trigger archival of events older than 180 days for closed sessions.

### 4.3 Data on disk

`box.Layout` names every path of Dyna's data on both sides. No other code spells them, and a test refuses a data folder joined anywhere else. A room's data is one folder on each side, so deleting a room removes one folder per machine.

```text
<data>/rooms/<room>/AGENTS.md                   room instructions, the store copy (the one to edit)
<data>/rooms/<room>/compose/<name>.yaml         room compose files
<data>/rooms/<room>/addons.json                 the room's skills, Pi packages and MCP servers
<data>/rooms/<room>/skills/<name>/              the room's skill folders
<data>/rooms/<room>/files/<sha256>              attachments and large outputs
<data>/rooms/<room>/transcripts/<session>/      transcript copies
<data>/rooms/<room>/shared/                     /box/shared, the one copy
<hostdata>/rooms/<room>/instructions/AGENTS.md  the host copy of the room instructions, which a box mounts
<hostdata>/rooms/<room>/instructions/addons.tgz the room's add-ons, one file a box unpacks at its start
```

`<data>` is the store and `<hostdata>` is a host's own data folder. On the control-plane host that is also a capacity host the two are different folders (`dyna-next` and `dyna-next-host` on hermeslab). The engine writes the `instructions/` files of `<hostdata>` from the store copies on every host, that one included, so the host copy is the engine's synced copy of the store copy, and an edit of the host copy alone is overwritten at the next sync. A room's `shared/` exists only in the store, at `<data>/rooms/<room>/shared/`: the engine host's boxes bind it there, and no current code creates `<hostdata>/rooms/<room>/shared/` on any host. An empty folder of that name is left over from before the shared folder moved to one central copy (commit 7d360adc0), when each host kept its own, and it holds nothing a box reads. `docs/legacy-removal.md` lists it for deletion.

Everything else belongs to no single room:

```text
<data>/AGENTS.md                                global instructions
<data>/compose/<name>.yaml                      global compose files
<data>/addons.json, <data>/skills/<name>/       global add-ons
<data>/store.db, <data>/store.lock              the store and its lock
<data>/connect/                                 Connect credentials
<data>/pools/<name>/script                      a node pool's script, which runs here and no box can reach
<data>/cliproxy/, <data>/cliproxy/auth-v2/      the model proxy and its sign-in folder
<data>/git/<owner>/<repo>.git                   repository mirrors
<hostdata>/instructions/global/AGENTS.md        the global copy a box mounts
<hostdata>/instructions/global/addons.tgz       the global add-ons, as the room's
<hostdata>/git/<owner>/<repo>.git               repository caches
<hostdata>/bin/<version>/dyna                   engine binaries, with a current link
<hostdata>/cache/                               dependency caches
<hostdata>/share/rooms/<room>/shared/           /box/shared on any other host, through its one mount
<hostdata>/share/cache/                         that mount's local cache
<hostdata>/sock/share.sock                      the forwarded socket that mount reads through
<hostdata>/sock/<box>/engine.sock               a box's forwarded socket
~/.config/containers/systemd/dyna-svc-<id>.container   a service's quadlet file on its host (5.18)
~/.config/systemd/user/dyna-svc.slice           the services slice, CPUWeight=1000 (5.18)
```

Mirrors and caches are named by repository, and rooms share them, so deleting a room leaves them. Dependency caches are shared across a host. A box's socket goes with its box. Box volumes are Podman's.

Blobs are per room. A blob's name is its hash and its bytes never change, so each room that uses one holds its own hard link, with no reference counts: removing a room's folder cannot break another room. Every upload names a room. A session's room comes from its socket and the owner gives one in the query. A blob in the folder is what lets a post use it, so no table records uploads. When the owner forwards a post, the engine links each blob into the target room before the post commits. Sessions cannot reach another room's blobs. `event_files` joined to `events` gives the room of every stored reference: the owner reads a hash through its newest reference in a room that is not being deleted.

## 5. Machines and box lifecycle

### 5.1 Control plane and hosts

The control plane runs on an always-on host. That machine may also be a capacity host, reached over SSH like any other host (decision 14). The engine runs no boxes. One Dyna-owned SSH ControlMaster per host carries the engine's framed requests, and each host run has a connection of its own (6.3); a missing or invalid reply trailer is a transport failure.

Hosts come from two places: the owner registers one by hand, and a node pool (5.17) brings one when a box needs it. The owner registers hosts with `dyna host add <name> --ssh user@addr`, optionally restricting rooms; `dyna host limit <name>` (`host.set_limits`) later replaces that list, like `accounts.set_limits` for an account, and boxes already on the host stay there. A host also has two switches, which `dyna host add` takes and `dyna host set <name> --agents on|off --ci on|off` (`host.set`) turns, each on its own: `agents`, on by default, lets new session boxes land there, and `ci`, on by default except on the host the engine runs on (the host it identified as its own, 5.6), lets the CI pool start runners there. Hosts added before this default keep their switch, since the store cannot tell one never set from one set off. The room list says which rooms a host serves while agents are on. With agents off, admission places no box there, and a stopped box there waits with `room-host` until agents are on again, as for a room the list leaves out. With ci off, the pool starts no runner there, and those it has finish their jobs; runners return when ci is on. Both off disables the host and keeps it registered, as before. A host added exec only (owner, 2026-11-03, for the owner's own machine) is a separate stored flag, set only by `dyna host add NAME --ssh user@addr --agents off --ci off`, and a host with both switches off that was not added so stays a full host. Nothing ever places a box or runner there, and only host exec (6.3) uses it. Its check needs SSH and bash and nothing else: no Podman, FUSE, images, cgroups, disk floor or binary on the host, and no engine sync of instructions, forwards, maintenance or image builds. Its heartbeat runs one small script over the existing SSH master each 10 s beat, with no Podman or cgroup: it reads the whole machine's cores (`nproc`), busy time (`/proc/stat`), memory in use (`MemTotal` less `MemAvailable`) and the home folder's filesystem (plain `df`, without the btrfs metadata adjustment a Dyna host's disk gets). A host where the script prints none of them is online or offline and nothing else. The engine keeps these as the host's CPU, memory and disk figures and minute history, the same fields as any host, but only for display: they are never stored with the host's disk columns, it never counts as low on disk even at 99% used, and the low-disk notice to room roots, disk eviction and placement never consider it. An unreachable exec-only host is Unreachable with its last figures dimmed and when it was last seen, as any host is, never zeros. `dyna host list` shows `online` or `offline` with `-` for both disk columns, never `low`, and `exec only` in place of the two switches; the web machine card shows the same CPU, Memory and Disk tiles as the other machines, "Online" where they show a workspace count (it runs none, so it has no count), and a CI runner line only when it has runners; with no figures yet it shows its name and Online. Turning agents or ci on with `dyna host set` runs the full check first and refuses with its reason when it fails, so the host stays exec only; success ends exec only; `--owner-only-admin` gives the same confirmation as at `host add`, which an exec-only add does not need. What runs there when a switch goes off stays until it stops. `dyna host list` shows both switches. `dyna host remove <name>` refuses while a box or a CI runner is on the host, a subscription Run is on it or a room's rule names it, and says which; otherwise it removes the row and the engine's connection and forwards. With `--discard-boxes`, boxes on the host no longer refuse it: they fail as on a host lost for good (5.10). A host that is not exec only becomes ready after checks for delegated cgroup v2 controllers, rootless Podman 5 or later, SSH StreamLocalForwarding, curl, git, FUSE with `user_allow_other` on any host but the engine's (5.6), free disk and memory, and owner-only administration. Podman is required: the installer installs it and registration reports a typed error when it is absent (owner, q60). Schedulable memory excludes the host floor; CPUs exclude one, with a minimum of one. **Service host check.** A host that runs services also needs, and `host.list` reports as a `service_host` problem without making the host unready: linger for the Dyna user, the quadlet generator (`/usr/libexec/podman/quadlet`), `pasta`, and the value of `net.ipv4.ip_unprivileged_port_start`, which sets the lowest host port a service may publish (5.18). `host.list` gains `services`: each service on the host with its room, name, state, `cpuMilli` and `memBytes`. `dyna host remove` refuses while a service is on the host, as it does for a box.

Admission serializes placement. A CI runner skips a host where a session box is pending for CPU or memory and would be placed there if the host's runners were gone: its room's rule allows the host and it fits, so only runners keep it out. A box that fits nowhere, that its rule keeps off the host, or that other boxes keep out holds no runner back. Each placed box counts one quarter of its CPU and memory size until stopped, failed or deleted; lost boxes count. A CI runner is busy for its whole job but uses about half its CPUs on average, so the runners on a host also fit in twice its CPUs at their full size. Runner memory limits fit in the host's schedulable memory at 1x, since a compile can peak near its limit. A CI runner prefers a host that already has the current runner image over one with more free memory, and goes to a host that must build it only when no host with the image has room; the pool builds the image on every ci host in the background, outside its lock, so a new host or a deploy that changes the image delays no job that another host can take. A stopped box counts only disk. A host must fit requests, remain below 80% measured memory and retain its disk floor after new requests. A room that no host serves, because each is limited to other rooms or has agents off, waits with `room-host`; other waits report their reason. `--git.name` and `--git.email` set box Git identity only when nonempty (owner, q61). A service counts as a pending box for this rule: a service that is pending for CPU or memory and would be placed on the host if its runners were gone keeps runners off it until it is placed (5.18).

**CI pool lease.** The repository variable `DYNA_CI_POOL_UNTIL` is the lease that routes a run's jobs to Dyna's runners ([CI runners](ci-runners.md)). The engine holds it for a repository whenever the pool is alive for it, which needs both: (1) a scale-set listener of the repository is running and has polled (one that replaced a failed listener counts only after a poll reaches it), and (2) at least one host that is ready, has ci on and is allowed by the room's rule (`only`) answered the survey of the current pass. A pass whose store reads fail aborts with no write. Free slots, CPU, memory, disk, `--max` and the polls' capacity do not count, so a pool whose every slot is busy keeps its lease and its overflow jobs queue for a runner. A host with ci off, one that did not answer, no host at all, or listeners that keep failing before a poll lets it run out. A write sets the lease 15 minutes ahead and the next waits 5 minutes. The write comes right after the survey, before builds and the sweep, on its own 30-second timeout taken from the pass's outer context, so a slow host cannot delay it. The engine keeps only the time of its last write, so the first pass after a start writes at once. A restart, or a survey of up to 10 minutes, cannot open a gap. A survey longer than 10 minutes (it runs under the 20-minute `scaleLimit`) can still let the old lease lapse, since the write comes after it.

**GPUs.** A host reports the GPUs its CDI spec offers. The heartbeat's first good probe and then every thirtieth (about five minutes) runs `nvidia-ctk cdi list` and `nvidia-smi --query-gpu=index,name,memory.total`. A card counts when CDI lists `nvidia.com/gpu=<index>` for it, and its name and total memory come from `nvidia-smi`; a card CDI lists but `nvidia-smi` does not report has memory 0, which no request fits. Each tool runs under a five-second `timeout`, and a name may hold commas (the first field is the index and the last the memory). A host with neither tool reports no GPUs. The engine stores the list on the host (`gpus`: index, name, memory bytes). A probe whose SSH call fails leaves the last list; one that reaches the host stores what it found, and a tool that is missing, fails or times out counts as finding nothing, which empties the list. `host.list` carries each card with the VRAM boxes have requested of it (5.5), and the Home host card and Settings > Hosts show them. An exec-only host reports none. One-time host setup, for a host that has a card: install the NVIDIA Container Toolkit and run `nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml`.

### 5.2 Images

`dyna-base` contains Debian, shell tools, git, Node, tini and, unpacked under `/opt/dyna/extensions`, pinned releases of the Chromium extensions uBlock Origin Lite and I still don't care about cookies (5.14); PiG holds no credentials. The image holds no agent: PiG is in the box agent, and Node stays for the package extensions PiG runs and Chromium's setup. Versioned Dyna binaries mount read-only from the host, independently of the image. Toolchains are room images (below); they start from `dyna-base` and finish as the non-root user. A room with several box images needs a compose file to say which one a session uses (5.16).

**Room images.** A room keeps its own images in files beside its instructions and add-ons (4.3): `<data>/rooms/<room>/images/<name>/` holds one image's `Containerfile` and its build context, with the `box-needs` and `size` files described here. An image is a folder of regular files (links are dropped) of at most 3 MiB packed, and it has no global scope. `dyna image save NAME PATH` packs a folder and replaces the room's image of that name whole; `dyna image list` shows each with its content id, file count and size; `dyna image show NAME` prints its `Containerfile` and its file list; `dyna image remove NAME` deletes it. The `image` tool has the same four actions (`save`, `list`, `show`, `remove`). A session changes its own room at once, as it does a room add-on, and the owner names any room with `--room`. A name is lowercase letters, digits, `_`, `.` and `-`. `ci-runner` is reserved for the room's CI runner image: its `Containerfile` has a `FROM` that names `${DYNA_CI_BASE}`, the runner image Dyna ships, while every other image names `${DYNA_BASE}`. A `Containerfile` is read as a builder reads it (comments and blank lines skipped, a trailing backslash joins lines, instruction names in any case) and holds to one rule: it declares `ARG DYNA_BASE` (`ARG DYNA_CI_BASE` for `ci-runner`) before its first `FROM`, as the build passes the base with `--build-arg`, and every `FROM` is `${DYNA_BASE}` (or `${DYNA_CI_BASE}`), optionally `AS name`; only `ARG` may come before the first `FROM`. A parser directive (`# syntax=`, `# escape=`, `# check=`) in the opening comment block is refused, since it changes how the builder reads the file or swaps its frontend. A heredoc body is read as instructions, so a heredoc line that starts with `FROM` is refused too. Multi-stage builds are allowed, but each stage starts from the base, so a `FROM` of another image or of an earlier stage is refused, as is a flag on `FROM`. The save also refuses a folder with no `Containerfile`, an unknown `box-needs` word and an invalid name, all with a typed `invalid` error. Limits keep one room from filling the engine's disk: an archive packs to at most 3 MiB, a room holds at most 16 images and 128 MiB unpacked, and a save over a limit is refused with the limit named. A name is checked once where it enters the store, so it cannot name a folder outside the room's images. A save moves the old image aside before it puts the new one in place, and every list, show, remove and save first restores an image a crash left aside (unless a newer one took its place) and clears unfinished saves. The Containerfile is read by a small parser here and not by BuildKit's, which Dyna does not vendor; its refusals err toward refusing. The content id is a SHA-256 over the folder's sorted paths, execute bits and contents, so saving a changed folder changes the image tag (the base's tag and this id, below) and saving the same folder changes nothing. Deleting a room removes its images with its folders. A host does not keep a mirror of the store, unlike add-ons: nothing on a host reads an image folder, since a box mounts none, and only a build needs the files, so the engine sends the build context with each build and the host never holds a copy that can go stale. A host offline during a save has nothing to catch up on: its next build uses the current folder and builds the new tag. This is the store alone: a box uses the room's sole box image, or the one its compose file names with `build`; scheduled runs name one too. **Migration:** the engine moves the legacy images of each room's primary repository (the room's sole repository when it has one and none is marked primary) from its `.dyna/images/*` (default branch or `dyna-images`) into the room, once per room. It runs in the background after start, and again before a box start, a scheduled run or a session start chooses an image, so a mirror that came late, or a repository added after the upgrade, is moved first (a repository with no mirror is fetched then; until it is moved its sessions use `dyna-base`, and the log says so). Only the primary repository is moved, so a room never holds the images of several repositories, which would make every session start without a compose `build` refuse for the choice; the image names of other repositories are logged as left, and `dyna image save` adds one. An image the room already has is never overwritten. A copied Containerfile is not rechecked, so one with a literal `FROM` still builds, but `dyna image save` of the same folder refuses it until fixed. **Final skips**, recorded as done: the room has the name, the name is `ci-runner`, the files exceed 3 MiB (checked with `git ls-tree -r -l` before any archive is read), or the store refuses the folder. Any other failure, such as a git error or the 2 minute limit on one repository's git calls, is logged and retried at the next call. Image ids are content hashes, not git tree ids, so each migrated image rebuilds once per host. A session with no repository takes the room's sole box image, where it took `dyna-base` before. Update an image with `dyna image save`. After that no repository is read for images. Settings > Images shows them too (5.13). **CI:** a repository's runners use the `ci-runner` image of the room it has CI on in (`repo ci`), or the shared runner image when that room has none; the image is never read from the repository, so a PR cannot change what its own job runs on. Each ci host builds it on the shared runner image (`DYNA_CI_BASE`) from the engine's copy at its next build-ahead or placement, so a host that missed a save builds the current image. The tag is the room and the content id, so a save builds again. Dyna names the entrypoint and the user (`1001:1001`) when it starts a runner, so a file cannot change them. Placement prefers a host that has the image. A failed build (its last lines of output, or a limit of 10 minutes per layer) is logged, the host runs that room's jobs on the shared image, and `host list` shows the failure until a build succeeds, retried every 5 minutes. A room whose image cannot be read shows the same, on every ci host, and does not stop other rooms or the lease. A layer no room has now is removed from each host. The layer build has network access and may use `RUN --network=host` and `COPY --from=` another image, as a room's box images do, and a file can overwrite files in the image, such as the entrypoint script, though never the entrypoint or user a runner starts with; it gains no more reach than its own room's runner has. A repository is in one CI room, so rooms cannot conflict.

Optional `box-needs` requests `nested-containers` or `kvm`; unknown needs fail loading. These grant additional devices or kernel access. Missing devices fail creation with a typed cause; admission does not select by device. Restrict rooms to suitable hosts. See [the container recipe](nested-containers.md). Image tags hash the base and image folder tree. Host builds are serial and reuse existing tags.

Podman gives a box's user mapping its own copy of a whole image the first time a container uses it, and every Podman command on that host waits meanwhile. Boxes that are already running keep running, because they do not call Podman, and heartbeats do not call it either. So a new image takes that copy once, right after its build, by creating and removing a throwaway container with the box mapping. The copy outlives the container. The step stops after two minutes: the image still works, and its first box makes the copy instead.

When the engine starts, once a host's forwards and binary are back (5.3), and daily during host maintenance, each ready host builds what its boxes would use now: the base, the toolchain image of each repository in a room it serves, and each image that the compose files in reach of those rooms build or name, from the mirror as it stands. One image builds at a time on a host. A new box, a box swapped to a new image at wake and this pass all choose images in one place, so they agree. A box that asks before the pass reaches its image waits on the same build. The same pass then removes all but the newest two tags of each image, keeping any tag the host would use now. A removal is never forced, so an image that a container uses, stopped ones too, or that another image is built on stays for a later pass. The same pass keeps each service's current and previous image ref on its host (5.18).

### 5.3 Box states

A box records observed state and desired state separately. Observed states are `pending`, `creating`, `starting`, `ready`, `stopped`, `closing`, `deleted`, `failed` and `lost`; desired states are `run`, `stop`, `close`, and `discard`. The reconciler commits observed changes with compare-and-set, emits `box.changed`, retries durable steps and resumes after engine restart. It admits in creation order, with at most one step per box and four per host.

Starting a session inserts pending/run. A box stops once its session's list (7.4) needs no box, no wake is on its way and its last turn ended 10 minutes ago. It retains its volume and no longer counts for host CPU or memory. Over 100,000 tokens of context it compacts first (5.8). A waking delivery requests run transactionally and admission runs again. Dispatch requires ready/run. Each start checks the image: a stopped box on an old image gets a new container with the same ID and volume, and the session is told once that anything outside `/box` is gone.

**Restart notices.** Each way a box comes back tells its session once, in the second person, and the wording differs by cause: a new image (files under `/box` and the conversation kept, anything installed outside `/box` gone), a container that stopped and started again as after a host reboot or crash (files and conversation kept, running processes gone), a box recreated after it failed with `session.restart` (conversation restored, the old volume gone), and a `session.refresh` restart (files and conversation kept). Owner exception, 2026-11-04, to wording notices as facts: when the session holds an open goal (an active row in `goals`, read in the transaction that stores the notice and recorded in the notice), the notice also tells it to continue: check `git status` and the goal, reinstall what it needs, and keep going until the goal is done or it is blocked, without ending the turn to report progress. That notice is a waking input, so an idle session starts a turn, and the box with it if stopped. With no open goal the notice carries only the facts and is not waking, except the refresh restart, which always wakes because the session asked for it. A notice carries the box and the start it is about, so the same start reported twice wakes once. A start that fails again tells nothing until a start succeeds. A box stopped for being quiet and woken by an input says nothing, since that input is the news. A box found stopped after it was lost, but meant to stay stopped, tells its session when a later input starts it, since that start is the first since it stopped. A box whose current image cannot be built does not start, and fails like any box that cannot start. Sidecars follow the same rule (5.16). A running box keeps its image and its box agent until it next starts. The box agent reports the checksum of its binary each time it connects. A box on an older binary stops as soon as its list needs no box, even with a wake on its way, and that wake starts it again at once on the new binary. If a shell job or an open terminal holds it past its turn, the session gets one non-waking notice per box per binary, naming what holds it, and an unread notice is dropped when the box stops. The owner or an ancestor can put a running box under the same rule with `session.refresh`, for one session or a room, whatever its binary: it keeps its volume, unlike `session.restart`, and the notice comes once per mark. The mark lives in engine memory until the next box agent says hello, so an engine restart forgets it. A refreshed running box, whoever asked, comes back alone: once its turn has ended and the box has stopped, the engine writes one waking notice for that mark, which starts the box and gives the session a turn, with the goal text when it holds an open goal. That wake cannot be written sooner, or it would be steered into the open turn on the old binary, and a start that fails retries under the normal rules without a second notice. A session can refresh itself by naming itself. A refresh of a box that is already stopped marks it and starts nothing: its next start, by an input, is the first on the new version and says nothing. Creation retries before failure, and hello has a 60-second deadline. Repository preparation and instruction synchronization retain a 15-minute preparation bound. After instructions, host setup steps (compiler cache, shared mount, slice, forward, compose setup, container create, sidecars and container start) each have a three-minute deadline. Image preparation, including the wait for another build on the host, has a separate 15-minute bound rather than a three-minute compiler deadline. That preserves the previous creation budget for a compiler without charging binary transfer time against it. An image deadline is an image failure, not a host setup failure. A typed setup timeout names the host and step and counts as a host create failure; owner cancellation and engine shutdown do not. The SSH boundary joins its local process and I/O workers, and cancels the recorded remote frame group, including input receive, setup command and output drain, before resource cleanup; registration and a cancellation-marker check precede blocking I/O, so a late shell is fenced too. Cancellation kills and confirms every non-zombie group member; an abnormal wrapper exit preserves ownership metadata. Remote cancellation has an independent 30-second bound and an unconfirmed cancellation is a typed error, retained in the host driver's process-local pending set. Later operations must confirm those pending cancellations before claiming cleanup succeeded. This set is not an interprocess lease or durable operation log. Resource cleanup then gets an independent 30-second total bound, reserving half for remote cancellation confirmation and half for its commands, including resources whose creation reply was uncertain. Once container start has been attempted, error cleanup removes the container but preserves its workspace and stack volumes: an early hello may already have started session work. Only the lifecycle/store transaction may decide that an allocation is safe to retry on another host. Instruction and image gate waits observe cancellation instead of blocking on another session's mutex.

Binary installation has a three-minute idle budget, not a wall-clock deadline: bytes consumed by the SSH transport reset it, including for sessions waiting on the same host installation. Probe, verification and activation without transfer progress have the same idle bound. One host transfer is shared by its subscribers; stopping one subscriber does not cancel the others, and the last subscriber leaving cancels and joins the work. The preparation deadline does not truncate a progressing transfer. Start status carries the typed host, step and the time this session entered that step. After a minute, list/context/web show the step and its elapsed wait, for example `Starting on arch · updating Dyna on host (3 min)`; changing steps resets the elapsed wait. Stopping a pending, creating or starting session accepts the stop even without a running turn, cancels its start and prevents a late completion from marking it ready. Running-turn stop is unchanged.

A disconnected box becomes lost; the engine inspects its container when the host is reachable. A running container waits for reconnection, an exited one becomes stopped, and a missing one fails. The first crash restarts immediately, the second waits, and the third without a completed turn fails. PiG runs inside the box agent, so a crash in PiG is a crash of the agent, and the agent exiting exits the box. A resumed turn marks unfinished tool calls “interrupted: the session restarted while this call ran, so whether it finished is unknown, and it is not run again. A command it started on another machine can still be running there” and never reruns them. A recovered turn whose last assistant message failed (for example a 503 after retries) drops that message from model context and runs again; one that ended on a completed, length-limited or aborted (owner-stopped) reply is refused.

Deploy stages the new binary on every ready, non-exec-only host before restarting the engine. The compressed payload is cached once per binary and encoding. The existing in-process zstd encoder uses its best-ratio level (the library's zstd level 10-or-higher mapping), one worker, an 8 MiB window and its low-memory setting; no external encoder runs. The driver probes a working zstd decompressor on a cold host and uses it when available, otherwise gzip. A host with neither gets a typed missing-decompressor failure, without a new registration prerequisite that would strand an existing host. A checksum cache hit needs neither tool and sends no payload. The host checks the decompressed SHA-256 before atomically publishing `<hostdata>/bin/<sha>/dyna`. A host already holding that exact checksum receives no payload. Staging never changes `current`; activation belongs to the engine using that binary. Deploy logs per-host staging times and waits at most 20 minutes for its ready-host snapshot, taken by the helper before it compresses or transfers. Hosts added or made ready after that snapshot are handled by the new engine's normal installation path. The helper reads only existing host columns through a read-only database connection, without opening the store, migrating it or taking the engine's lock. At the cap it logs missed hosts and restarts; the independent staging process continues across the engine restart, and starts on those hosts can still wait for installation. A private temporary and checksum check make concurrent staging safe. The helper retries until completion or its separate 24-hour lifetime ends, and owns an immutable artifact under `staging/<sha>` that deploy's `stage/` pruning does not remove. Engine subscribers deduplicate within the engine; at the deploy wait cap the independent helper and a new engine can both transfer the same checksum, but neither can publish partial bytes or activate a different version. No host routing or firewall changes are involved.

An engine restart cuts every forward, because each SSH master dies with the engine, while containers and turns run on. The engine opens local sockets at once and starts without waiting for any host. Each host then comes back by itself, retrying with backoff until it answers: first the forwards, then the current binary, which only a starting box needs, and then image builds. A deploy's binary can take minutes on a relayed link, and no running box waits for it. A box cannot reconnect before its forward returns, so its disconnect time and hello deadline wait for that, for at most 10 minutes. A heartbeat still reports a host that is really gone. A restart that lands during all this loses nothing: the next engine does the same work from the store.

**One other-host create retry.** Before an allocation would fail with the typed cause `create_failed`, a never-ready box with no image and no session turn gets one automatic placement attempt on a different host. The used budget and the excluded first host are stored with the box, so an engine restart, replay or another failure cannot reset them. The usual per-host create attempts still apply on that second host, and host create-failure accounting is retained for the failed first allocation. Normal room rules, room limits, CPU, memory, disk, GPU and scheduling-health checks apply; no other eligible host produces a terminal failure naming that fact rather than waiting forever or returning to the first host. A failed second allocation produces one final failure notice. Stop and close intents win over the retry. Partial resources on the first host are recorded for cleanup there, never mistaken for resources on the new host.

A creation result can arrive after an early hello or a turn began. Such a box, or one with a previous successful run or an existing image, is not moved automatically: its failure names that the other-host retry was unsafe, and its volume stays on its host. There is no volume migration. Other failure causes do not use this retry. An explicit owner `session.restart` creates a new allocation, with a fresh one-other-host budget, under its existing discard confirmation.

The owner or an authorized ancestor can restart an open session with a failed box. Restart discards its volume, unpushed work and unacknowledged transcript bytes; it preserves the session, grants, feed and acknowledged transcript. The box returns to pending/run. A restart detaches a host with a create problem, of either kind (`create_failed`, `share_unavailable`), so admission can choose another. For a dedicated pool node, the pool first destroys the unused quarantined node, which counts against its maximum until destruction completes. Old resources may be orphaned when the host is unavailable. Closing is possible in any state; lost boxes wait for the host's return unless the owner discards them, and unpushed work can be lost (5.9–5.10).

### 5.4 Sizes and pressure

| Size | CPUs | memory.high | memory.max | pids.max | disk request |
|---|---:|---:|---:|---:|---:|
| agent | 1 | 2 GiB | 3 GiB | 1024 | 5 GiB |
| small | 2 | 4 GiB | 6 GiB | 2048 | 10 GiB |
| medium | 4 | 8 GiB | 12 GiB | 4096 | 20 GiB |
| large | 8 | 16 GiB | 24 GiB | 8192 | 40 GiB |
| xlarge | 16 | 32 GiB | 48 GiB | 16384 | 80 GiB |

Disk requests are accounting, not quotas. Any session may request any size. Defaults are agent for root and children, medium for leads, or a repository default. The engine emits non-waking `box.pressure` once per pressure episode. Box growth is cut until after cutover (owner, q40); start a new, larger box instead.

Heartbeats measure each host and the control plane with one script. Free space is what `df` calls available. On btrfs, under 2 GiB of metadata room (free metadata chunks plus half the unallocated space) counts as no free space; an unreadable sysfs falls back to `df`. The disk floor is the larger of 20 GiB and 10% of the disk, so at 90% used, new boxes and wakes wait with `disk`. A host is low on disk only when measured free space is strictly below that floor; equality is not low. This same rule drives `host.disk_low`, the low flag in `dyna host list` and the web's Disk low status, for ordinary hosts, pool nodes and the control plane. There is no early warning above the floor. An exec-only host is never flagged low. A missing or unreachable sample does not start or end a warning spell. The first reachable sample below the floor posts `host.disk_low` in every room and wakes each root, with the fact that closing a finished session frees its volume. Persistent per-host warning state prevents repeats, including across engine restarts. The existing anti-flap recovery stays: another notice waits for a reachable sample at least a tenth above the floor and at least an hour after the previous notice, then a new sample strictly below the floor, because the metadata rule can move free space to zero and back between samples. The low flag itself follows the measured floor, not this notice suppression. `dyna host list` shows use and the low flag for every host. Admission accounting and the eviction wait at or below the floor are unchanged.

### 5.5 Budgets and placement

Each box has its own slice and hard limit; the session tree carries no resources. All box slices sit under a host Dyna slice. Admission counts one quarter of each box's CPU and memory.high. At 80% measured use admission stops; at 90% memory.high slows allocation; at the host limit the kernel can swap. Registration warns if swap is absent. Services (5.18) are counted at 1x, not a quarter, and come off the host's CPU and memory before boxes and runners are counted: box CPU and memory.high sums are held to 4 times what is left, runner CPU to 2 times and runner memory to 1 times. Services take at most a quarter of a host's CPU and memory, and a stopped service keeps its reservation.

The owner accepts a kernel kill when RAM and swap fill, or at a box's own limit. A build may exit 137; a killed agent (which holds PiG) or init follows the crash path. The volume and session stay, and `box.pressure` records the kill. No pause policy ships unless pressure shows real kills.

A host quarantines new session-box creation after three completed box-creation failures in a row; retry attempts for one box count once, and missing-device failures do not count. A successful in-flight creation or the owner's `dyna host set NAME --clear-create-problem` clears it. Heartbeats do not. Running boxes and wakes of existing boxes stay, and CI admission is independent. What counts is exactly: failure to make the box socket, the slice, the forward, the container or its volume, or to start the container. Repository preparation, image build or pull, an error naming a missing or invalid image, compose failures, missing devices, and any step cut short by the creation deadline or by shutdown do not count. When a host becomes quarantined, its waiting boxes that built nothing yet are detached and place elsewhere, and their leftovers are recorded. A failed box shows the typed cause `create_failed` and the typed phase of creation that stopped (`remove_old`, `repository`, `box`); a compose failure keeps its owner-readable reason, and the raw error goes to the engine log only. Cleanup of a failed creation runs on its own short deadline, and a box failed by the startup check records its leftovers. Host list reports the typed problem.

New boxes choose the ready host with the most headroom: the smaller of its free CPU and free memory shares; existing boxes stay on their host. Children can run while their parent is dormant. `sameHost` pins a child to its parent's host. Default maximum depth is 3; zero removes the limit. Room limits count placed requests across hosts; zero means unlimited. There is no subtree cap. M1 uses hermeslab.

**GPU placement.** A session asks for a GPU with `gpu` on `session start`, a whole number of GiB of VRAM, at most 1 048 576 (1 PiB; decoding refuses more, so a request in bytes cannot overflow) (decision 2 applied to a card: a request, not a limit). On the wire `true` means 1 GiB and `false` none; the request decodes once into a number of GiB and nothing inside the engine sees the boolean. A workflow script asks for it for its crew's box in `meta.gpu`; an `agent()` worker shares the crew's box and has none of its own. Room and profile defaults do not exist: a session that wants a GPU says so. Admission counts, for each card, the requests of the boxes on that host assigned to it that are not pending, stopped, failed or deleted. A card takes a new request when `memory - memory/10 - counted >= request`: it keeps a tenth of its memory in reserve for the host's own use (a desktop, the driver), and a request that exactly fills what is left fits. A box goes to the first card, by index, that takes it, on the host admission otherwise picks; a host with no card, or none that fits, is skipped, and a box that no ready host takes waits with `gpu` (every card is taken) or `no-gpu` (no ready host has a card). A stopped box keeps its host and its card, and waking it asks that card alone, since its container was created for it. Node pools do not bring GPUs: a box that wants one waits for a host that has it and never for a node. `session start` refuses with the typed error `no_gpu` when no registered host reports a card, and with `gpu_too_large` when the request exceeds the largest card's memory less its reserve. **Accepted risk:** GPU memory has no cgroup limit, and the engine does not enforce a box's number. A box that uses more than it asked for makes CUDA allocations fail in the other boxes on that card and kills none, as a box over its RAM request does until the host runs out. Follow-up, not built: CUDA MPS with `CUDA_MPS_PINNED_DEVICE_MEM_LIMIT` could cap CUDA work on the 2080 Ti and the 3090 Ti, though not Vulkan or OpenGL rendering.

Once every sample from a ready host has been at or below its floor for a minute, the engine closes its oldest idle leaves, stopped or failed, without the 7-day wait or what only that wait respects, a goal or a PR (7.4): close hands the goals on. A sample above the floor, a failed probe, a missed heartbeat or an engine restart starts that minute again, so one bad reading closes nothing. It takes four per read, every 10 seconds. It skips a host with four closes running, or with eight stuck on a failed removal, so a failure common to every box stops eviction instead of starting the whole host without admission. It never closes a root, a session with an open child, a running turn, shell jobs, a pending delivery, a waiting question, or a pending, approved or running operation, and it leaves paused rooms alone. The normal sweep runs hourly, takes 200 leaves that passed 7 days, and keeps the PR and goal exemptions.

Disk work that is designed but not built:

- **Per-box quota.** A hard limit needs root plus an XFS graphroot with project quota, because rootless Podman has no volume quota and `--storage-opt size` covers only the rootfs. Measure instead: an hourly per-box volume size, `box.pressure` at the disk request, and a stop at a set multiple of it.
- **Shared cache caps.** Apart from the compiler cache, which keeps its own bound (5.6), `<hostdata>/cache` has no limit and no measure. Add it to the daily size pass and `host.list`, and delete a tool's folder past a cap. Share only Cargo's registry and git folders.
- **Orphan reaper.** Daily, list `podman ps -a --filter label=dyna.box` and `podman volume ls --filter name=dyna-box-`, and after a grace period remove any box whose row is deleted or missing.
- **Transcript retention.** Transcripts and files of closed sessions stay forever. Keep 30 days, delete by 90, alert at 20 GiB, and sweep files with no reference weekly.

### 5.6 Repository copy and shared caches

M1 boxes have no repository. From M2, the control plane fetches GitHub into its mirror and pushes a bare cache to each host. Starts of one repository that overlap share a fetch, and a push per host. A start only takes work that began after it asked, so it never gets older refs than it would alone. Repositories do not wait for each other, and nothing waits to read a mirror. Hosts hold no GitHub credentials. Boxes clone against a read-only cache and keep new objects in their own volumes. Git uses the engine route (5.7).

**A new session's branch starts at GitHub's current default branch.** The box creation step fetches the mirror, but the box clones the cache later (after the image is pulled or built, which can take minutes), and the session's branch (below) is cut from the cache's default branch, so a main that moved in between would seed the branch. So the box's first hello, while its session has no turn yet, fetches GitHub again before it answers with the repository (the same fetch, token and room check as every mirror fetch, and the same share per repository) and pushes the cache. The fetch and the cache push together are bounded to 10 seconds, and a fetch that finished within the last 3 seconds is reused, so sessions that start together share one. If they do not finish in time or the fetch fails, the session starts on the mirror as it stands, and the engine sends it one `session.notice`, once per box, saying its default branch was not refreshed and that `git fetch origin <branch>` brings it current. A repository with no mirror yet still fails the start, as it needs the first clone. A restarted box or one that already has turns does not fetch at hello.

Dependency caches are shared read-write per host; cross-box cache poisoning is an accepted risk. The compiler cache is shared read-write by a host's boxes and CI runners alike, so a CI job can poison what a box builds from too, and that is accepted as well. A Run gets `/box/cache` as well.

**Compiler cache.** Cargo in a box or CI runner compiles through sccache 0.18.0, which both images carry with `RUSTC_WRAPPER=sccache` set, so a repository's Rust build uses it with nothing of its own to set up. sccache's local disk cache serves one sccache server at a time, and every box and runner runs its own, so each host keeps one store instead: `dyna build-cache serve`, a user service on the host like the share mount, serves `<hostdata>/cache/build-cache` over WebDAV on the Unix socket `<hostdata>/sock/build-cache/cache.sock`, and sccache reads and writes it by key. A box or runner start brings the service up where it is not running, and a deploy leaves it on its old binary. A box mounts the socket's folder read-only and reaches it at `127.0.0.1:7781/build-cache`, which the box agent passes through. A runner has no box agent, so its entrypoint relays `127.0.0.1:3129` to the socket with socat, as it does for the proxy. A write lands beside its key and is renamed into place, so a box never reads half an entry. The store keeps 50 GiB, or a tenth of the host's disk if that is less. Every hour, past the bound, it removes the entries read longest ago, down to nine tenths of it. A read marks its entry used. sccache's keys hold the paths a build hands the compiler and every `CARGO_` variable: a dependency's key holds its folder under `CARGO_HOME`, which is also the compiler's working directory, and the target folder whenever the crate reads `OUT_DIR`, about one in eight of Horizon's. `SCCACHE_BASEDIRS` strips paths for C and C++ only. So boxes and runners build at the same paths and set the same two variables: `CARGO_HOME=/box/cache/cargo`, and for a box of a repository and a runner of it, `CARGO_TARGET_DIR=/box/work/<owner>/<repo>/target`, which is Cargo's default for a box's checkout and the folder a crew's worktrees share. A runner gets both as mounts of its slot's build folder, `cargo` and `target`, so they outlive the job like the rest of it. A box, a runner of any slot, and a crew all then hit what the others compiled. A job that sets its own `CARGO_HOME` or `CARGO_TARGET_DIR`, or another `CARGO_` variable a box does not have, such as `CARGO_TERM_COLOR`, keeps to entries of its own, and so does a build of a second repository in a box. Two kinds of crate still miss between a box and a runner, because their keys hold what the image's C toolchain made, and a box's Debian differs from a runner's Ubuntu: one that takes a derive macro, since sccache caches no proc-macro crate and each side links its own, and C code that a build script compiles. That is 35 of Horizon's 308 dependencies. A checkout's own crates are at different paths in a box and a runner, so they never match, which costs nothing in a dev build: sccache caches no incremental build, so a workspace's own crates in a dev build compile each time; the win is their dependencies. With the store down, sccache counts every crate a miss and compiles it: it skips its start-up check of the store (`SCCACHE_SKIP_CACHE_CHECK`), which would otherwise fail the build. A box or runner that sets `RUSTC_WRAPPER` to nothing builds without it.

Each room has one read-write folder at `/box/shared`, the same on every host. Its one copy is on the engine host at `<data>/rooms/<room>/shared/`, so deleting the room removes it. It survives box close. It has no hard quota, and losing the engine host loses it. The engine measures each folder daily into `room_shared`, and Home warns when one passes a quarter of the engine host's disk.

The engine host's boxes bind the folder directly. Every other host reaches it through rclone, built into `dyna` as the hidden commands `dyna share serve` and `dyna share mount`, so a host gets it with the normal binary and installs nothing else. A user service on the engine host serves each room's `shared` folder over WebDAV on a Unix socket, and a filter leaves the rest of a room's data out of what a host can list or read. Each other host gets that socket as a reverse forward over the SSH connection the engine already holds, so there is no new login and no inbound access to the engine host. A user service on the host keeps one mount at `<hostdata>/share/rooms`, with a local cache of up to 10 GiB. A box binds only its own room's folder, never the mount. Rootless Podman starts containers from a mount namespace of its own, held by its pause process, and on a host whose `/` is not a shared mount, as on WSL, a mount made after that namespace never reaches it. So each box start checks that Podman sees the same mount as the host, and when it does not, `podman system migrate` gives Podman a new namespace, but only once no container runs on the host, since that stops them all. Until then no box starts there, and the reason says why. A host other than the engine's needs `fusermount3`, setuid or run by root so that FUSE mounts work, and `user_allow_other` in `/etc/fuse.conf`. The host check reports what is missing, and the engine edits no host system file. A host that fails only this check is still ready and keeps its CI runners, but takes no session box: it carries the host problem `share_unavailable`, which `dyna host list` shows and `dyna host set NAME --clear-create-problem` clears once the host is fixed. A box create that finds the shared folder down on its host sets the same problem at once, when the box built nothing there; a box with files on the host is not moved.

The rules of the folder:

- Last write wins. Nothing merges or reports a conflict.
- File locks work on one host, not across hosts. A script that needs them pins its Run with `dyna subscription add --host`.
- Another host can take about 5 seconds to see a change.
- A dying host can lose its last 2 seconds of writes, because a host sends a closed file 2 seconds later.
- Heavy files that can be rebuilt belong in `/box/cache`.
- On a host other than the engine's, there are no symlinks or hard links, and every file reads as executable. A file made there lands on the engine host as not executable. A symlink on the engine host is left out for the other hosts: it is never followed.

The server and every mount outlive the engine, so an engine restart stops neither. It drops the forward, and host restore puts that back with the box forwards. Meanwhile a call that needs the server waits about 5 minutes for it, as a model call does (5.7). Past that it gets an I/O error, and the mount carries on either way. The heartbeat brings back a mount it finds down. A box bound to a mount that died loses `/box/shared` until it restarts, because a bind cannot move to a new mount. Under a mount that is down lies an empty local folder. A host makes no folder there, and a box cannot start on one that is not there, so its start fails with the reason and retries.

### 5.7 Box socket, model route and git

Each box receives only its own forwarded Unix socket. The engine derives session identity from that listener; no token is sent. The engine restores forwards after master failure, and the box agent retries and buffers output. Standing instructions mount read-only.

A profile may set `images: false` for its text-only models. At hello, the box receives the deduplicated model IDs from all such profiles and registers them with PiG, including every crew worker, so PiG substitutes image placeholders even after a profile switch. A box reads this list at hello; refresh running sessions after changing it.

**Profile methods and `dyna profile`.** `profile.list`, `profile.set` and `profile.remove` are the owner's. `profile.list` returns `profiles`, one entry per profile with the stored profile whole under `profile` (name, description, ratings, provider, model, `images` always explicit, thinking, allowed models, compaction trigger, `maxConcurrent`) and the read-only `inUse` count beside it, never inside it. An entry's `profile` is a valid `profile.set` body unchanged: `{"profile": entry.profile}` succeeds and changes nothing. `profile.set` with `create` false replaces the whole stored profile, so a client changes one field by reading the profile and sending it back with that field changed. `dyna profile list` prints a line per profile (name, provider and model, thinking, `images on|off`, sessions in use). `dyna profile show NAME` prints every stored field, one `field: value` line each. `dyna profile set NAME` takes one flag per stored field (`--description`, `--taste`, `--diagnostics`, `--intelligence`, `--cost`, `--provider`, `--model`, `--allowed-models`, `--images on|off`, `--thinking`, `--compact-tokens`, `--max-concurrent`); it reads the stored profile with `profile.list`, changes only the fields whose flags were given and sends the whole profile, so a flag-only change drops nothing. It refuses an unknown profile unless `--create` is given, which starts from an empty profile that the flags fill and the engine validates. `dyna profile remove NAME [--replacement NAME]` moves open sessions to the replacement; without one, a profile in use is not removed. The CLI has no `--json`, as no command has. A request body with a field the method does not take fails with `unknown field "NAME"`, the decoder's wording, which the `dyna` tool's `unknown field "x"; tool takes: ...` (7.9) also begins with.

PiG sends model calls to the box agent's loopback listener with a placeholder key. The engine checks the profile, substitutes the CLIProxyAPI client key and streams through the proxy's Unix socket. Besides the profile's models it passes the models of the session's last two dispatched turns, so a session that changed profile can finish its running turn and compact on the model it left. The engine records those itself at dispatch, so a box cannot name one. A crew may also call every model of its script's profiles (9.2). PiG alone retries a model call that reached a provider. A call that reached nothing, because it could not dial the box socket or its connection closed before any response headers, the box agent sends again with the call queue's backoff, from half a second up to ten seconds, for up to 5 minutes. That carries a turn across an engine restart: the drain holds new calls without sending them on, and closes the socket on them as the engine exits. A call that fails after its headers stays failed. Failed turns retry pending inputs with bounded backoff; paused rooms wait for resume. The proxy keeps each session's account binding in a file in its sign-in folder, with its expiry, and loads it at start, so an engine restart or deploy keeps a session on the account that holds its prompt cache; an exhausted or unavailable account still fails over.

CLIProxyAPI is a pinned vendored fork supervised as a separate child. Its patch ledger is `next/third_party/cliproxyapi/DYNA.md`. Strict cloak mode stays off. Claude sign-ins use cloaking, with the accepted account risk in decision 4. M1 stores proxy sign-ins in its protected file store; M3 moves them into its SQLite token store. Only the engine holds its management key. Shutdown drains admitted model calls before stopping the proxy.

**Local harnesses.** The owner can point Claude Code, Codex or another Anthropic-style or OpenAI-style tool at the same route. `dyna proxy env [--tool claude|codex]` prints lines to source: a loopback address and the owner's proxy key, which the engine makes on first use and keeps in `meta`. `dyna proxy reset` replaces the key. `dyna proxy serve` runs where the harness runs, on any machine with the owner socket (decision 14), and forwards that port's `/model/` paths and nothing else over the socket, so the engine opens no listener and its network listeners still accept paired devices only. The route is the box route with no profile, every account, no pin and one affinity, `local`, for all the owner's harnesses. A harness names real models, and the proxy refuses a model no account serves. It reads each request in full before forwarding it, so a reply that starts early cannot cut the upload short. It also serves `messages/count_tokens`, `responses/compact` and `GET models`, which a box does not need. Calls count against accounts as usual. `proxy.usage` (`dyna proxy usage`) totals them by model as the local client, and no session or turn sees them.

The key keeps "no secret in a box". `proxy.key` answers only on the owner socket, never on a box socket or the web listener, and a box's `/model/` stays its own session's. So the key never enters a box, and a box that reached the loopback port has nothing to send it. As with the sign-ins, control-plane host exec can read it.

From M2, git smart HTTP goes through the engine. Fetches cover room repositories; pushes cover only the session repository and its owned branches. The engine rejects unauthorized refs before forwarding.

**Session branches.** A session's default branch is its session name, and the engine records it as the session's own in `session_branches` (repo, branch, session, when). The engine gives it at the session's first box setup, after that setup's fetch, and tells the box the branch in `box.hello`; the box never derives it. A name with `..`, a trailing `.` or a trailing `.lock`, which session names allow but git refuses, is made valid first: a run of dots becomes `-`, a trailing `.` gets `-` after it and `.lock` becomes `-lock`. The engine never gives out `main`, `master`, `HEAD` or the repository's default branch; those are its protected names, and it does not ask GitHub for protection rules. It also skips any name that is a branch on the mirror just fetched, or the branch of another session in that repository that is not closed. Each skip tries the next suffix, `-2`, `-3` and on. A closed session's rows stay: they keep what a resumed run may push, and its name is free again for a new session when no remote branch holds it. A session's branch is the newest row it has; a session with none yet has no push right. The release that added the table gave every earlier session with a repository the row `v2/<session ID>`, the branch it already had, so nothing in flight moved. `dyna session set-branch SESSION BRANCH` (the owner socket only; it is how root moves a live session to a normal name) adds a row and makes it the session's branch, under the same refusals and with `BRANCH` as given, so it must be letters, digits, dots, underscores and hyphens, start with a letter or digit, and pass the same git checks as above; the old rows stay the session's own, so work on them still pushes and its PRs still update. The session gets a `session.notice` naming the new branch. Nothing is pushed or renamed on GitHub.

The git route lets a session push its recorded branches; `<branch>-<topic>` of each, where the topic is letters, digits, dots, underscores and hyphens, does not end in `.` or `.lock` and has no `..`, unless that name is itself the recorded branch of another session that is not closed; the branch of a PR it owns; and the recorded branches, with their topics, of the runs its run resumes (9.2). A refused push names the session's branch: `not owned by this session: it can push <branch>, <branch>-<topic>, ...`. The agent reads its branch in the `box.hello` prompt (`Your branch: <name>`) and the `pr open` default uses it. Boxes have outbound internet but no device keys; engine network listeners accept paired devices only.

**Failed upstream requests.** The git route logs each failed request to GitHub (`slog` warning "git route: upstream request failed") with the repo, session, path, status (0 for a transport error), attempt and the first line of GitHub's error, which is cut to 200 bytes and has the token and any credentials in a URL replaced by `[redacted]`. A failure is a 5xx answer, or, for a push, a 200 answer whose first 64 KiB holds `fatal error in commit_refs` (GitHub's own transient receive-pack error, after which no ref was updated). The route sends such a request once more, at once, when it kept the body: a fetch or advertisement (no body), or a POST with a Content-Length of at most 1 MiB, which the route reads into memory (git's `http.postBuffer` default and the bound on a push's command section). A chunked or larger body streams through once and is never retried, and a transport error is not retried because the request may have arrived. A 4xx is never retried. A commit_refs error later than 64 KiB into a response, or split across sideband packets, is not seen. A second failure goes to the client with its cause: a push that failed with a 5xx gets a 200 report `unpack GitHub returned 500 (a transient error on its side; a ref may or may not have been updated, and git ls-remote shows the remote's state); the engine retried once and it failed again` (git prints it as `remote unpack failed`), a 200 with commit_refs keeps GitHub's bytes and, with side-band-64k, gets one message-band line before them (`GitHub reported "fatal error in commit_refs" (a transient error on its side; no ref was updated)`), and a 5xx on a fetch keeps its status with that text as the body.

### 5.8 Box agent

The box agent runs the session's PiG in its own process (`harness/pig`) and the Dyna MCP server (7.9). PiG reads the same agent folder, `/box/pi`, as Pi did, and writes the same session files. In a crew's box the box agent runs the script instead (9.2), and no session; each crew worker is a PiG session of this same kind, in the same process. The session has only in-process listeners, so the box agent turns off PiG's buffered event channel: nothing reads it, and a full channel would hold the agent loop. M2 adds a secret-masking job server and transcript stream. `bash` (7.9) runs a command as a job, locally in a process group, or on a host through the engine (6.3). Stopping a job kills its group. Masking hides the fixed token shapes anywhere, and the value of a `NAME=value` or `"name": value` assignment whose name ends in key, token, secret or password only when that value looks like a credential: a run of at least 12 token characters, bare ones with a digit or a symbol, so code such as `key: &T` or `let key = (x, y)` is left as written.

A box with a GPU request (5.5) is created with `--device nvidia.com/gpu=<index>`, its assigned card, and no other GPU device. The CDI spec puts `nvidia-smi` and the driver libraries in the box; CUDA toolkits belong to the room's image. GPU boxes unset `VK_ICD_FILENAMES` at container creation so an image's forced software Vulkan ICD (such as lavapipe) cannot hide the vendor ICDs supplied by CDI; the Vulkan loader discovers them without a hardcoded vendor path. Boxes without a GPU keep the image's Vulkan environment unchanged. The card is stored with the box beside its host (`gpu_index`), set in the same write that places it, so an engine restart or a recreation of the container uses the same card.

PiG owns steer and follow-up queues. An input that arrives during a turn goes to PiG's steer queue, and PiG reads it after the current tool calls, before the next model request. The box's settings for PiG set `steeringMode` to `all`, so every input queued during one call joins that request together. The input keeps its own frame and reply, and the turn it joined owes that reply. A delivery is done only when the session file records its ID: PiG writes it as the `deliveryId` member of the input's user message, as the Pi fork did, and never sends it to the model. A steered delivery is `read` only once the box reports it done that way (`delivery.done`), which it does before `turn.output`: a steer can reach the box or PiG after the turn's last model request began, with PiG past its last queue check, and no request ever reads it. So when a turn ends, a steer it took that was never reported done goes back to pending instead of to `read`. After a completed turn it keeps its wake and starts the next turn as that turn's input. After a stopped one it waits for the next wake. At the end of each run, failed or not, the box agent clears what PiG still holds queued (`ClearQueue`), so that input reaches the model once, in the next turn: after a failed run the engine gives its unread inputs to the next turn too. PiG refuses a steer once its run has ended with `harness.ErrNoTurn`, and the box leaves that steer to the same rule. A steer that was read was reported done, so it starts no extra turn. Inputs that started the turn are read when it ends. Until `turn.output` commits, each reconnect resends `TurnStart` with all original inputs, including done deliveries, then unread later inputs as `TurnSteer` in sequence order. The runner skips IDs already in the session file. Identical turn-result retries do not duplicate events; conflicting results fail. Failed turns except `output_limit` return inputs to pending without waking, preserving reply channels. PiG controls compaction, apart from one case the engine asks for, idle compaction, below.

A turn start applies the session's profile with `Session.TransferModel`, on the first turn of each PiG session and whenever the model or compaction trigger changed. `box.hello` starts PiG on the current profile, so only this check finds a conversation that came from another model. PiG compacts on the model that last held the conversation when the context exceeds the target's limit, or when the model changes and the context is over 100,000 tokens, because the new model starts with a cold prompt cache. If compaction fails, a conversation that fits moves whole, and one that does not moves with a boundary that names the session file. The channel keeps reading during a transfer: steers wait in the runner until PiG accepts the prompt, and a stop cancels the compaction, leaves the model unchanged and returns the inputs to pending (`not_started`). Only a model PiG refuses fails the turn (`set_model_failed`). That is a patch of Dyna's PiG fork (P4), and keeps the compaction trigger for the session (P3).

**Idle compaction.** A stopped box wakes to a cold prompt cache, so its next turn pays for its whole context. When a box is about to stop for being quiet (5.3), the engine sends `Compact{Turn, OverTokens}` with 100,000 tokens, and the stop waits for the answer. The box agent asks PiG for the context size (`Session.ContextUsage`), which is PiG's own measure and not summed turn usage, and over the limit calls `Session.Compact`. PiG knows no size right after a compaction, so that case does nothing. `box.compacted` answers, after the transcript has gone out; the compaction itself is an ordinary entry in the session file, shown in the transcript like any other. A real try, whether it worked or failed, becomes one `session.compacted` event, which carries its usage against the session and names the session's last turn. That turn is the quiet period, so a period tries once, across restarts of the engine, and a failure neither blocks the stop nor repeats. An ask nobody answers runs out after 11 minutes, past the box agent's own 10-minute limit, and the box stops; an older box agent skips the message, so this is how it stops. A wake during a compaction sets want back to run, so the stop never happens, and the turn waits for the compaction before its transfer: PiG refuses a prompt until then, the channel keeps reading, and steers wait in the runner as they do during a transfer. A stop of that turn cancels the compaction and returns its inputs to pending (`not_started`). A crew has no conversation of its own, so it never compacts.

The transcript stream sends offset-addressed chunks and resumes from the last acknowledgment. Replacement boxes retrieve acknowledged files when needed. `transcript.read` is owner-only and returns bounded tool steps; agents read a digest of their own room's transcripts through `transcript.digest` (7.9). A read that returned an image carries only a marker; the owner-only `/v1/files/transcript` route serves the bytes from the engine's transcript copy, so a preview stores nothing new and needs no box. A quiet box uses the current host binary on wake.

### 5.9 Close

Dyna's own git operations in a repository never run its hooks: the diff saved at close, a crew's branch pushes, trees, commits and merges all run with `core.hooksPath` set to nothing on the command line, which beats a repository's hooks folder and its own `core.hooksPath`, and the pushes also pass `--no-verify`. The agent's own git commands are its own, and its repository's hooks apply to them.

Close durably closes the subtree deepest child first; move a child first to keep it running. Nothing a session holds refuses a close: the owner and its ancestors can always close it, and its list (7.4) says what happens. Root alone cannot close. A turn still running when its session closes ends as `stopped` with the typed cause `closed`, not as a failed turn: the close stops the agent program, which the box reports as a harness failure, and the engine records the close as the cause when the session is closing. It sends no reply and no failure notice. Stop the harness and jobs, save a diff of what is not pushed, remove box resources and emit deleted and `session.closed`. Close keeps no archive and pushes nothing: a session's pushed branches are its record, and work in its tree that was not pushed is lost with the volume, except for the diff.

**What counts as unpushed.** A commit is pushed when the remote has it, even if the box's last fetch predates it, so the check fetches first: before it compares a repository's worktrees, the box runs `git fetch --prune origin` there, within 15 seconds of its own (inside the 60 for the step). Pruning drops the remote-tracking branches the remote deleted, such as a merged branch, so the comparison falls to the base branch that holds the merge. The commit count, the changed-files count and the `.diff` all use that one base, so a merged commit is in none of them; uncommitted and untracked files still count as unsaved. A fetch that fails or times out does not hold the close: the old remote-tracking branches are used, the section says the figures may be stale, and the notice names the repository and the reason and says the figures come from the box's last fetch and may count merged work as unpushed.

**The diff.** A box that is connected and had turns is asked once, before the removal, to write `/box/shared/archives/<name>-<id>.diff` in the room's shared folder, so no git push and no engine endpoint are involved and it works for any repository. The file is one section for each worktree of each repository, the main tree first and then any other worktree `git worktree list` names, as a crew's worker trees. A section holds a header with the repository, path, branch and the commit it is taken against, then `git log` of the commits after the newest one the branch shares with its remote branch (`origin/<branch>`, or the base branch if the branch was never pushed; with neither, its whole history), with their messages, then one `git diff --binary` from that commit to a snapshot of the tree. The snapshot holds the committed, uncommitted and untracked work, made through a temporary index so the branch and index do not change; binary files are in it as binary patches. **Untracked files that `.gitignore` does not list are included**, a `.env` or a token among them, so the box writes the file 0600 into a folder it makes 0700, through a new temporary file that a planted link cannot redirect. **The shared folder does not keep those modes.** WebDAV carries no file modes (5.6), so on a box that reaches the folder through the share mount the modes the box asks for are dropped: the mount shows every file as 0777, the engine host creates what lands there with its own umask (664 and 775 on hermeslab), and a `chmod` through the mount changes nothing. What holds is that the file is in the room's shared folder, which every session of that room reads and no other room does, so an untracked file with a secret in it is readable by the room's sessions and by whoever reads the room's shared folder on the engine host. Files git ignores are never included, so secrets in ignored files stay out, and symlinks are recorded as links and never followed out of the tree. A section with no unpushed commit and no change is left out, and with every section left out no file is written. Each worktree gets 20 seconds and the whole step 60. A section whose diff is over 10 MiB holds the commit list and `git diff --stat` only, and says so in its header. The git commands are Dyna's own and never run the repository's hooks.

The step is one try, and a worktree that fails does not cost the others: its section says `not saved: <reason>`, the other sections are written, and the notice lists each failure. If the write fails, or every worktree fails, close goes on and no file is written. The close notice to the parent says which: it names the file with its commit and file counts, says `nothing was unpushed`, or says `no diff was saved` with the reason. **Unpushed work in a dormant box, or on a host that is unreachable, is lost on close**: a dormant box is not started for it, and a box that does not report within two minutes is removed all the same, so the notice reads `not checked, nothing saved` with the reason. A session with no repository, or with no turn, gets no notice.

Removal failure leaves the box closing, and the engine retries it every 30 seconds. A box on a host that is not ready is not waited for: the engine lets go of it at once, as a room delete does, and the host removes the box if it returns; the notice says `not checked, nothing saved`. Disk eviction closes the same way. `session close` has no `--discard`, because a close never waits for a box; `room delete` keeps the flag as its confirmation. Older versions pushed `refs/dyna/archive/<session>` refs to repositories. They stay where they are: Dyna never reads or deletes them, and the git route refuses a push of that name. There is no restore from a close, and `session restart` of a failed box is unchanged.

**Room delete.** Only the owner deletes a room: `dyna room delete ROOM --discard`. The flag is the confirmation, and `room.delete` refuses a request without it. Deleting a room never widens access. An empty account or host limit means every room, so the delete refuses with `room_limited`, naming each account and host with no other open room, until the owner changes those limits with `accounts.set_limits` or `host.set_limits`. A limit that also covers another open room just loses this one. One transaction makes this check and sets the room to `deleting`, so a concurrent limit change cannot slip past, and from then on no account or host limit can name the room. The same transaction starts every open session on the close path with discard, stops host commands, and makes pending operations due. From then on the room refuses new sessions, posts, uploads, instruction saves and transcript chunks, mentions cannot name it, no box in it can wake, and a second delete gets a conflict that carries the reason, if any, the first one is held.

The reconciler does the rest, with one step per room at a time. When every session is closed and no operation or host command still runs, it removes `<hostdata>/rooms/<room>` from each ready host, in the host's user namespace, since a box can leave files that the host user cannot remove. It then removes `<data>/rooms/<room>` and deletes the rows in one transaction, children first. Each step tolerates having run, so a crash at any point resumes from the top on the next pass. A ready host that fails, whether removing the folder or a box, holds the room and shows why in `room.list`. A room's services go the same way: each is stopped and removed with its quadlet, secrets and data volume on a ready host, and its row goes in the final transaction with the room's other rows (`service_secrets` first).

An offline host neither holds the delete nor gets skipped. A closing box on a host that is not ready counts as deleted at once, and each such box, and the room's folder on each such host, becomes a row in `room_leftovers`, which outlives the room. `host.list` counts these rows. When the host is ready again the reconciler removes the boxes and then the folder, and only then the rows. Until it does, the host keeps the room's data and any such box keeps running, cut off from the engine. A service on such a host becomes a `room_leftovers` row of the same kind and is removed with the box rows when the host is ready again.

Accounts and hosts survive a room delete with their links to the room dropped. A repository another room lists stays, with its default room moved to one of those rooms. One that no room lists goes, with its CI hosts.

### 5.10 Host failure and relocation

Three missed 10-second heartbeats make a host unreachable, and its ready boxes whose agents are not connected lost. A probe that fails while the SSH master still gets keepalive answers is a reachable but busy host, not an unreachable one. Three consecutive failed probes mark scheduling health degraded until a good probe resets it; new session boxes and CI runners skip degraded hosts, while existing boxes and their wakes stay on their host. Before any probe, health is unknown and does not independently block a checked host. Exec-only hosts report probe health but never take boxes. Health is process-local and independent of reachability, so a box whose agent holds its channel is running whatever scheduling health says. Lost boxes wait for that host; they never start on another (owner, r22). On return, running containers await agent reconnection, exited containers stop, and missing containers fail. No box can move to another host, because its volume stays on its host. For a machine that is gone for good, the owner runs `dyna host remove <name> --discard-boxes`: in one write the host closes to admission and every box on it becomes `failed`, with reason `host removed` and cause `host_lost`, from any state. On a host that answers, each box's container and volume are removed; on one that does not, they go with the machine and only the engine's side goes. The boxes let go of the host and it is removed, whether or not it answers. Work that was not pushed is lost. Each parent hears of the failure once, and `dyna session restart` gives a session a new box on any host. A box being closed has nothing left to do, so its session closes with the box discarded. Removal does not restart sessions itself: a restart sets the box to run, which would wake a dormant session, and a failure cleared at once would reach no parent. Host drain is not built. A service on a host that goes unreachable shows `unreachable`, with its last state kept, and is not moved: it stays on its host for good, and the next heartbeat after the host returns gives its real state. `dyna host remove --discard-boxes` makes each service on the host `failed` with `host_removed` in the same write (5.18).

Relocation is manual (r22). Stop the old engine and keep it stopped. Copy a fresh SQLite snapshot and the remaining data, including credentials and Connect secrets, over SSH. Verify integrity, start the new engine and restore forwards. Boxes keep running and buffer. Delete the transfer copy. M3 provides `docs/relocate.md`.

### 5.11 Carried from D-585

Shell commands run in boxes. Node jobs are not ported; GitHub Actions runs CI on [Dyna's runner pool](ci-runners.md) or GitHub-hosted runners. Host-specific work uses host exec or room placement. One SSH master per host carries builds and forwards; host exec runs over connections of its own.

### 5.12 Accounts page

The owner manages accounts and room limits in the web app. The engine alone calls CLIProxyAPI's management API. Connect uses the proxy's OAuth or device flow; key entry passes the key to the proxy without displaying it again. The owner can add any OpenAI-compatible provider with a name, address and key, and the proxy reports each account's models, which is the list profiles choose from. Usage for every provider comes through the proxy's `auth-files/quota` readers without exposing model tokens to the engine. Typed `account.quota_low` and `account.failed` alerts are the only colored account chips. Account changes are owner-class.

New work goes to the account whose quota expires first (`routing.strategy: soonest-reset`). Session affinity keeps a session on its account, so the order steers new sessions and failover. The proxy computes the order and publishes it, and `accounts.quota` marks each provider's next account active from that order, so Home and routing cannot disagree. A 402 insufficient-balance answer exhausts the whole account, not one model: routing skips it for an hour or the upstream retry hint, and the order carries the typed reason `insufficient_balance`, which `accounts.quota` shows as the usage cause (CLIProxyAPI [#4853](https://github.com/router-for-me/CLIProxyAPI/issues/4853)). The owner can choose an account for a session, by session and never through the box, on the session's About panel. A chosen account outranks affinity. When it cannot serve a request the request runs on Automatic and the row says so. When an upstream overload cools every account of a model, the next request finds none to pick and the proxy fails it with its own `auth_unavailable`; the failure body carries the upstream error's own code (for example `server_is_overloaded`) as `error.code`, so the turn reports the overload as the cause. The cooldown is unchanged.

- **Failed attempts.** An assistant message that a later `context_edit` record removes from the model's context (`replacement` null; Pi writes one after a model call failed mid-stream, and for the tool results paired with it) is not shown: none of its thinking, text or tool calls become items. ### 5.14 Computers

Each box has one desktop at the agent's size, 1280x800. TigerVNC's `Xvnc` is both its display and its VNC server, on the box-only socket `/run/dyna/vnc.sock`; `jwm` gives it a taskbar and nothing else; Chromium runs in a window on it, with DevTools on port 9222 for the agent's actions; `xdotool` is installed for agent input. Chromium loads the image's uBlock Origin Lite (with its cookie-notice, overlay and other annoyance lists on) and I still don't care about cookies at every launch, with `--load-extension` and `--disable-features=DisableLoadExtensionCommandLineSwitch` (Chromium 156 loads them without it; Chrome 137 and later need it), since a managed policy cannot install an unpacked extension, so a Playwright attach on 9222 sees them too. Both extensions can read and change every page the browser opens (uBlock Origin Lite holds all-URL access with scripting and user scripts; the cookies extension holds http(s) access with tabs, web requests, web navigation and notifications), so they are pinned, loaded unpacked, never update themselves and never touch the Web Store; a bump changes the tag, URL and sha256 in the `dyna-base` Containerfile and rechecks that the three annoyance rulesets (`annoyances-cookies`, `annoyances-overlays`, `annoyances-others`) are still turned on. Chromium launched with a missing extension folder stops answering DevTools, so the folders belong to the image and are never optional. The non-root user owns them, because Chromium writes each one's indexed rulesets under its `_metadata` and fails an extension with rules when it cannot; Debian's `/etc/chromium.d/extensions` is cut to `--enable-remote-extensions` so no empty `--load-extension=` joins the argv. `scripts/check-extensions.sh` checks both in the built image. Nothing runs until the first agent action or `computer.start`. All of it runs in the box's `computer` cgroup with half the box's memory, and stops with the box; a Chromium that exits opens again on the next use. The box reports `computer.changed` while the display runs. Agents can drive loopback pages and public sites, but not the engine web app.

The agent's `computer` tool has v1's actions, one to a call, and the box runs them itself. Pointer input (`click`, `move`, `drag` and `scroll`) goes to the whole desktop through `xdotool`, as real X input in any app, and `xdotool` also finds `launch`'s window. All keyboard input (`key`, `type` without a selector, and the keys a click, drag or scroll holds) sends Xvnc's own key events, since Xvnc keeps a key it maps onto a spare key code mapped and xdotool does not; `open`, `text` and a selector's `type` use DevTools, and a selector's `click` is a real click at the element's center. Key names are v1's: its aliases, single characters, and X keysym names from xorgproto checked before any input, plus chords such as `ctrl+l`; with Shift in a chord, a character is the one Shift types, as in v1. After each input the box watches Xvnc's own changes, as v1 waited for output damage, and returns what changed once the screen settles: up to 1 second for a first change, then 200 ms still, within 3 seconds. `screenshot` returns the desktop, a region of it, or Chromium's whole page; `launch` starts an app with its own log and waits for its window; `wait` pauses; `stop` stops the desktop. An action's optional `status` is v1's intent line, which the owner watching reads under the screen.

The owner's view is noVNC in the web app. `computer.start` (owner, `computers` scope) starts the desktop and returns once it runs. `GET /v1/computers/stream?session=` is a WebSocket, also under `computers`, that runs the box's `dyna computer stream` through the host's `podman exec -i`, with no terminal, and carries the VNC bytes both ways. Xvnc sends only changed regions, as continuous updates paced by fences up to 60 frames a second, so the frame rate does not depend on the distance. While the picture moves it streams at JPEG quality 6; after 1.5 seconds still it asks for quality 9 and a full redraw. Watching, Xvnc draws the pointer into the picture, so the owner sees where the agent points; in control, noVNC draws the owner's cursor in the browser. An open view keeps the box awake, as an open terminal does.

The session header's Computer button shows while the box is ready. The view floats over the app at the desktop's shape, scaled to fit, on every display; the desktop never resizes for it. A double tap or double click makes it full screen and gives the owner control; leaving full screen gives control back. Full screen has a chat bar along the bottom, the session's DM composer. Sessions cannot send owner input, and owner input does not pause them. No second browser, recording, reminders or host computer ships.

### 5.16 Compose files

A compose file gives a child session a chosen toolchain image, and sidecars such as a database. Files keep the AGENTS.md levels:

```text
<data>/compose/<name>.yaml                global
<data>/rooms/<room>/compose/<name>.yaml   room
.dyna/compose/<name>.yaml                 repository, on the default branch or the dyna-images branch
```

A name resolves global, then room, then repository, and the most specific file wins whole, with no merging. `session.start` takes `compose`, and without it uses `default`. With no file of that name at any level, the session starts exactly as it would with no compose files. A room's root takes none. `compose.list` (`session compose_list`) gives each name a session could use, its winning level, and why it would be refused. There is no write path: the owner keeps the global and room files, and agents keep the repository's.

The session keeps the name. Every start reads the file again and checks it again, as it does an image, so a broken or deleted file fails that start, and a dormant session cannot wake until the file is back. It can still close, which reads no file. A named file not found in the mirror fetches once, as does a first session of a repository; otherwise `default` is read from the mirror as it stands.

```yaml
services:
  agent:                                # the agent's box; this name is required
    build: rust                        # a room image (dyna image list); without it, the sole box image or dyna-base
    environment:
      DATABASE_URL: postgres://postgres:dev@db:5432/postgres
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: dev
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 2s
      retries: 20
    mem_limit: 1g
volumes:
  pgdata:
```

**What a file may hold.** A file comes from a repository, and agents can write repositories, so it is untrusted at every level. `engine/compose` parses it with `compose-go`, and anything not listed here is refused with an error that names the key. A session start checks the file first, so a bad file fails there.

| Key | Allowed |
|---|---|
| top level | `services`, `volumes`; a volume is only a name, with no settings |
| every service | `build` (the name of a room image; `.dyna/images/<name>` still reads as that name), `environment`, `volumes`, `depends_on` |
| sidecars | also `image`, `command`, `healthcheck` (`test`, `interval`, `timeout`, `retries`, `start_period`), `cpus`, `mem_limit`, `pids_limit` |
| service `volumes` | a declared name, a plain absolute target, optionally read-only; an agent's cannot cover `/box`, `/opt/dyna` or `/run/dyna` |
| `depends_on` | a list, or `condition: service_started` or `service_healthy`; nothing depends on `agent`, which starts last |

A sidecar takes `image` or `build`, and an image must come from a registry; `localhost` would reach other repositories' images on the host. It is pulled with no sign-in. A sidecar's `build` image may not have `box-needs`. The agent's own image, command and limits belong to its box. Limits may not pass the session's size. A file holds no variables and has no environment to read from: `$VAR` is refused, `$$` is a dollar sign, a name with no value is refused because it would pass the host's through, and an agent cannot set what Dyna sets. So a box's environment comes only from the file and Dyna, and no secret reaches it. A file is at most 64 KiB, with at most 16 services.

**Running it.** One service is the box; a file with only `agent` needs no pod. Other services run in a per-box Podman pod, with the box's user mapping, in the box's slice, so together they stay under its hard limit and admission counts nothing extra. They share only the network: `127.0.0.1` reaches each service, and so does its name, through the pod's hosts file. They do not get the box's socket, repository cache, `/box` or any host path.

The pod always names `pasta`, whatever a host's `containers.conf` says. So a sidecar never gets host networking, and a host where pasta cannot start, such as an LXC guest with no `/dev/net/tun`, fails the start with Podman's reason. The shared loopback is the accepted cost of `127.0.0.1`: a sidecar can reach the box agent's ports and act as that session, and a sidecar that takes one of those ports first keeps the box from starting. So a file's images carry the session's trust, like anything the agent itself runs.

**Lifecycle.** Sidecars start in `depends_on` order, each once the one before is up and, with a healthcheck, passing. Dyna runs that check itself, for at most two minutes, so there are no Podman timers. The box starts last, so it never says hello before they are ready. Sidecars stop with the box and follow its dormancy. A box that is closing starts without them, so a broken sidecar cannot hold up the close.

A start compares the stack with the one on the host, which covers each sidecar's image and settings. If either that or the box's image changed, the whole pod is replaced, volumes kept, and the session is told once. Compose volumes are named after their box and go with it, and with a restart. They sit in the same Podman store as the box volume, so the host's disk floor sees them and the session's disk request covers them, with no hard quota (5.5). A new image is pulled once and warmed like a box image. Build-ahead covers both, but image pruning only covers Dyna's own tags, so a pulled image stays on the host until removed by hand. A sidecar that dies while the box runs is not restarted until the next start.

### 5.17 Node pools

Dyna decides when a node is needed, and a small script knows how to get one, so Boat, EC2 or anything else works and Dyna never knows which. The script answers `create NAME SIZE`, which prints `{"ssh": "user@host:port"}`, `destroy NAME`, and `list`, which prints a JSON list of the names it still has. It lives at `<data>/pools/<name>/script` and runs on the engine host as the owner's user, in that folder, with a timeout and a bare environment. Stdout is parsed, and stderr goes to the log and the failure notice. No box can reach it.

```sh
dyna pool add boats --script ./boat-pool.sh --per-session --max 6
dyna pool list
dyna pool remove boats
dyna room hosts horizon --only boats
```

A pool is a name, a script, `max`, `per_session` and `idle`. A node is an ordinary row in `hosts` with `pool` set, and `box` for the one box a per-session node serves, so the host check, heartbeats, the shared folder, images, admission and the disk rules work unchanged. `dyna room hosts ROOM --only POOL[,HOST...]`, held in `rooms.only_hosts`, restricts where a room's new boxes go; `--clear` removes the rule. It names at most one pool, and a box already placed stays where it is. A shared node serves the rooms whose rule names its pool and the rooms with no rule, which may use any host; a per-session node serves only its box. A node has ci on, and serves the CI runners of the rooms whose rule names its pool as it serves their boxes: a job no host takes waits for a node as a box does ([CI runners](ci-runners.md)). The owner adds a pool directly. A session's `pool add` or `room hosts` waits for the owner as `op.requested`, because it runs on the engine host and costs money, and the card shows the script. Scripts get no secrets from Dyna.

`pool.set` changes a pool's `max`, `per_session` or `idle`; an omitted one stays. It is the owner's alone, for Settings > Pools: agents' `pool` tool keeps add and list, and the CLI has no command for it. It refuses, before anything changes, a request that sets none of them, a `max` below 1, an `idle` below zero or over 2562047 hours (the most a duration holds in nanoseconds, which is how the step reads it; `pool.add` refuses the same), and a pool that does not exist. A zero `idle` makes 30 minutes, as at add. The step reads the pool on its next pass. A lower `max` deletes no node: the pool makes none until it is below it. A new `idle` counts from when each shared node emptied. A node already up keeps the shape it was made with, so after a change to `per_session` a shared node goes once it is empty and a per-session one keeps serving its box until that box is gone.

One step beside the reconciler moves each node along, and the row says where it is, so a restart carries on:

- **Grow.** A new box waits with `pool-node` when its room's rule names a pool and nothing can take it. Below `max`, counting nodes being created, the step generates a name, records a `provisioning` row, runs `create` and then the host check and setup. The row comes first, so a restart cannot lose count: it finds a `provisioning` row that no step holds, runs `destroy` once and removes it. With `--per-session` a node serves exactly one box. A shared pool adds one node at a time, because the first may take every box that waits. A node too small for the box it came for is a failure.
- **Failure.** A failed create or host check runs `destroy` once and removes the row. Boxes wait with `pool-failed`, `dyna pool list` shows the problem, and the pool backs off from a minute, doubling to an hour. The first failure of a spell posts one `notice.posted` in the box's room.
- **Shrink.** A per-session node goes when its box is gone, and a shared one after it has held no box for `idle`, 30 minutes by default. Closing it to admission and checking that no box is on it are one write, so a node is destroyed only after its box is deleted. It stays `draining` until `destroy` works, so `max` never loses count of a machine. A dormant session keeps its node, which costs money until the session closes. The idle clock is in memory, so a restart starts it again.
- **Audit.** Every 10 minutes the step runs `list`. A name with no row is one notice in a room that names the pool, or else the first open room, and it is never destroyed. A node the script no longer lists is marked unreachable, the lost-host path takes it from there, and a heartbeat that answers brings it back.

A subscription Run follows its room's rule but never uses a node, so a room limited to a pool alone has nowhere to run them.

### 5.18 Services

A service is a long-running container that Dyna owns on a host: a row in `services` plus one Podman quadlet user unit. It is not a box (no agent, no session, no `/box` volume, no shared folder) and not a node (no `hosts` row of its own): it pins part of a host. The first user is horizon's `horizon-friends` relay. One declaration serves every kind of service, with no per-kind field. This section is the engine core; the agent tool and approvals are 7.9 and 3.5, and the Settings page is 5.13.

**Declaration.** Only `name` and `image` are required.

| Field | Type | Default | Meaning |
|---|---|---|---|
| `name` | string | none | 1 to 40 characters: lowercase letters, digits and `-`, starting with a letter. Unique among the room's services that are not being removed. |
| `image` | string | none | A room image name (5.2), or a registry reference pinned by digest (`ghcr.io/o/r@sha256:<64 hex>`). A reference with a tag and no digest is refused with `invalid: image must be a room image or name a digest`. |
| `command` | list of strings | the image's | Replaces the image's `CMD`. |
| `ports` | list of strings | none | `"PORT"`, `"PORT/udp"` or `"HOSTPORT:PORT/tcp"`; tcp when the protocol is left out. Each is published on every address of the host. |
| `env` | map | none | Plain values. A name must not start with `DYNA_`. |
| `secrets` | list of names | none | Each is an environment variable whose value the owner sets apart (below). |
| `data` | absolute path, without `\`, `$`, `=`, `:`, `,`, `"`, `%` or space | none | A named volume `dyna-svc-<id>` mounted there. It is the only writable place besides `/tmp`, survives restarts, updates and rollbacks, and goes with the service. |
| `cpus` | number | 1 | Hard limit and reservation, in steps of 0.25, from 0.25 to 8. |
| `memory` | size | `512MiB` | Hard limit with no swap, and reservation, from 64MiB to 16GiB. |
| `disk` | size | `1GiB` | Accounting for the data volume and logs, as a box's disk request is (5.4); not a quota. Up to 100GiB. |
| `host` | host name | admission picks | A host that exists and is in the room's rule; `service.set` refuses any other. It narrows the room's rule and never replaces it. Once placed, the service stays. |
| `restart` | `always` or `on-failure` | `always` | Passed to systemd as `Restart=`. |
| `health` | list of strings | none | A command run in the container with `podman exec`, checked only while an update is gated. Without it, a service that stayed active for 10 seconds is healthy. |

Env names and secret names are `[A-Za-z_][A-Za-z0-9_]*`; a name is in `env` or in `secrets`, not both. A value or an argument holds no control character. A host port below 1024 is allowed only when the host's `net.ipv4.ip_unprivileged_port_start` is at most that port (`port_privileged` otherwise). The wire form is one JSON object, decoded once at the API; every field is validated there, and the engine works on the typed result.

**Row.** `services` holds the declaration (`spec`, a typed JSON body with the defaults filled in), `generation` (plus one on each `set` and `update`), `host` (set at placement, never changed), the reservation (`cpu_milli`, `mem_bytes`, `disk_bytes`), `deployed_spec` (the declaration last deployed successfully), `image_bytes` (measured after a pull or build) and `image_estimate` (held before one succeeds; disk counts the larger of it and `image_bytes`), `want` (`run`, `stop`, `remove`), `state`, `reason` and `cause` (typed, below), `detail` (the tail of a failed build or pull), `deployed_generation`, `image_ref` (what runs: a local tag with the content id, or a digest), `previous_ref` (kept for rollback), `unit_sha` (the hash of the quadlet file as last written), `last_state`, `restarts` and `since`. `service_secrets` holds each secret's value, write-only. A unique index keeps a name once per room among rows not being removed. Every state change commits with compare-and-set and emits `service.changed`.

**States.** `pending` (not placed, or held; the reason says why), `deploying` (the reason names the phase: `image`, `unit`, `start`, `health`), `running`, `crashing`, `stopped`, `failed` (a deploy that could not finish, with no version running), `unreachable` (the host is; `last_state` keeps the state it had) and `removing`.

**Reasons.** Each is set by the step that failed, never read from message text.

| Reason | Set when | State and what happens next |
|---|---|---|
| `cpu`, `memory`, `disk` | admission fails on every allowed host, or on the named one; `disk` is also checked again from the current host figure before each pull or build | `pending`, retried on each pass, with no image work while disk is full |
| `room-limit` | the request plus the room's active box quarters and whole service reservations exceeds its CPU or memory budget | `pending` before placement; a placed `set` refuses with `conflict` |
| `room-host` | the named host is not in the room's rule, is exec only or is the engine's host | `pending` |
| `service_host` | the service host check fails: no linger, no quadlet generator, no pasta | `pending`, retried each minute; the failed check is the cause |
| `port_taken` | another service on the host declares that host port and protocol | `set` refuses, naming the other; `pending` when only the host admission picked clashes |
| `port_in_use` | `ss` shows the port held by a process that is not a Dyna service, checked at the `unit` step | `failed`; the previous version keeps running if it held the port |
| `port_privileged` | host port below the host's `ip_unprivileged_port_start` | `set` refuses |
| `secret_missing` | a declared secret has no value | `pending` until it is set |
| `image_build` | the room image build exits non-zero | `failed`, or `running` with `rolled_back` on an update |
| `image_pull` | `podman pull <digest>` exits non-zero | as `image_build` |
| `unit_failed` | writing a Podman secret or the quadlet file failed at the `unit` step | `failed`, or rolled back |
| `start_failed` | the unit does not reach active in time | `failed`, or rolled back |
| `health_failed` | the health gate times out | rolled back |
| `crash_loop` | systemd gave up at the start limit (5 in 10 minutes) | `crashing`; one `service.failed` event per episode; `restart` clears it |
| `rolled_back` | an update failed and the previous image runs again; `cause` is the reason of the step that failed: `image_build`, `image_pull`, `port_in_use`, `port_privileged`, `unit_failed`, `start_failed` or `health_failed` | `running` |
| `host_unreachable`, `host_removed` | 5.10 | `unreachable`, `failed` |

**Admission.** Box and service placement, a placed service's `set`, and a CI runner claim serialize their capacity read through the reservation write; each reads the same complete box and runner reservations and current measured host memory, and a runner rechecks after image preparation rather than trusting its earlier survey. A service is never placed on the engine's own host, an exec-only host or a pool node, and a host whose engine-host flag is unknown (the engine clears it at each start until the host check refills it) counts as the engine's. Services placed in one pass count against each other, ports included. `service.set` on a placed service is judged by the same admission, with the service's own reservation set aside, and refuses with `conflict` when the change does not fit. Services are counted at 1x and come off the top, before boxes and runners (5.5). With `C` the host's CPUs and `M` its schedulable memory, and `S` the sums of the services on it, the box and runner sums are held to `4·(C−S_cpu)`, `4·(M−S_mem)` and, for runners, `2·(C−S_cpu)` and `1·(M−S_mem)`; free disk after box requests and the services' `disk` plus the larger of `image_bytes` and `image_estimate` stays above the floor. A new service fits a host when: its CPU and memory plus the services already there stay within `C/4` and `M/4`; the box and runner load already counted still fits after the cut; the disk rule holds with its disk and an image estimate (the newest measured size of that image on any host, or 1 GiB); `service_image_sizes` records exact measurements by source after a pull or build, with room images scoped to their room and registry digests shared across rooms, so a desired-image change cannot relabel an older image's size; the measured-memory rule holds; and the host is ready, not exec only, not the engine's host and allowed by the room's rule, with no `agents` or `ci` switch needed. When the load already counted does not fit, the service waits `pending` with `cpu` or `memory`, and the CI runner skip rule (5.1) applies to it as it does to a pending box. Boxes are never stopped to make room. A stopped service keeps its reservation. Each new non-target generation, including an update or a secret change, refreshes the newest source image estimate and reserves it under admission before image work begins; a prior successful deploy's cleared estimate is not reused. Services also count against the room's limits at 1x, alongside the room's active boxes at a quarter, across all its hosts. A request excludes its own prior hold. Declaration, intent and secret changes wait for any in-flight host work before taking admission and writing their change, rechecking placement if it changed while waiting; it never frees a generation's resources while that generation can still start. The reservation covers the larger of desired and live CPU, memory and disk, and the union of their host ports, until a successful deploy replaces the live declaration. A failed shrink or port change therefore leaves what the rolled-back unit uses reserved without replacing the owner's desired declaration. `box.AdmitService` decides a service; `box.Admit` reads the same reservations from the host snapshot, so every placement counts them.

**Kernel side.** Every service sits in `dyna-svc.slice` under `dyna.slice`, written to `~/.config/systemd/user/dyna-svc.slice` with `CPUWeight=1000`, so a service gets its reserved CPU whatever runs beside it. The container has hard `--cpus`, `--memory` with `--memory-swap` equal to it, and `--pids-limit` of 512 per CPU, at least 256. Memory protection and CPU pinning are not promised.

**On the host.** Per service, one quadlet file `~/.config/containers/systemd/dyna-svc-<id>.container`, written over the host's SSH master, then `systemctl --user daemon-reload`; the generator makes `dyna-svc-<id>.service`. The file holds no secret value. `Restart=always` (or `on-failure`) with `StartLimitBurst=5` per 600 s, `WantedBy=default.target`, `Slice=dyna-svc.slice`. A room image runs as the local tag of its content id with `Pull=never`; a registry image runs by digest with `Pull=missing`.

**Isolation.** Every promise is a line of the quadlet or a placement rule, and a test holds each:

| Promise | How |
|---|---|
| No agent, no shared folder, repository, caches, engine socket or token | No `Volume=` or `Mount=` except `dyna-svc-<id>` at `data`; `--image-volume=ignore` discards Dockerfile `VOLUME` metadata instead of creating anonymous writable mounts; the environment is `env` and the declared secrets only. |
| Own network namespace, no host loopback | `Network=pasta:--no-map-gw`. |
| Not the host user | `UserNS=nomap`. |
| No privileges | `DropCapability=all`, `NoNewPrivileges=true`, `ReadOnly=true`, `ReadOnlyTmpfs=false`, `/tmp` a 64 MiB tmpfs. |
| Bounded | `--cpus`, `--memory`, `--pids-limit`. |
| Not on the engine's host | Admission and every start path, including a direct `restart`, refuse an engine host or one whose engine-host flag is still unknown. Removal can still reach it. |

Not promised: isolation from the network the host can reach, kernel separation beyond rootless Podman, protection of a secret from the image that reads its own environment, and memory protection.

**Exposure.** A published port is an ordinary listening socket of the Dyna user, so the host's firewall applies and the client's source address is kept. Dyna adds no proxy or tunnel, and any TLS is the service's own. The owner opens the firewall, enables linger (`loginctl enable-linger`) and, for a host port below 1024 such as 443, sets `net.ipv4.ip_unprivileged_port_start` on the host; Dyna sets none of them, and the service host check reports them.

**Secrets.** The owner writes a value with `service.secret_set` (`dyna service secret set ROOM NAME SECRET`, the value read from stdin); nothing reads one back. A value lives in `service_secrets`, never in `spec`, an event, an operation card, a log or the engine's environment. At the `unit` step it reaches the host as `podman secret create --replace dyna-svc-<id>-<NAME> -` with the value on stdin, never in argv or a file, and the container gets `Secret=dyna-svc-<id>-<NAME>,type=env,target=<NAME>`. `service list` and `show` give each secret as set or missing. Masking of values in log reads is part of 7.9.

**Reconcile.** One step beside the box reconciler, with at most one step per service and per-host serialization through the host driver. A `service.set` that runs inserts the row (`want=run`, `pending`, generation 1), and admission places it. A placed service with `deployed_generation < generation` deploys: `image` (build the room image on the host through the room image path, or `podman pull <digest>`, then record `image_bytes`), `unit` (check ports, write the Podman secrets, write the quadlet, `daemon-reload`), `start` (`systemctl --user restart`), `health`. On success `deployed_generation = generation`, `previous_ref` is the old `image_ref` and the state is `running`.

- **Heartbeat.** The host's heartbeat gains one line per service on it: `systemctl --user show dyna-svc-<id>.service -p ActiveState,SubState,NRestarts,Result`. It maps to `running`, `crashing` or `stopped`; a rising `NRestarts` updates `restarts`.
- **Engine restart.** Nothing on the host changes. When the host's forwards return, the step lists the quadlet files and compares each hash with `unit_sha`. A match is left alone, with no restart; a missing or different file is written again and the unit restarted; a file with no row is stopped and deleted.
- **Update and rollback.** `update` redeploys the declared source (the room image at its current save, or another digest of the same registry repository). It stops and starts, with a few seconds of downtime. The new image is built or pulled while the old runs. The health gate waits up to two minutes. On failure the quadlet is written back from the declaration that last deployed, with `previous_ref`, so the file and its hash match the running unit and an engine restart restarts nothing. The unit is restarted: the state is `running`, the reason `rolled_back` and the cause the failure. On success the old ref stays as `previous_ref`, and `rollback` makes it current through the same steps. Any session of the room may run `update`, `restart` and `rollback`; `set`, `remove` and `secret_set` are the owner's in this part (7.9 gives sessions a request).
- **Host unreachable.** The state becomes `unreachable`, with the last state kept. There is no move: a service stays on its host. The next heartbeat gives the real state when the host returns. `dyna host remove NAME` refuses while a service is on the host; with `--discard-boxes` each becomes `failed` with `host_removed`. Admission closes before cleanup waits for all in-flight service writes and starts on the host; cleanup is last, so an old deploy cannot recreate the unit afterward. A queued step rereads the current intent and generation and rechecks both the host and its placement after entering that work gate; an old stopped/want-run snapshot cannot restart a service the owner has since stopped or begun removing.
- **Stop, start, remove.** `stop` and `start` change `want`, and the reservation stays. If the heartbeat sees a stopped-intent unit running again, as after a host reboot, the step stops it regardless of the row's old stopped state. A successful direct `restart` also sets `want=run`; a stopped service becomes `running`, rather than running while reported stopped. `remove` stops the unit and deletes the quadlet, the secrets, the data volume and the row; on an unreachable host it becomes a `service_leftovers` row that the reconciler removes on its first pass after the host is ready again, not only at an engine start. Repeating host cleanup tolerates an already missing unit, container, secret or data volume and affects no other service. Genuine cleanup failures, including secret enumeration and container removal, propagate; the removing row and its secret values, or an existing leftover debt, remain until cleanup succeeds on retry. Once removal begins, further owner intents refuse with `conflict`, including a request that resolved the ID before removal; they never revive a removing row.
- **Failure notice.** A `crash_loop`, a `rolled_back` or a `failed` emits one `service.failed` event with the typed reason, once for each time the state is entered. The waking notice to the room's root is 7.9.

**Image pruning.** The pass of 5.2 keeps each service's `image_ref` and `previous_ref` on its host.

**Logs.** `service.logs` needs the admin scope until the agent tool masks secret values in the lines (5.18, later change). It reads the user journal of the unit, `journalctl --user -u dyna-svc-<id> -o short-iso -n N`, N from 1 to 2000 and 200 by default, with an optional `--since`. Retention is journald's.

**Interfaces.** The methods `service.set`, `service.list`, `service.show`, `service.logs`, `service.restart`, `service.stop`, `service.start`, `service.update`, `service.rollback`, `service.remove` and `service.secret_set` are the owner's, with `dyna service` as the CLI: `list`, `show`, `logs`, `restart`, `stop`, `start`, `update`, `rollback`, `set --file F` or flags, `remove` and `secret set`.

## 6. Host exec

Host exec runs one command outside boxes on a capacity host or the control plane. It always needs a grant.

### 6.1 Grants

A grant names hosts and reason, and permits any command until the session closes (owner, 2026-10-31, msg_64eccb5e3dff2300). There are no command rules or per-run approvals. An agent runs a command with `bash` and its `host` option. A missing grant returns `no_grant`. `hostexec.run` is class `auto`; every run is recorded and emits `op.ran`.

### 6.2 Default grant, owner grants and session close

Each room root gets a default grant for all hosts, including the control plane. Only the owner grants host exec, and the room's root too when the owner has turned on the `hostexec` root-approves setting for the room (off by default; no other security change). A request names hosts and reason and never expires: it waits until it is decided, or until the requesting or target session closes, which withdraws it. Grants have no expiry or revoke control. Closing the session ends its grants, prevents pending runs, and stops running units with retries and forced termination. A new non-root session needs a new grant. Root gets its default grant as before. The web lists active grants (owner, 2026-10-31, msg_64eccb5e3dff2300).

The planned `show_pty` tool (`dyna show-pty`) requests a live terminal for the owner to see. Owner questions remain separate.

### 6.3 Run path

The box socket identifies the caller. The engine rechecks the grant before execution. A run on a capacity host takes an SSH connection of its own, with the host's key options but not its master, so runs have no limit and never take the sessions sshd's `MaxSessions` gives the master for heartbeats, box operations and stops. At most four connections to a host are opening at once, each for its first 5 s, because sshd's `MaxStartups` refuses unauthenticated connections past 10 and some hosts ban an address that opens many. Stops reach a run by its scope, whatever became of its connection. A host that does not answer fails the run as `host_lost`. A run's output is its stdout and stderr in one stream, which also holds what fails before the command starts, such as a `cwd` the host lacks or a `$DYNA_OUT` that cannot be made. Each run is `bash -c` on one command string, in a named systemd user scope over SSH, or locally on the control plane, with empty stdin and the host user's login environment. The scope is started by a detached runner (`setsid`), not by the SSH call: the runner writes the run's output, exit status and own pid to `log`, `exit` and `pid` in `dyna-out-<run>.run`, a folder beside `$DYNA_OUT` made with mode 0700 (a path already there, a planted link included, fails the run before anything is written) whose files are mode 0600 whatever the user's umask, and the SSH call only follows the log with `tail` until the runner ends, then prints the status. A call that goes away therefore ends neither the command nor its output or status, and a later call that follows the same files gets the whole output again and the status. A run on any host, exec-only or full, first imports the user's graphical session environment from `systemctl --user show-environment`: `WAYLAND_DISPLAY`, `HYPRLAND_INSTANCE_SIGNATURE`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR` and `DISPLAY`, whichever it lists, so GUI commands such as `hypruse`, `grim` and `wtype` work over SSH. A host with no graphical session lists none of them and the run goes on without. The rule needs no setting and does not depend on how the host was added; it costs one `systemctl` call per run, and a value left from an ended session is possible. The variables reach only the run's own command: the engine starts boxes and runners itself, not through host exec, so nothing here enters a container. Every run gets `DYNA_OUT`, an empty folder in the host's temp directory (mode 0700). When the command ends the engine reads back the regular files left there with a second short run on the host, as one tar of at most 8 MiB, and removes the folder; a larger set is not copied and the output says so. The engine stores the tar as a room file and names it in the result as `outFiles`. In a box the job server unpacks it into `/box/hostexec/<run>/`, skipping anything that is not a regular file inside that folder, and adds the box paths to the run's output. A run whose call went away still has its files in the room's files, but nothing unpacks them. The default timeout is 10 minutes and maximum two hours. Output has no live stream: 64 KiB is inline, the rest is a file, and the cap is 8 MiB.

In a box the run is a job of the box's job server, whose call to `hostexec.run` stays open until the engine answers. So it behaves like a local job: up to 30 s in the foreground, then in the background with a job ID, a wake when it ends, status at the running marks, masking, and a row in the Jobs panel with its host. Its output arrives at its end. `job stop`, and the box closing, stop a host run by name: the run's call carries a client ID, and `hostexec.stop` with that ID has the engine stop the run's scope on the host and store it as `stopped`, which the sweep retries until the run ends. The job reads `stopped`, and a run the engine has not ended within the 5 s grace period stops being waited for. A call that only goes away stops nothing, because the box's connection to the engine runs over the host's SSH master and can drop under load. The job server then asks again with the same client ID until the engine answers with the run's result (the engine's answer to a repeated client ID waits for the run, whether it is running under this process or one resumed after a restart), so a dropped connection, an engine that answers `unavailable` while it shuts down and an engine that is away for a deploy all end with the run's own output and exit code, whenever it arrives, and only a stop or the box closing ends the wait. A result that arrives while no call is waiting wakes the session on `op.ran` as before, so a result can arrive both ways. A refusal such as `no_grant` leaves no job. From a box shell, `dyna bash --host HOST COMMAND` makes the same call and waits for the result; an interrupt stops the run by name and still waits, and a second one ends the command at once. Lost units stop after reconnect.

**Engine restart (deploy).** A host run lives on its host, not in the engine: the store holds it as a running operation with its host and scope name, and the host holds its runner, files and scope. When the engine shuts down, a running host run is left as it is: the operation stays `running` and the run is neither stopped nor marked lost. At startup, before anything else runs, each `running` `hostexec.run` operation is resumed instead of failed as interrupted: the engine follows the same files on the host with a new SSH call (once the command has ended, that is the output and status at once), waits out what remains of the run's own timeout, and then finishes the operation as an ordinary run, including reading back `$DYNA_OUT`; the output starts again from the beginning, so nothing is lost or doubled. A box that asks again with its client ID gets that result. This is the smaller design: the alternative, a registry of live runs in the engine with a stream per run, would store what the host already stores (a named scope and files), and would need the engine's own output buffer to survive the restart. A resume that cannot follow ends the operation `failed` with cause `engine_restarted` (not `host_lost`, and not a bare `context canceled`) and the error `the engine restarted during this host run (deploy); the command may still be running on <host> as <unit>`: when its host did not answer again before the run's time was up, or when the host no longer holds the run's files (the follow then exits 253 and prints `[no run files for <run>]`; a command's own exit 253 does not read the same, because only that line with that status counts, and a command can print it only into its own output). A run whose files were already read back and removed before the finish was stored is such a case. A follow is bounded by what is left of the run's time counted from its start plus 15 s, which also ends a `tail --pid` that waits on a pid the host has since reused. A grant that ended while the engine was away is checked once the run is resumed: the operation ends `stale`, the command is stopped like a session's stop, and the run's folder stays on the host, readable by its user alone. A crash that kills the engine with no shutdown takes the same path at the next start. Without a restart, a run whose own SSH call fails still ends `host_lost`, with its scope stopped by the sweep.

A run guards Dyna's own containers against accidents (owner, 2026-11-03, after a bulk `podman ps -aq | xargs podman rm -f` removed every box on a host). Each run puts a `podman` shim first on its `PATH`, and a `docker` one when the host has docker; the engine's own Podman calls never go through it. The shim resolves the targets of `rm`, `stop`, `kill` and `restart` (also as `container`, `pod` or `volume` subcommands, with `-a`, `--latest` and `--filter`) with `inspect`. If any carries a `dyna.` label (a box, a CI runner or a stack), it refuses with a non-zero exit and lists the Dyna containers it would have hit with their `dyna.` labels (box or runner and repository), and says that forcing is `DYNA_FORCE=1 podman rm -f <name>` on the named containers, never on a bulk or prune command. `prune`, `system reset` and `system migrate` are always refused, forced or not, and so is any command whose targets came from a bulk list (`-a`, `--all`, `--latest` or `--filter`). `DYNA_FORCE=1` applies only to containers named in the arguments. A pipe such as `podman ps -aq | xargs podman rm -f` passes names explicitly, so once forced it cannot be told from a typed list; this is accepted, because without `DYNA_FORCE=1` the label refusal catches it first, and forcing takes a deliberate rerun. Every other command and unlabeled target runs the real Podman unchanged. Bulk flags count with or without a value (`--all=true`), and a listing that fails refuses the command rather than running it. `image prune`, `network rm` and other commands that do not remove or stop containers pass through, by design. It guards against accidents, not attacks: an absolute `/usr/bin/podman` bypasses it, by design. The shim and its folder live beside `$DYNA_OUT` and go when the run's files are read back.

### 6.4 Control-plane safety and accepted risks

Host exec on the control plane runs as the owner and can use the owner socket. A control-plane grant gives full owner power (owner, 2026-10-31, msg_462f3f1d210856c2). A grant gives full host access. Root's default grant therefore reaches control-plane sign-ins and owner files. A capacity-host command can change boxes and caches, connect to forwarded sockets and act as those sessions; a host that also runs the engine may hold model and GitHub credentials. Output can contain secrets and is visible only to the room's sessions and the owner. The owner accepts these risks.

## 7. Identity, rooms and the tree

### Standing instructions

v2 has no rules feature. PiG loads global `/box/pi/AGENTS.md`, room `/box/work/AGENTS.md`, and each repository's own file. The engine stores the first two as owner configuration at `<data>/AGENTS.md` and `<data>/rooms/<room-id>/AGENTS.md` (4.3). It atomically replaces files; boxes mount their folders read-only at `/run/dyna/instructions/{global,room}` and symlink to them. The room file is outside every checkout.

PiG starts in the default repository's checkout, or in `/box/work` when the session has no repository.

For remote hosts, the engine copies both files over its SSH master to the host paths in 4.3, skipping a room being deleted, reconciles hashes before box start or resume and after reconnection, and tests new and offline hosts. It also hashes the global file and every open room's every few seconds and publishes the same way when one changed, so an edit made on disk reaches every host as an API save does. The owner edits them in the web markdown editor; `instructions.set` is owner-only, uses the read hash and returns a typed conflict for stale saves. A room's root edits the files in place on the engine host with `bash` (owner decision 2026-11-02); other agents ask their root or the owner for changes. A saved edit reaches every session before its next model request by itself, even mid-turn between two tool calls, so no session needs a message about it. PiG sends changes as context diffs and folds them into the head at compaction; there is no delivery or event. The v1 import writes rule texts as plain Markdown bullets under a short heading, without numbers or authors.

### 7.1 Principals

The engine derives identity from the connection (3.7), never from the caller. The owner uses the mode 0600 `$XDG_RUNTIME_DIR/dyna/owner.sock`, checked by `SO_PEERCRED` and unavailable to boxes, but available to control-plane host-exec processes, or a paired device token with scopes. Each session, root included, uses its box socket; restart invalidates the old socket. The internal-only engine principal sends notices and results, never acts as root.

### 7.2 Root is a position, not a role

Root is the parentless session. An ancestor controls every session under it at any depth, not only its children: it can stop, close, restart, refresh, set the profile of and move such a session, and a move's new parent is the ancestor itself or another session under it. Room grants `ask-owner` and `hostexec` give extra powers. A default subscription wakes root for engine notices and the default branch moving. Root holds no goals. It has a room-creation prompt template. v1's dual address, root seat, service flag, `NeedsRoot` routing and engine-as-root have no v2 equivalent.

### 7.3 External members (dropped for now)

There is no external member principal, token, inbox or grant. A future need requires a separate design (D-583).

### 7.4 One tree per room (D-584)

Each room has exactly one root; every other session has a parent in that room. The owner starts sessions under root or a chosen parent. A session's `session start` creates the child under itself, or under the `parent` it names, an ID or a name in its room, if that is itself or a session under it; any other parent is refused with `parent must be you or a session under you`. Session stop, close, restart, refresh, set profile, move and responsibilities accept IDs or names in the caller's room; the owner names IDs. An ID-shaped argument is always an ID, and a new session's name cannot be shaped like one. Close ends the subtree deepest first, saves a diff and deletes boxes, and transfers tracked PRs and tracked issues to the closing session's parent. Open goals transfer too, except to root: they remain unheld, and `session.closed` lists them and wakes root to assign them. Pending and unacknowledged deliveries are dropped, and the nearest session up that can receive gets one notice with their count, such as `host-lead closed; 14 undelivered messages to it were dropped.`; the posts stay in the room. Posts to a closing session fail with `session_closing`. A session cannot receive while it is closing or closed, or while its box is failed, lost, or pending for a reason that lasts until someone acts (no host its room allows, its room's limit, a size no host has, or a failing pool). A box waiting for CPU, memory, disk or a pool's next node starts by itself, so the parent reads its messages then. What a child sends such a parent goes to the nearest session up that can receive, ending at root (7.5). `session.close` answers with what it hands over and what ends, and `session.closed` names what moved in one notice that wakes the parent, unless the parent is closing too, whose own notice names all of it.

Root cannot close. After box failure the owner may replace its box with the same session ID, box ID, grants and history; unpushed work, the old volume and unacknowledged transcript bytes are lost, but feed and acknowledged transcript remain. The owner or an ancestor of both places may use `session.move{Session, NewParent}`; cycles and cross-room moves fail. A move updates the parent and emits `session.moved`, without touching the box.

#### Responsibilities

One list answers "what does this session still hold?". `Responsibilities(session)` in `engine/store/responsibilities.go` is its only definition, and box stop, the 7-day close, disk eviction, check-ins, close, the agent's context, `session.responsibilities` and the web read it instead of keeping rules of their own. Each item has a kind, an ID or name, and a group. A batched form reads any number of sessions in one query, because the reconciler asks for every ready box on each pass. Terminals live in memory, so the reconciler gives the store a way to see them.

| Kind | Group | Holds off the 7-day close | Holds off disk eviction | On close |
|---|---|---|---|---|
| open turn | needs box | yes | yes | stops |
| shell job | needs box | yes | yes | stops |
| open terminal | needs box | yes | yes | stops |
| workflow run, a crew's own, while its turn is open | needs box | yes | yes | stops |
| goal held | owes work | yes | no | goes to the parent; under root it is unheld, listed in `unheld` of the close result and under root in `goal list` |
| open tracked PR | owes work | yes | no | goes to the parent |
| open tracked issue | owes work | no | no | goes to the parent |
| open question | owes work | yes | yes | withdrawn |
| open child | needs box | yes | yes | closes first, with its own list |

Anything in the needs-box group keeps the box running; nothing in the other group does, since that work waits for a wake and survives the box. A child is in the needs-box group because its reports reach the parent at once. A stop for an update is a restart, so a child does not hold it, and the parent's box starts again straight away. A background shell job still running reports at 15, 30 and 60 minutes of running time, then every 60, with how long it has run, how long since its last output and its last lines, masked. The status goes to the session that owns the job. It wakes the session only if no turn is open; otherwise the next turn reads it. A newer status replaces an unread one. A job that ends or is stopped sends no more, and the end of a job takes back its unread status. A job stopped with `job stop` is reported to the engine as a silent end: it leaves the session's list, the box-update notice and `dyna_holds` at once, and sends no event or wake. A timeout or an exit wakes the session. Pending input and operations are not held: they are on their way, and quiet stop and the 7-day close check them themselves. A turn's output names the shell jobs still running, and the list takes those from the last `turn.ended`, less any that have ended since. A box agent's jobs die with it, so `box.hello` clears them. `session.responsibilities` gives the list and what a close would do with it now, and the web's About panel shows both.

#### Goals, check-ins and failure notices (done)

`goal journal` with text adds the line and returns the newest 5 journal lines, newest first, with `older`, the number of lines before them; `older` is left out when there are none. A read without text returns the same. `goal list` takes `session` as an ID or as a name in the caller's room; a name no open session has is `not found`, not an empty list.

A goal has text, a done condition, a holder, checklist items, a journal and a state: `active`, `done` or `dropped`. Its ID is `g<n>`, numbered per room. A session started with a goal holds a real goal record from its first moment; `sessions.goal` keeps the text it started with. The holder, anyone above it and the owner may work on a goal; root or the owner may pick up a goal with no holder. A goal can go only to the caller or a session below it, and never to root. Root holds no goals, so a goal whose holder closes under root keeps no holder. The close result and root's notice name it as unheld, `goal list` with root's session shows the unheld goals, and root or the owner ends it with `goal done`, which, since nobody holds the goal to settle its items, drops the items still open. `goal done` needs every item settled; `goal done` with `drop` does not. A holder that someone else handed a goal wakes on it as on a brief. Any change to a goal, a journal line included, counts as progress.

A turn is silent when it completes or fails for good with an open goal, no final text, no post of its own, and an input that asked for a reply; a turn that only read notices owes none, so it is not silent. A silent turn counts as a stall at once; any other goal holder counts after 10 minutes without a turn or progress. A stall is a goal holder that is idle, stopped or blocked, with nothing moving below it: a running turn or a box start excuses it for 2 hours, counted from the turn's latest tool call (the box agent reports one at most each second and the engine records it at most once a minute) or from its start when it has made none, so a turn that keeps working is not stalled; goal changes and pushes are not read, only tool calls, and a pending input, a scheduled model retry, a shell job on its list or a `blocked` question waiting for the owner's answer excuses it always, since a job's end wakes its session. Blocked means a failed or lost box, a failed last turn, an undecided operation, or one of those 2-hour limits passed.

Check-ins are engine notices, in every unpaused room. Every minute the engine writes one report per session at most, stalest first, on one transaction with the clocks in `checkins`, so a restart repeats nothing. A stall goes once to the parent, then one ancestor higher per hour, until root has it; only time drives this, so a parent stuck in one turn holds nothing back. Each session gets at most one check-in per 30 minutes and none while its last report is unread. A reader that left a report unread for an hour, a closing session and a failed or lost box are skipped. A report wakes an idle or stopped reader and steers a running one. New progress on the goal starts the stall over; otherwise the same stall is never reported to the same ancestor twice, and it stops at root. Timing constants are in `room/checkin.go`.

Failure notices do not wait. Every 10 seconds the engine compares each open session of every unpaused room with what its ancestors were told. A failed or lost box, or a failed last turn, sends one `session.failed` notice to the parent, or to the nearest ancestor that can read it, with root as the last resort. For a failed last turn it says that the session's input is kept and that its next input starts a new turn. A run of failed retries is one failure, a failed turn whose reply already reached the parent is not repeated, and a recovery clears the record. A box counts as recovered only after 10 minutes up, so a box that keeps coming back and going again, as on a host that keeps dropping out, is one failure. The notice counts as telling that ancestor for check-ins, so a stuck goal holder keeps climbing from there.

A failed or lost box keeps its open turn, because a box that returns or restarts resumes it. Nothing runs that turn, so `session.list` leaves it out and the web shows no running turn.

`session.list` takes `parent` (the direct children of one session), `limit` and `after`. A session that names no limit gets 25 sessions per call, in creation order, because its harness cuts a tool result at about 10 KB and a longer list lost sessions from the end without saying so; the owner and the web get the whole list. A cut list sets `next` to the last session shown, and `after` with that ID returns the rest.

### 7.5 Reply channels (D-579)

The engine derives surface and reply channel from the input, including for root. Each input starts with `[Dyna] From <sender>, <surface>. <for> <attachments> <reply sentence>`, where `<for>` names a parent that could not receive the input (below), then the sender's text. Only that first line is an engine frame. Each attachment in the frame is its path in the box, `/box/attachments/<post seq>/<name>`, with its type and size. The name is reduced to one safe path segment, and repeats in a post are numbered. Before PiG reads an input, the box agent fetches its files by hash over the box socket. It does this off the channel, so a stop still reaches it and a big file on a slow host delays only that input. If a turn ends before a steer's files arrive, `turn.output` names the steer in `unread` and the next turn takes it. A session reads its room's files and any post delivered to it. PNG, JPEG, GIF and WebP files up to 16 MiB are also shown to the model. Pi's session file keeps only the frame: the box's extension (`box/dynaext` on PiG) adds the image to each model request from the file, shrunk to the model's limit, newest first up to 20 images and 20 MiB, and names any it leaves out. So images add nothing to the transcript, stay visible across a restart, and cannot push a request past the 32 MiB model route. `box.hello` supplies stable identity, the fact that only the engine writes this frame, how `context_update` works, and how to reply; it contains no commands or state.

The owner can say which host a paired device is on (`dyna device set ID --host HOST`, or Host on the device in Settings; empty clears it, default none). The sender of the owner's inputs from that device then reads `the owner, on <host>`. The host must be registered or the control plane.

| Input | Surface | Channel and target |
|---|---|---|
| Owner feed post, mentioned or unmentioned to root | feed | final to owner in feed, replying to post |
| Owner session DM | dm | final to owner in that DM; parent does not wake |
| Session start brief | session | final to parent |
| Parent mention | feed | final to parent in feed |
| Card submit | card | final to owner in feed, replying to card |
| Child result | session | post to child if action is needed |
| Child mention | feed | post to child if action is needed |
| Mention from a sibling or another session under the parent | feed | post to sender if action is needed |
| Owner answer to a question | dm | final to owner in that DM; parent does not wake |
| Group-only mention | feed | none |
| Check-in, failure notice, engine notice, service event, shell or job end | engine or service | none |
| Voice dispatch, after port | voice | final to owner in call, or feed if call ended |

A final response is delivered to its target and home; if the turn already posted to that target, delivery is quiet and links that post. A child's final response to its parent follows the chain of command below. A `post` channel sends nothing automatically. A `none` response stays in the transcript; the frame asks for one line. Multiple inputs require one reply per distinct final target and home.

**Chain of command.** A session messages its parent and any session under its parent: its siblings, its own children and theirs, and so on down. Root, with no parent, messages any session under it. The owner sits above everyone. A session's `post` may mention `parent`, `children`, `siblings`, and by name or ID its parent or any session under it. Within the room the engine refuses any other mention, `room:…`, `root` unless root is the parent, a grandparent or a session in another branch, with one line, such as `you can message your parent (hooks-lead) and sessions under it; your parent passes anything else on.`, and queues nothing. A crew mentions only its parent: `a workflow can message only its parent (root).` One store function, `receiver` in `engine/store/receive.go`, decides who receives for a session now, and both this check and the routing below use it. What a session sends its parent while the parent cannot receive (7.4) goes to the parent's nearest ancestor that can, ending at root, and that delivery's frame says so, as in `For host-lead, which can't receive (box failed).`; the session never names root itself. A child's final reply to its parent goes the same way. A session's subscription may wake itself and whom it may address; the owner's may wake any session.

**Cross-room root posts.** A room's root may post non-empty plain text to another room's feed with `room` set to that room's ID and exactly `mentions: ["root"]`. The target root wakes with a `post` reply channel, never an automatic final reply. A `post.sent` event in the sender's feed records the text and target room and root names without a delivery or wake. The stored post carries the source room ID and immutable room and session names; the input identifies the sender as `room:session` even after the source room is deleted. Cross-room attachments, HTML and visuals are refused with a typed error; home may only be the target feed, and replyTo, visual update and visual reply are refused. A cross-room post cannot use `endTurn`. Non-root sessions are told to report to their own root with `post @root`. All other session cross-room posts are forbidden. The owner retains its existing cross-room capability. The store rechecks both roots and the target room in the post transaction.

A session's post with no home that mentions no session goes to the owner's conversation with it: the home of the final reply its open turn owes the owner, else where the owner last wrote to it (the newest delivery from the owner), else the feed; a post that mentions sessions goes to the feed, and a session may name only its own DM as home. A frame with a `post` or `none` channel says where those posts go.

To answer, a session ends the turn with text; that text is the reply. A post with `endTurn` replaces that text when the reply needs attachments or mentions, or goes elsewhere. A plain post is a mid-turn update. `box.hello` states this rule.

**The startup prompt.** `box.hello` returns the session's whole system prompt, which the box passes to PiG as its system prompt (`SystemPrompt`, with an empty, non-nil `AppendSystemPrompt` so PiG does not look for an `APPEND_SYSTEM.md`). It replaces PiG's own preamble, `<tools>` and `<rules>`; PiG still appends the `project_context`, skills and cwd sections, and Dyna's host sections follow. The engine builds it in `sessionPrompt` (`engine/prompt.go`), whose parts are Go string constants in the order a session reads them: the intro, how work goes, working on your own, the tools habits that span tools, git and shared work, delegation (briefs and results), the role, communication, what holds across turns, compactions and restarts, and `This session`. The text states facts and how work goes, in the words of how the system behaves; no line tells the agent whom to trust, and the fact behind such advice is stated instead: the `[Dyna]` line is written only by the engine and names the true sender, and the rest of an input is the sender's own text. Each fact has one home: tool behaviour is in the tool descriptions, the owner's choices in AGENTS.md, changing state in the `dyna_*` sections, and the prompt holds identity, inputs, replies, mentions, goals, context, compaction, files, outside text, notices and the working practice. The role is decided from typed session facts when the box says hello: **root** when the session has no parent, **lead** when it has ever started a child (one store query), **worker** otherwise, so a worker that starts its first child reads the lead text at its next box start. Workflows are in `Delegation`, which root, leads and workers all read and a crew's worker does not: it says what a workflow is for and that any session may start one, and leaves who may to the `dyna_workflows` section and the tool's description (9.2), so no role claims them. The role picks the `Your role` section and the variants of `Inputs`, `Mentions` and `Goals`: root's `Mentions` reach only the sessions under it and its role says it holds no goals, so it has no `Goals` bullet. `This session` holds the identity line (name, ID, room, parent), `Your branch` and the git route only when the session has a repository, and for root the `Files` and `Standing rules` lines, whose paths come from the layout (`<data>/AGENTS.md`, `<data>/rooms/<room>/AGENTS.md`, `<data>/rooms/<room>/shared/`) and whose host is the host list's engine host, so they cannot drift from where the files are. The compaction bullet says what a compaction keeps: the context sections (the `project_context` section of the AGENTS.md files, the skills and the `dyna_*` sections, which hold the goal) and the tools come back whole, and everything else, a brief included, survives only inside the summary; PiG compacts past the profile's compaction limit, when the model changes over 100,000 tokens, and before a quiet box stops over 100,000 tokens. The text of a session that already exists changes as one `context_update` diff at its next request (7.9, P5), because its head sections changed. `box.hello` also returns `WorkerInstructions`, the shared core (intro, how work goes, working on your own, tools), which a crew's box puts before the crew paragraph under the heading `# Your role: workflow worker` (9.2), since a workflow worker is a process of the session's box and has no inputs, replies or posts of its own. A test asserts each of the four renderings whole, with and without a branch.

**Sol spacing mitigation (owner, 2026-11-05).** OpenAI models with ID `gpt-6.1` or in its `gpt-6.1-` family get two sentences asking for spaced prose without changing code or IDs, including posts, briefs and files. The wording lives once in `engine/prompt.go`. The engine passes this model-specific part separately from the invariant session prompt, using the resolved typed model choice at box hello, each turn and each workflow profile. PiG holds it in a host prompt section and replaces or removes it after a successful model transfer; a refused or aborted transfer keeps the old model's guidance. This avoids leaving the old model's instruction in the fixed startup prompt and covers workflow workers whose model differs from their crew's. No output is rewritten. A small offline session-JSONL counter reports heuristic join-site counts per 10,000 decoded characters, separately for assistant text and tool-argument string values, grouped by each assistant message's recorded model; it is not a language-quality score. Effectiveness is not measured until fresh post-deploy output is collected with explicit model, timestamp and prompt-cohort boundaries.

`endTurn` ends the turn with no further model call and makes the post the turn's reply, whatever the turn's channels and wherever the post goes. The turn has no final text, and `turn.output` names the post in `endPosts`. Every final channel of the turn links that post in `turn.ended.replies`; no event or table records `endTurn`. A session target that the post mentioned already has it. Any other session target receives the post itself as a waking delivery. A `post` or `none` channel owes nothing.

PiG stops only when every tool call in the message ends the turn and no steering is queued. So a post that fails, a post beside another tool call and a turn that takes steering all continue, and the turn ends on text as usual. A post from a codemode script sends and the turn continues, because nested results never reach the agent loop; its result carries `turnContinues: true`. Recovery treats an end batch as settled and makes no model call. `endTurn` exists only on the MCP tool; `dyna post` has no turn to end.

### 7.6 Rooms and repositories

A room lists zero or more repositories, exactly one default if nonempty. Each repository has exactly one default room and may appear in others. Owned events reach and wake their owning session in its room; after close, the nearest open ancestor owns them. The default branch moving has one event row and one delivery per listing room; only the default room's root wakes. Other repository events are for subscribers (8.5).

Merge policy (`queue` or `manual`), CI mode (`github` or `box`), and commit, PR and comment attribution belong to the repository; only owner-class `repo.settings.set` changes them. Store `room_repos`, `repos` and `repo_attribution`, plus `devices`, `device_scopes`, `pairing_codes` and `connect_sessions` (7.8).

**Deferred (owner, 2026-11-01).** M3 ships PR status first. The approval flag (`pr.approve`), merges by Dyna, merge policy, `repo.settings.set` and `repo_attribution` are not built, and decision 13's approval and merge rules wait for them. Until then people merge on GitHub, nothing in a box can merge through Dyna, and a room keeps any disclosure lines it needs on GitHub text in its instructions, as Horizon does.

### 7.7 GitHub request budget

Watch repositories through their feeds. Each pass, 60 seconds apart with no back-off, makes one conditional GET of each feed of each watched repository, sending the last ETag. A 304 costs no quota, so a quiet repository costs nothing, however many PRs it has. A feed that answers with a longer `X-Poll-Interval` is left alone that long; `git/ref` sends 300 today. Below 20% quota, reads of a repository stay at least 10 minutes apart. Target fewer than 300 REST requests and GraphQL queries combined per hour per repository with 20 open PRs, in the worst case of one change a minute. GitHub App webhooks through the relay replace polling later. The CI runner pool long-polls the Actions service, outside this budget; its REST use is one lease write every 5 minutes and one runner list an hour per repository ([CI runners](ci-runners.md)).

**Agents' reads.** Every box reads GitHub through the `github` MCP server (7.9), and those reads spend the feeds' quotas: they go out through `prs.Client.Reads`, so what GitHub says of a quota on an agent's read is the feeds' reading too. They stop while less than 40% of the REST or GraphQL quota is left, twice the line where the feeds slow, so agents never push the feeds into their slow pace and PR and issue wakes keep theirs. The refusal names the reset time. Search has limits of its own that only agents spend, so a search waits only when GitHub asks. A refusal with `Retry-After` on the REST or GraphQL quota pauses the feeds too, as the token is theirs. At most 8 agent requests are in flight across all boxes.

**Opening.** `pr.open` creates the PR on GitHub, then records its owner and the `github.pr.opened` event. `head` names the branch; without it the head is the session's recorded branch (5.7), and an error about a missing or empty head says so, with the default it used. The result carries the PR `number` and `url`, and the returned operation leaves out the `body` field, which the caller wrote; the field is absent, not empty, and the stored operation and the GitHub request carry the body. If recording fails after GitHub created the PR, the call still succeeds: its `output` names the PR and the failed recording step, and the PR is not tracked until `pr.track`.

**What is tracked.** Every PR a session opens through `pr.open`, plus any PR added with `pr.track`. A session tracks for itself, and either the PR's base or its head repository must be in its room, so a fork's PR on an upstream that no room lists counts. The owner tracks anything for a named session, or for a room's root. A `Run` tracks through its socket for a session it names in its room, or root, under that session's rules. Tracking grants no push right. One session owns a PR; `pr.untrack` is for that session, its ancestors and the owner. Close hands PRs to the parent (7.4). `issue.track` adds an issue under the same rules, except that an issue has one repository, so that one must be in the session's room; a `Run` uses `POST /v1/issue.track` on its socket. One session owns an issue, `issue.untrack` is for the same people, and close hands issues to the parent. An open issue does not hold its session open for the 7-day sweep (5.5), as an open PR does: issues can stay open for months, and close hands them on.

**What is read.** `engine/prs` watches each repository a room lists, and each with any row in `pr_owners` or `issue_owners`, closed rows too, because a feed is how a reopen arrives and an unchanged feed is free. The feeds are `issues` (`state=all`, by `updated`), `issues/comments` and `pulls/comments` (by `updated`), `issues/events`, and `git/ref/heads/<default>`. A `github_feeds` row holds each feed's ETag and cursor, which commit with the events they produced. An item is new if GitHub's ID for it has not been seen and it is no older than two minutes behind the newest time the feed has shown, so an item shown late still counts and none counts twice. After downtime a feed pages back to its cursor by the `Link` header, up to 34 pages of 30. Past that the log reports the gap, the cursor moves to the head, and the pass reads every tracked item once, so a close it missed is still told. A feed with no row starts at its head, and that first pass reads every tracked item the same way, so a deploy replays no history and loses no close.

Each new feed item is one typed record, `contract.GitHubItem`: repository, number, kind, action, actor, URL, the item's author, a small detail such as the label, and comment or body text. `assigned` and `review_requested` take their actor from `assigner` and `review_requester`, because GitHub's `actor` on them can be the one assigned. GitHub's `mentioned` names only who was mentioned, so the stream keeps those of the owner's account alone, and takes its actor from the comment that came with it, within 15 seconds, or else the item's author, for a mention in a body. A merge is one `merged` record: its `closed` is dropped by the PR's `merged_at`. `subscribed`, `referenced` and the like are not kept. The issues feed's item is also the source of a tracked item's title, draft flag, labels, assignees and milestone, and a body hash shows an edit without keeping the text; GitHub does not say who edited a body.

GraphQL reads only what no feed shows, in one query per repository per pass: check rollup, mergeability, review decision, the head and the latest reviews with their bodies. It reads a tracked open PR when a feed touched it this pass, when GitHub has not finished its checks or mergeability, for ten minutes after a new head with no checks yet, on its first read, on every tracked open PR when the default branch moves, and on every tracked open item when a feed lost its place. Nothing else costs a query, and an unchanged pass makes none. A closed item is not read. The one exception is who the token is, which is one query per engine start. `pr.track` and `issue.track` are one REST read each, with the ETag of the last, and `issue.track` reads nothing for an open issue the session already owns, so a hook can repeat it over a list. Nothing moves the feeds for a check result, so a rerun on an unchanged head whose last result was final shows on the next read of that PR, not by itself.

**CI state and the notice.** CI is read from the rollup of the commit that is the PR's head. A rollup of another commit is an earlier push's, so the new head is pending until its own checks report; a rollup that says success with no check in it is "no CI" (`none`), not a pass, and neither tells CI passed or failed. **A PR's CI settles by the rule of 8.5 for a head**, the one rollup summary a default-branch head also uses: it is `pending` (`dyna_holds`, `pr status` and the web badge say CI running) until every check run is `COMPLETED` and no status context is `PENDING` or `EXPECTED`, whatever GitHub's rollup `state` says, and only then `failure` (a check that failed, timed out, failed to start, needed action or went stale, a status `FAILURE` or `ERROR`, or every check cancelled) or `success` (a cancelled run alone is not a failure). **This changed:** a PR followed the rollup `state` before, so a cancelled check, which turns the rollup `FAILURE` while other checks run, told "CI failed" at once. A failure is now told only when the run is complete, which is later than before on a long CI: it can no longer fire on the first failed check, and a PR with a failed check and others still running shows CI running. A PR with more contexts than one read lists (the first 50) cannot be proven all terminal and has no list of recent heads to fall off, so its CI follows the rollup `state` as before, a cancelled check included; a rollup with no context keeps its rule too. A "CI passed" or "CI failed" notice is sent once per head and states `The checks ran on <head sha>.`; a PR with no checks reported gets no such notice. Failed check names come from the workflow files at the PR's head, so they are wrapped (decision 13) only for a PR from a fork by an author who is not the owner's account; on a branch of the tracked repository itself they are shown unwrapped, and the failing log is outside text wherever it is read.

**Review state.** GitHub's review decision and latest reviews give it. The owner's convention for a PR opened by the token's own account, which GitHub cannot approve, is a statement by that account that starts with 🤖 and has a line `**Verdict: Approved at <sha>**` or `**Verdict: Changes requested at <sha>**` (a prefix of 12 to 40 characters of the head sha, on the second line). The statement is either an issue comment or the body of a submitted review of any state, usually COMMENTED, which is how an agent approves without GitHub refusing it; a pending review is not one. The format is fixed and has no room setting; a sha of 7 to 11 characters does not match. One derivation reads both kinds, so `pr status`, `dyna_holds` and the "PR approved" notice agree. A statement counts by its current body at its last edit time (else its creation or submission time), and the latest verdict at the current head counts as the review, so a verdict for an older head counts for nothing and a head that moves makes it stale. A review's own commit is not compared, since GitHub pins a review to the commit open when it was started while the verdict names the sha judged. A changes-requested state from GitHub stands over a verdict's approval.

**Who is told.** A merge or close reaches its owning session once, in its `github.pr.changed`: a subscription that wakes the owner does not also deliver `github.pr.merged`, `github.pr.closed`, `github.ci.finished` or another event of the same tracked item. `pr.track` refused for a PR another session tracks names that session, by name and ID, to a caller in its room.

**What wakes.** `pr_owners` and `issue_owners` keep the last state read, the last CI result told per head, the newest review seen and what is waiting. This is a cache of GitHub for telling each change once, not a review record, and it commits with its events, so a restart neither repeats nor loses a wake. A session hears of a failed or passed CI result, requested changes, approval, a conflict, a merge, a close without merging and new reviews or comments, and of an issue's close and new comments, with outside text wrapped (decision 13). A plain conversation comment by any account whose login ends in `[bot]` never wakes, on a PR or an issue, while its reviews and inline review comments still do. On both it hears of metadata, each with who did it: labels added or removed, assignees, title, milestone, an edited body and a reopen, and on PRs draft or ready and requested reviewers. A comment or review body by the token's own account may be a session's, so it cannot wake freely, and that account also speaks for the owner, so it is not ignored. Text from that account that starts with 🤖, after any quote marks, never wakes, which covers Horizon's two disclosure lines. Other text from it wakes at most once per item in 10 minutes, as recorded in the row, so a restart does not reopen the window. Text inside the window waits in the row, and arrives on the first pass after it, or when the item closes. Comments from anyone else are not held back with it. A session that answers each such wake without the marker therefore gets at most six wakes an hour per item: the rule bounds that case and does not end it. Labels churn, so a metadata change with nothing else to tell wakes at most once per item in 10 minutes, as recorded in the row, so a restart does not reopen the window. Inside the window it waits in the row and arrives on the first pass after, or when the item closes. CI, a review, a comment or a close is not delayed: it wakes at once, carries anything waiting and spends no window. Titles, label names and milestones are wrapped when the login that set them is not the owner's account, and `pr status` and `issue status` wrap by the item's author, or by the last outside login to set them on the owner's own item.

One pass gives each session one delivered event and one engine-surface delivery, whatever moved for it: `github.pr.changed` if any of its PRs moved, with its issues inside, and otherwise `github.issue.changed`. A PR or issue that moved without news, such as CI starting, gets a change with no change kinds and no delivery, so the web stays current. A pass that moved both PRs and issues also commits an undelivered `github.issue.changed` beside the `github.pr.changed`, so every pass that moved an issue has one and a subscriber sees every issue change. A subscriber's own delivery fires only on news, and never for the session that owns the items, which already has the pass in its one delivery. A push is the one change kind that tells subscribers only: when a read finds the head of a tracked open PR other than the stored one, and the stored one is not empty, the change carries `pushed` with `push` {before, after}, the stored head and the one read, so several pushes between two reads are one move. The owner made the push, so `pushed` alone sends it no delivery and no wake, and it still wakes on the CI result of the new head. A change with other news also shows the head move to the owner. A subscription on `github.pr.changed` filters it with `where kind=pushed`: `kind` matches any change kind of the pass, as `repo` and `number` match its PR. It is a kind of `github.pr.changed`, not an event of its own, because subscribers already listen there and `where` selects it, and `github.ci.finished` is a separate event only because it states a result for people who do not hear the pass.

The stream also states itself as typed events, with no delivery, for subscribers: `github.pr.opened`, `github.pr.merged`, `github.pr.closed`, `github.issue.opened`, `github.issue.closed`, `github.comment`, `github.label` and `github.mention`, on any item of a watched repository, tracked or not, `github.ci.finished` on a tracked PR, and `git.main_ci_finished` on a watched repository's default branch. Each commits with the pass that found it, and a tracked item's name its owning session. Other actions have no event of their own and reach only an owner. These events go to the repository's default room, and only if a subscription lists that type: a busy repository shows thousands a day, and nothing else reads them. An upstream no room lists has no one to tell. A comment or a label on a closed tracked row is an event like any other and is not its owner's to hear, unless the item reopens: a reopen puts the row back and tells its owner.

`git.main_updated` has no owner: when a pass reads a new head on a listed repository, one event goes to the repository's default room, where the default subscription wakes root, and each other room that lists it gets one quiet delivery to its root (7.6). `repos.main_head` holds the last head, so a restart repeats nothing and a move during one is still told; the first head ever read is no move. **Default-branch CI.** `git.main_ci_finished` is the end of CI on a default-branch head, which `github.ci.finished` never states because no tracked PR has that head. It is `contract.GitMainCIFinished`: `repo`, `branch`, `sha`, `result` (`success` or `failure`, a `PrCI`) and `runs`, one `{name, conclusion, url}` for each check run or status in the head's rollup, as far as the first 100 of them, and `runsTruncated`, true when the rollup holds more than `runs` shows (the `result` still comes from the whole rollup). It fires for every repository `git.main_updated` watches, which is every row of `repos`, so a repository a room lists without making it the default one is included. It goes to the repository's default room only, like the other typed events above and unlike the quiet root deliveries of `git.main_updated`, and it is not in the default subscription. `where` reads `repo` and `kind`, where `kind` is the result, so `kind=success` keeps the passes. The result is a `PrCI` from the one rollup summary a tracked PR's CI also uses, with the rule of 8.5 for a head (every context terminal, a cancelled run not a failure), which a PR's CI follows too, and the event is one for the head's whole rollup, not one for each workflow.

**Recent heads.** One event is for one head sha, not for the newest head: a head's CI finishes whenever it does, and in a busy repository the default branch moves on before that, as upstream merges can come every six minutes while CI takes twelve. So `repo_heads` (`repo`, `sha`, `seq`, `seen_at`, `settled`) holds each head a pass has read, in the order they were first read (`seq`), and each is settled on its own. A head is added when a pass reads it as the new `repos.main_head`, unsettled, with `seen_at` the pass's time; a repository's first head ever read is added already settled. The list is bounded, and the rule is one: a head stays while it is among the newest 20 of its repository and was first read less than two hours ago. A write that adds a head prunes the rest, and a read never polls a head past either limit. A head pruned while still unsettled is dropped with no event, and a pruned sha is never reported, so a CI that outlasts the bound is not told. If the branch moves twice between two passes, the middle head was never read and has no event; that is acceptable here, because the event is for knowing that the branch's CI went green, and no commit list is fetched to find it.

**Reading the CI.** A pass reads the rollup of every unsettled head in the list, all in the one GraphQL query for the repository, one alias for each head (`h0: object(oid: $h0) { ...ci }`, the sha a variable and not query text). That is the only addition to this budget: at most one query per watched repository per pass, with at most 20 aliases in it, and no query at all when every head of the list is settled, for a quiet repository, and for a repository whose first head has not been read. A settled head costs nothing. A pending rollup is read again on the next pass. Only a terminal rollup state settles a head with an event: `SUCCESS` (with at least one check) is `success`, and `FAILURE` and `ERROR` are `failure`; `PENDING`, `EXPECTED` and a rollup with queued or running checks are not settled, whatever the checks that have finished say. A head whose rollup has no check in it is read again until ten minutes (`ciGrace`) after its own `seen_at`, then settles with no event; the clock is the stored `seen_at`, so an engine restart does not restart it. A repository with no CI costs at most ten queries for a head.

**Once per sha.** The pass writes each event in its one transaction, in the order the heads were first read when several settle in one pass, and settles the head in the same transaction: the update changes the row only for a head that is in the list and not settled, and the event is written only if it did, so a restart, a repeated pass, a head pruned meanwhile or a rerun on the same sha repeats nothing. No head from before the table existed is reported: step 94 seeds the list with each repository's stored `main_head`, settled, and drops `repos.ci_settled`, so enabling the list reports nothing from before it. It adds no feed and no timer.

A PR from `pr.open` starts with nothing known, so its first results are news. A tracked one and a tracked issue start from a baseline: the next pass records what they show and wakes nobody. Merged and closed PRs stop holding their session open for the 7-day sweep (5.5). `pr.track` and `issue.track` take a merged or closed row again.

### 7.8 Remote access

The web listener binds loopback behind an owner proxy. Each `--web.route <origin>` permits its own hostname and Origin; other hosts get 421, and state changes and WebSockets require that Origin. A proxy does not authenticate.

`dyna device pair` issues one 10-character code, valid for 5 minutes or 5 wrong tries; a new code replaces it. No explicit scope means all scopes on loopback, otherwise `read` and `operate`. Wrong and expired codes return 403 and 410 respectively. Pairing returns configured routes; Settings shows a QR code `<address>/#pair=<code>`, or explains that no route exists.

The `dyna_device` cookie is a random 256-bit token, HttpOnly, SameSite=Strict and Secure on HTTPS. SQLite stores only its SHA-256; its 30-day sliding expiry writes at most daily. `dyna web` also creates a device. Scopes are `read`, `operate`, `files`, `terminal`, `computers`, `admin`; every API method and operation kind registers a required typed scope. Attachment reads need `read`, uploads `operate`. Only admin manages devices; `device.scopes` needs no scope and returns the caller's scopes. The owner socket has all; sessions cannot call device methods. The web app reads scopes on connect and hides unavailable controls. Revocation applies on the next request; streams and terminals recheck every 15 seconds.

Connect keeps its wire protocol and relay paths. `engine/connect` ports link, mint, session exchange, renew, revoke and hello; relay passkeys authenticate linking. Supervised `cloudflared` is an engine child. Session token hashes live in SQLite; machine key, link, relay keys and tunnel token live in mode 0700 `<data>/connect`. Route ranking, signed hello, session handoff and event-stream route fallback follow v1 and ship in g1512. A route has one app origin. The machine sends Web Push itself with its own VAPID key; the relay never sees subscriptions. Web Push needs a separate r23 design and lead approval before implementation.

### 7.9 Agent surface: MCP tools and the context snapshot

PiG is the session's harness. The box agent serves one `dyna` MCP server at `127.0.0.1:7781/dyna/`; each call routes to `POST /v1/<method>` on the box socket. The CLI uses the same methods and principal. The engine alone authorizes and renders `context.snapshot`. PiG owns MCP, search, codemode, skills, keyed sections, compaction and context updates. The box agent configures PiG and passes state; it has no authority or credentials. Dyna's one extension, `box/dynaext`, is Go compiled into the box agent, and loads ahead of PiG's codemode, `tool_search` and MCP extensions, so a tool of its takes the place of theirs of that name. It links nested calls to their outer call, registers `mcp__dyna__post` in place of the MCP tool, because only a tool's own result carries `terminate`: MCP results and the `tool_result` hook drop it, and registers `bash` and `job` (below) on the job server's Go API. It registers `mcp__dyna__visual` the same way, deferred and sequential, because the agent runs one message's calls in parallel unless one of them is sequential, and a check reads a file that an earlier call in the message writes. It adds no authority; the post and the check call the same `dyna` server in process, which the engine authorizes. A crew worker's PiG loads the same extension, with its own working tree as `Dir`. PiG carries upstream Pi fixes #11625 and #11632 (tool search ranking) as its fork's patch P6, recorded in the fork's `PATCHES.md`.

**GitHub reads.** The engine serves GitHub's own MCP server, `github-mcp-server` (MIT, the Go module `github.com/github/github-mcp-server/v2`), at `/github/` on each box socket. `engine/githubmcp` builds it from upstream's packages as upstream's stdio server does, with `--read-only` and every toolset, adds the read tools that wait behind flags (file blame, issue dependencies, duplicate issues), and leaves out `ui_get`, a helper for MCP Apps forms. It is pinned at v2.0.2, because v2.0.3 needs Go 1.27.3. One stateless server answers every box and every crew worker. The box agent passes `127.0.0.1:7781/github/` through to the engine, and PiG lists a deferred server named `github`, so its tools load through `tool_search` or a codemode script; an owner's add-on server named `github` takes its place. A box hello says whether the engine has a token, and without one no server is listed. The token stays in the engine. Reads are enforced twice: upstream registers no write tool, and the transport sends only REST GET and HEAD and GraphQL queries that name no mutation. Writes stay with `pr open`, operations and hosts, except the scoped ones a room's `githubWrites` setting allows (next paragraph). Its tool results are wrapped by the box as decision 13 says, for a model's direct calls: `<outside source="github">`, with no author, since an author belongs to each item.

**GitHub writes.** A room's `githubWrites` setting lets its sessions make a small, named set of writes on the room's own repositories without a host grant. It is off by default and is the owner's: `room.set` with `githubWrites` (`{"repos": [...], "groups": [...]}`; an empty `groups` turns it off) or `dyna room set ROOM --github-writes issues,pulls,projects@REPO[,REPO...]` (`--github-writes off` turns it off), stored as JSON in `rooms.github_writes`, shown by `room.list` as `githubWrites` and in Settings > Approvals (5.13). `repos` holds repositories of the room (`room.repos`) or `*`, which means every repository the room lists when a request is made, so a repository added later is covered and one removed stops being. `room.set` refuses a repository the room does not list (`invalid`, naming it and the room's repositories), an unknown group (`invalid`, naming the groups) and a caller who is not the owner (`forbidden`); a group with no repository, or a repository with no group, is invalid (an empty `groups` is the only way to turn it off); repositories match without case, as GitHub names them; deleting a room removes the value with its row; the stored value holds only checked values, in the order of the groups below. A stored value that no longer decodes is that one room's problem: `room.list` still lists every room, shows the room without `githubWrites` (off) and logs the room once per engine run, while the tools of that room get no writes (the grant fails closed). **Groups and the upstream tools each registers** (names as the pinned v2.0.2 has them; a tool in two groups is registered once):

| group | tools | what a tool may do through the transport |
|---|---|---|

**Enforced twice.** (a) Registration: the engine builds one server per set of groups from upstream's packages, not read-only but with a filter that keeps every read tool and only the write tools of the groups that are on, so a room with the setting off sees exactly the read-only server, and the tools appear in the deferred tool list only when allowed. A tool's description gets one sentence saying what the room cannot do with it, and `update_pull_request`'s schema drops `state`, `draft`, `base`, `reviewers` and `maintainer_can_modify`. (b) Transport, which is the enforcement: every request to GitHub passes `githubwrites.Check` with the room's allowed set, which comes from the request's context. The API layer sets that value from the box socket's caller, whose room the engine fixed when it opened the socket, and from nothing a box sends. The check is an allow-list: a request is allowed only if it matches a route or GraphQL mutation of the table above for a group that is on and names a repository of the allowed set; anything else is refused with a `githubwrites.Refusal`, an error whose `Reason` is typed (`writes_off`, `group_off`, `route_not_allowed`, `repo_not_allowed`, `field_not_allowed`, `id_unresolved`, `content_type`, `body_unreadable`, `graphql_*`) and whose text names the `githubWrites` setting, so no caller reads the message. GET, HEAD and queries stay as reads (7.7 rule 5). **REST** requests must be to the engine's API host, with a path of exact lower-case literals and segments of letters, digits, `.`, `_` and `-` (an owner and repository compare case-insensitively with the allowed set), numbers where the table has numbers, no empty or dot segment, no trailing slash, no percent-encoding that changes the path and no query; the body is JSON of the content type `application/json`. A redirect arrives as a new request and is checked again, so a transfer or rename cannot carry a write to another repository. A route with a field list (the PR edit, the labels edit of a PR, project item fields) takes a JSON object whose keys are all in the list, compared exactly; any other key, such as `base`, `state`, `draft`, `reviewers` or `maintainer_can_modify`, is `field_not_allowed`. **GraphQL** bodies are one JSON object with `query`, optional `variables` and `operationName`, parsed with a real GraphQL parser: a body with `extensions` or no `query` (a persisted query), an array (a batch), a query that does not parse, and any subscription are refused. Every operation of the document is checked, whatever `operationName` selects: a query is a read; every root field of a mutation must be a plain field of the table (aliases are fine, fragments and directives at the root are not) whose only argument is `input: $variable`, with that variable given in `variables` as an object whose keys are all in the mutation's list of input fields. Mutations that name objects by node ID (all of them) are resolved first: the engine looks up each ID with a query under its own token and requires the repository (or, for a project, the owner) to be in the allowed set, so an ID of another repository is `repo_not_allowed`. A project is checked by its owner, which must own an allowed repository, since GitHub ties a project to an owner and not a repository; by decision the projects group covers every project of such an owner, as a project has no repository to name; adding an item also needs the item's repository to be allowed. **Ids that name no repository** are resolved or refused, never passed on: a REST project item update names its item by a number, so the engine reads the item first and requires its content to be an issue or PR of an allowed repository, the rule the GraphQL field update has: the item's `content_type` says which (an issue names its repository by `repository_url`, a PR by its `url`; the GraphQL `content` is the union `Issue | PullRequest | DraftIssue`, read by `__typename`), a draft item is `repo_not_allowed`, and on REST any other type or an answer naming no repository is `id_unresolved`; the REST comment edit (`PATCH /repos/{o}/{r}/issues/comments/{id}`) names a comment by a number, so the engine reads the comment and requires its issue to be in the repository the path names (`repo_not_allowed`); a lookup that fails or answers in no readable shape is `id_unresolved`. `createIssue` requires `repositoryId`, `parentIssueId`, `milestoneId` and every id of `labelIds` to belong to an allowed repository; `assigneeIds` are users, who belong to no repository; `issueTypeId` is refused (`field_not_allowed`), since an issue type belongs to an organization and is not resolved. The `in_reply_to` comment id of a reply to a review comment (`POST /repos/{o}/{r}/pulls/{n}/comments`) is not checked by the engine. **Never allowed, even with every group on:** merging (`merge_pull_request`, `mergePullRequest`, auto-merge and merge queue mutations), anything deleted (every REST `DELETE`, `deleteLabel`, `deletePullRequestReview`, project and view deletes, `delete_file`, `delete_repository`), repository settings, secrets, workflows (`actions_run_trigger`), branch protection and rulesets, pushes and file writes through the API (`push_files`, `create_or_update_file`, `create_branch`; the git route is the push path), releases, a PR's base branch, state, draft state and reviewers, forks, gists, notifications and stars, anything GraphQL not in the table, and anything on a repository outside the allowed set. **Where agents learn of it:** the write tools' descriptions, and one line of `dyna_room` for every session of the room while the setting is on (`GitHub writes: issues, projects on owner/repo`, 7.9). Writes go out under the engine's token, as `pr open` does; this changes no attribution setting.

#### PiG core change: context updates

Replace mid-conversation system messages for every provider with one general PiG mechanism, without Dyna names. Ask the owner before offering it upstream.

The first head and each `appendCompaction` contain current keyed sections and declared tools. Sections change only through updates, and tools only when `tool_search` loads them or a compaction unloads them (Deferred tools block). At the steering insertion point, including the first request of `continue`, PiG compares current and delivered state and adds one fixed-frame user `context_update` only when changed. Changed sections use line diffs, new sections appear whole, and removals are named. Context files (`AGENTS.md` and `CLAUDE.md`) go in one `project_context` section, and a change to any of them is a line diff of that section. PiG stats them and the skills folders before every model request, at the same point, and rereads only files whose stamp changed, so an edit mid-turn travels as a `context_update` before the next request and the head is never rewritten. The `dyna_*` sections are rendered when a turn starts, so a change to one arrives with the session's next turn; a change wakes no idle session, and a session whose context holds no such section gets no frame for it. `box.hello` says this in one sentence of the startup prompt, and a test asserts the text. Skills come from Pi's skills folder and list name, description and path; the model reads `SKILL.md` on demand.

Context updates carry sections only; a tool definition reaches the model when declared or loaded, and stays the same for a box's lifetime. Direct servers announce their tools; the tools of deferred and codemode servers are named in `deferred_tools` (below), and a deferred tool is declared on a `tool_search` hit. Standard MCP `notifications/tools/list_changed` carries list changes. Search returns a short count, not schemas.

**Deferred tools block.** The system prompt has a `deferred_tools` section that names every registered tool not declared yet that `tool_search` or a script can reach (exposure `deferred` or `codemode`): Dyna's tools but `post`, the `github` tools and the tools of added servers. It holds names only, no descriptions; a search returns those. Tools group by namespace: a line `mcp__github__: actions_get, actions_list, …` names the tools that take no action, and each tool with an `action` enum in its schema gets its own line below it, `- session: close, compose_list, list, …`. A namespace lists at most 80 tools and a tool at most 80 actions; the rest end the line as `+N more; tool_search finds them`, so a server with 300 tools costs no more than one with 80. The first line says that `tool_search` loads them and a codemode script calls them, naming only the one of the two that is active; with neither, or with nothing to list, there is no section. PiG builds the section only where it builds a head anyway, at the first prompt and at each compaction, from the tools as they are then, so a loaded tool leaves the block at the next compaction. Between heads each request carries the delivered text unchanged, so a load adds only its `toolsAdded` system message: the system prompt and the request's top-level tools stay byte-identical and the cached prefix holds. The first prompt waits up to 10 seconds for every enabled server, not only direct ones, so the block names their tools; a server that connects later is named from the next compaction, and `tool_search` finds its tools meanwhile. The block replaced the `mcp_servers` section, a line per server with its description. Counted in o200k (`tiktoken-go/tokenizer`), a Dyna box's block, 19 Dyna tools with their actions and 59 GitHub tools, is 526 tokens, against 163 for `mcp_servers`: 363 more up front, each a name a session no longer has to search for. The 674 in the prompt-cleanup draft is the token size of the `session` tool, not a tool count: a box registers 79 tools it can load. **Unloading.** At each compaction, every tool that `tool_search` could have loaded (exposure `deferred` or `codemode`) and that is active but was not called since the previous compaction, or since the session started, is unloaded; `tool_search` loads it again when needed. A call from a codemode script counts as a call. Base tools (`bash`, `job`, `read`, `edit`, `write`, `codemode`, `tool_search`, `post`) are never unloaded. `box/dynaext` records the names of the tool calls (`OnToolCall`, which a script's nested calls also fire) and, at `session_before_compact`, sets the active tools and clears the record; a session restarted mid-window loses the record, so its next compaction unloads what the restart hid. `session_before_compact` also runs when the compaction then fails; the tools stay unloaded and the next search loads them again. The compaction head declares the session's executable tools (the fork's patch P11, whose entry in the fork's `PATCHES.md` is its one description), so the removal saves its tokens at that compaction and leaves no removal note; a mid-conversation removal alone saves nothing, which is why only compaction unloads. The head's block then lists the unloaded tools. `tool_search` loads 3 tools when the model gives no limit (`harness/pig` passes `toolsearch.Options.DefaultLimit: 3`; PiG loads 8), and the schema text says so. PiG builds the block as its fork's patch P7 (`mcpext` and `tool_search` options of the same name drop `mcp_servers`, wait for every server and point the search description at the block), and each compaction's head also holds the sections as they are then.

The `dyna` server and added servers are deferred, which activates `tool_search`. PiG declares `bash`, `job`, its own tools and `post` directly. A model whose catalog entry allows it takes a load as a mid-conversation change, `tool_addition` on Anthropic and `additional_tools` on OpenAI, so the cached prefix survives the load; on other models the tool list changes and the next request misses that cache once.

Each update entry stores its full delivered sections in `details`; compaction stores the folded head and declarations. PiG derives delivered state from the active branch's latest update, compaction or first head. Crash recovery sends only an update not yet recorded. Tests cover restart. PiG does this with `SessionOptions.ContextUpdates` and `Session.SetHostPromptSections`, a patch of Dyna's PiG fork (P5). PiG reads the Node Pi's updates from a session file the same way, but names some sections differently (`project_context` holds the context files that Pi keyed `file:<path>`), so a session that moves to PiG gets one larger update at its first request.

`Session.SetHostPromptSections` replaces host sections, and a failure is an error. Before each prompt or continue the box agent sets the sections in process and fails the turn on error. Context files and skills reach the next model request, as above; the MCP config, settings and add-ons reach a session at its next box start (Box start, below). Remove old mid-conversation system and tool-change paths; retain `supportsMidConvoEffort`.

For speed, stat context files and the skills folder first; read only changed files. Section equality gates diffs. The no-change budget is under 5 ms per run, measured in evaluation; an injected-filesystem test asserts zero reads and diffs. Snapshot queries use indexes, not full scans, with a query-count test. The engine writes instruction files only on save.

Every session starts with `bash`, `job`, `read`, `edit`, `write`, `codemode`, `tool_search` and `post` declared (the box starts PiG with `+codemode`; `codemode.mode` stays `on`, so declared tools stay direct and scripts can call them). `post` stays direct because a third of inputs use it and its extension tool is what ends a turn. Every other Dyna tool waits for `tool_search`, which loads it for the rest of the session, or for a script, which calls `tools.mcp__dyna__<name>` with no search and reads a schema with `describeTool()`. `deferred_tools` names them with their actions. PiG's search loads eight matches by default and each stays declared, so the extension sets `limit` to 3 unless the model chose one. PiG waits for the servers before the first prompt, up to 10 seconds. Maximum-depth starts fail with a typed refusal. Dyna calls use the MCP route; the box resolves names and actions, returning `unknown_action` with valid names. The handler strictly decodes arguments once and returns its typed error unchanged. Owner-only methods stay in CLI and web. `hostexec.run` has no action of its own: `bash` reaches it, and the CLI has `dyna bash --host`. `session.restart` requires tree access; `room.repos` allows a session its own room. The Dyna MCP timeout is 600 seconds with progress notifications; longer work returns an operation immediately and wakes the session on `op.ran`.

**Navigation tools.** `search`, `history` and `transcript` are deferred like the other tools, and `post` takes `forward`. The owner approved the design on 2026-11-04 with access option C: feeds, sessions and rooms are readable across rooms, and transcripts, DMs and files only in the caller's own room. Each tool's description says what it reaches, and nothing else teaches it (no AGENTS.md line, no skill). Text of another room, or delivered from one, reaches a session in `contract.Outside("room <name>", <session>, text)`; own-room text is plain, and a forward quotes another room's text wrapped the same way. The three tools stay deferred, by the owner's later decision that every loadable tool is listed by name in the deferred-tools block; `post` is the only direct dyna tool. Session goals of another room are wrapped as outside text too, since a goal is free text; names are not. The owner calls the same methods with no room limit. Results are compact JSON with names in place of IDs, and a page is at most 8 KB, under the 10 KB where the harness cuts tool output.
- **Across rooms:** `search posts` finds the text of feed posts in every room; `search sessions` finds a session by name or its goal text in every room; `search rooms` lists rooms, with each root and its open and working sessions, optionally narrowed by a name. `history` reads any room's feed. `post` with `forward` quotes a post from any room's feed.
- **Own room only:** `history` with `dm` (any owner DM in the caller's room), `transcript`, and the files of a post. A DM post is never returned from another room: not by `search posts` (not in its hits and not in its `total`), not by `history` (by `dm`, `around` or `post`, which refuse with `forbidden`), not by `forward`. `transcript` refuses a session of another room, and finds a name only in the caller's room; a session may read its own. No tool returns a session's thinking. A cross-room forward carries the quoted text and no files.
- **`search`.** Actions `posts`, `sessions` and `rooms` take `query` (1 to 8 words, at most 200 characters, each a prefix; `rooms` may omit it), `room` (a name or ID; `here` for the caller's; omitted, every room), `limit` (default 10, at most 25; more is refused) and `after` (a result's `next`, for the rest). `posts` returns newest first, each hit with `id`, `room`, `home` (`feed` or `dm:<session>`), `from` (`owner`, a session name, or `<name> in <room>` for a cross-room post), `at`, a snippet of at most 240 characters with the matched words in `[ ]`, and the count of files; `from` narrows it to one author. `sessions` matches each word in the name or goal and lists open sessions first, with `id`, `name`, `room`, `parent`, `state` (`open`, `working`, `closed` or `failed`) and `goal` (at most 200 characters). `rooms` gives `id`, `name`, `root`, `open`, `working` and `lastPost`. `total` counts every match the caller may read, and `next` appears only when more follow.
- **`history`.** One conversation in time order: a room's feed (`room`, default the caller's), or with `dm` the owner's DM with that session (name or ID). Without a cursor it shows the newest `limit` posts (default 15, at most 50); `before` (a post ID) and `after` page back and forward; `around` (a post ID) centres the page on that post and sets the room and conversation from it; `post` returns that one post whole. A text over 800 characters is cut and marked `cut`; `post` returns it up to 32 KB. `older` and `newer` are present only when posts exist beyond the page, and the page is trimmed from the far end to stay within 8 KB. An unknown ID is `invalid`.
- **`transcript`.** A session's turns, newest first (`limit` default 2, at most 5). Each turn has its `id`, start, outcome (`ok`, `failed`, `stopped` or `running`), what it read (`in`, at most 300 characters each), one line per tool call and post (at most 160 characters), and its final text, cut at 800 characters with the item ids that were cut in `cut`. `before` takes the `next` of the previous page; `turn` reads one turn; `turn` with `item` and `offset` returns that text item whole in chunks, with `nextOffset` while more follows. Masking applies as for the owner's `transcript.read`.
- **`post` with `forward`.** The engine builds the quote: `> **Forwarded from <author>** · <time>`, a `>` line, the quoted lines, then the sender's note. The author reads `<session> in <room>` for another room's post, and the time is UTC (`Nov 2, 21:40 UTC`). The post goes where the sender's own post would (the owner's conversation, or the sessions it mentions) and carries the original's files, by hash, only when the original is in the sender's own room. Text from another room is outside text and is wrapped by `contract.Outside("room NAME", SESSION, text)`, the one wrapper for text from outside the room (decision 13). Mentions inside the quote wake nobody. An unknown ID, or a DM post of another room, is refused.
- **Tests.** Each rule above has a test that fails without it: another room's transcript, DM and files refused and the own room's allowed; a DM post holding the search word returned to its own room and not to another; the owner reading everything; limit and page boundaries at the cap and cap + 1, and empty results; unknown IDs; a session reading its own transcript; the forward's author, text and wrapper.

**`bash` and `job`.** Agents have one command tool, under Pi's name. The extension registers `bash` in PiG's built-in's place: an extension's tool wins over a built-in of that name, so PiG needs no patch. PiG's own bash has no background mode, so this one calls the box's job server, `box/shell`, over plain JSON at `/shell/`. It always takes a command string, with `description`, `cwd` and, for a run on another machine, `host`. A `timeout` in seconds, at most 7200, stops the command as `job stop` would, in the foreground or after it moved to the background; its state says `stopped after its N s timeout`, and a background one wakes the session with that line after its tail. A box command has no timeout by default, and a host run 600 s. It starts where PiG started, which is the repository's checkout, or a worker's own tree, and a `cwd` that does not exist fails with its name quoted. Its model text is the output, cut to the last 20 KiB with the rest in a file, and a line with the job's state. A nonzero exit is not a tool error, since `grep` finding nothing is one: the line says the code. A command that moves to the background adds `The job is in the background. You can end your turn and Dyna will wake you when it completes.` after its job ID. When PiG queues a steer from the owner or an ancestor, foreground commands step aside as described below; a script sees `message_arrived: true`. A job already in the background is unaffected. A stop of the turn is another thing: it aborts PiG's call, which ends the extension's request, and the job server moves a command still running to the background, in the box or on a host, rather than killing it; the tool error then says that the turn was stopped, that the answer was dropped, and that a command that had started keeps running and wakes the session when it completes. An MCP call aborted the same way says that its caller stopped it, that the server was asked to cancel it and that work it had started can continue. A crew's workers take no input, so their commands never step aside. The description states what agents got wrong most: `job output` shows only new text, and `pkill -f` on the command's own text ends the job. A script's `tools.bash()` resolves to `{output, job, running, status, exit_code}`. A job's end notice carries the last 2000 bytes of the same merged stdout and stderr that `job output` reads. The calls of one model message run in parallel, so a `read` in the message that holds the `bash` which writes the file finds nothing yet; a later message reads it. A file written on one host reaches `/box/shared` on another within about 7 seconds (a 5 s listing cache and a 2 s write-back). `read` and `bash` resolve a path the same way, in the same mount namespace, and `read` resolves a relative one against the same start folder. A job stays for its life in the Jobs panel. `job` is the companion for what `bash` cannot be: `output`, `stop` and `list` name no command, and `bash` always takes one. One tool with an action costs less of the prompt than three. An ID the box does not hold is `not_found`, saying that a box holds only the jobs it started since it began and the last 20 finished ones, that commands of a replaced box ended with it, and that a host run is stopped when its box closes but keeps going on its host when the box was lost or its connection dropped, with its end arriving as a notice; an ID not shaped like `job_` and 12 hex digits is `invalid`. Both stay direct, because a command is what almost every turn does.

The registry generates the server description, which names the areas for search ranking and `describeNamespace()`, and the tool list is the same for all sessions. The startup prompt names tools only in `deferred_tools`. It has no documentation block either: the embedded PiG carries no docs bundle, so it builds no `docs` section, with its paths and its rules to read `.md` files, and a crew worker's PiG is the same. A test asserts the section's absence, and the skills and context sections are unchanged. No Pi documentation is in the box, and the `dyna-extend` skill says so, and gives the keys a package's `pi` block takes. Tool schemas and help appear in the declarations, or on a search or `describeTool()`; identity and trust come from `box.hello`; instructions from context files; state from snapshot sections; skills from PiG; authority from the engine. A test checks registry and CLI action coverage.

**Messages from above.** The engine supplies a typed interrupt on a steer from the actual owner or any ancestor session, based on event identity and the current tree, never the reply destination. The box acts only after successful steer delivery. Siblings, children and engine notices do not interrupt. Follow-ups remain follow-ups and do not interrupt a running call. Direct bash keeps running in the background as before, but the note names the sender: `The owner`, `Your parent build-lead`, or `build-lead, above you`. The note describes the change without ordering the agent to read the message.

**Code mode interruptions.** The Dyna extension wraps PiG's public codemode definition. An interrupt gives the running script 5 seconds to finish normally; if it does not, its derived context is cancelled with a typed sender cause. The result says `Script stopped`, keeps the output so far and the call summary, and states how many calls ran and which were cancelled. Store writes from the stopped script are discarded. Nested bash commands already started keep running as background jobs and wake the session when they end; other nested calls are asked to cancel. The next script is unaffected. A script is never detached: its tool context, transcript and usage belong to its originating call, and concurrent script actions or delayed store commits would race the model's response to the message. Tool descriptions, not a new prompt instruction, explain both behaviors.

#### The context snapshot

At dispatch, the engine renders ordered `Sections []ContextSection{Key, Text}` in `TurnStart`; the box passes them unchanged. Steers send no snapshot update. Caps count four characters per token; overflow ends with `N more: context show`.

Every list in a section keeps a stable order that does not follow activity, so equal state renders equal text and a context update appears only for a real change.

| Section key | Contents | Cap (tokens) |
|---|---|---|
| `dyna_goal` | own goal, its done condition and open items | 200 |
| `dyna_children` | open children, in the order they were started (a child's activity never reorders them, so only a real change makes a diff): profile, state, current item, PR state, and whether it waits for the owner's answer; at most 8 rows | 250 |
| `dyna_requests` | operations and questions waiting on this session, and its own that wait on others | 150 |

Usage names accounts by provider and number, not identity-bearing labels. Numbers count all of a provider's accounts, so a room limit renames none. Pace compares usage share to elapsed window share: over 10 points above is ahead, over 10 below is under, otherwise on. A window with no reset time, or one already past, has no pace. No section contains timestamps or durations. `dyna_room` likewise states facts. It is read at the next turn, so a flip while the root is idle arrives as a changed section with no wake, and turning the last setting off removes the section. `dyna_holds` states facts and gives no instructions, reaches the session at its next turn like any section change, and wakes nobody. It replaced `dyna_prs` and `dyna_issues`, which said part of the same thing.

`dyna_usage` lists the accounts the session's room may use, one line each, rounded down to a step, so only a spent window reads 100%. Accounts that routing would use come first, so past the cap "N more" counts idle ones, which are marked; `context show` lists all. A model's own window shows when it adds something, as on Home, and an account with no readable window has no line.

The section never reads a provider. It takes the last whole `accounts.quota` reading, and a dispatch that finds that reading past the 5-minute cache age starts one `accounts.quota` read in the background, for the next dispatch. A turn therefore adds no reads to the shared path and never waits for one. The first dispatch after a start has no section.

#### Skills, Pi packages and MCP servers

There are three kinds of add-on, because not every skill is a Pi package. A skill is a folder with `SKILL.md`, saved with `dyna skill save PATH` from a folder or a link. A Pi package is an npm or git source Pi installs, added with `dyna package add SOURCE`. An MCP server joins Pi's config, added with `dyna mcp add NAME URL_OR_COMMAND`. Each has `list` and `remove` and a matching tool, and each lands in the caller's room unless it says `--global`. Repository skills stay Pi's: they live in the repository, and Dyna's only part is `defaultProjectTrust: always` in the box's settings, since a box has nobody to answer Pi's trust question. That setting also lets a repository's other `.pi` resources load.

**Store.** The engine keeps each scope in files beside its instructions (4.3): `addons.json` lists the items with who added them and whether they are on, and `skills/<name>/` holds the folders. A save mirrors like instructions, through the same sync, so a host offline during a save catches up the same way. Each scope mirrors as one file, `addons.tgz`, holding its enabled items, in the folders a box already mounts read-only at `/run/dyna/instructions/{global,room}`. Deleting a room removes its add-ons with its folders.

**Box start.** Before the session opens, the box agent unpacks both bundles, and on a name clash the room wins. It rebuilds `/box/pi/skills`, Pi's own folder, from the built-in skills embedded from `box/skills/<name>/` and the unpacked ones. It writes the packages into `/box/pi/settings.json`, and merges the servers into `mcp.json` with deferred exposure. An item reaches a session at its next box start. Nothing reloads a running box.

**Root only.** Each item has a typed `rootOnly` flag in `addons.json`, set with `--root-only` on `dyna skill save`, `dyna package add` and `dyna mcp add` (and their tools), and toggled by the owner with `addon.set_root_only`, which Settings offers in each item's detail. A global request from a session carries the flag through the owner's approval card. The engine keeps root-only items out of what other boxes receive: a scope's items bundle in two files, `addons.tgz` with the items that are not root-only, which every box mounts, and `root-addons/…/addons.tgz`, holding only the root-only ones, in folders beside the instructions that only a root session's box mounts, at `/run/dyna/root-addons/{global,room}`. A session is root when it has no parent; the engine decides this when it creates the box, and the box agent reads the extra bundles only if it finds them. A non-root box therefore holds no root-only skill body, server URL, command or package source. Saving an item again keeps its mark, so a session cannot clear it by saving a same-named item without the flag; only the owner's toggle does. The `list` methods leave root-only items out for a session that is not root, so such a session cannot read their sources, URLs or commands there either; root and the owner, and so Settings, see everything. `op.list` likewise leaves out a pending root-only add-on request for a session that is not root, since its card and arguments name the item, and `events.list` leaves out its `op.requested` event, whose card is marked `rootOnly`. The later `op.ran` event carries only the item's name. A session can still remove a root-only item from its own room, as it can any item there. A change reaches a session at its next box start.

**Packages.** The engine pins a source when it is added, to an exact npm version or a git commit, so every box gets the same thing. A range cannot be pinned, so it is refused. The box agent installs each pinned source once per host with PiG's own package manager, called as a library with no `pi` or `pig` binary, into `/box/cache/pi-packages/<hash>` by way of a temporary folder, so racing boxes do not collide. It does so by loading that folder's resources, as PiG does at startup, so the install also loads the package's extensions through PiG's subprocess extension host, and a package whose extension fails to load stays out of the box and is named in the notice. An install that outlasts the install timeout is ended with it, and the box goes on without the package. The settings `packages` then list the installed folders as local packages, and the session and each crew worker load their skills, prompt templates and extensions. Extensions run in PiG's subprocess extension host on the image's `node`, started only when a package has an extension, so a box with no packages starts no Node process. The host loads Dyna's own extension, `box/dynaext`, ahead of the packages', so on a tool name clash Dyna's wins, and a package extension that fails to load at box start (after the install check) is a notice too and the session runs without it. Agents learn what a package brings and what a failed one costs from the `package add` tool's description.

**Failures.** A package that fails or an MCP server that does not connect leaves the session running. The box sends `box.notice`, which stores a `session.notice` event: the owner sees it, and the session reads it with its next turn. It wakes nobody, so a box that fails at every start cannot keep paying for turns.

**Who can add.** A session changes its own room at once. Its global change is an `addon.global` operation of class `owner`, which pins and reads everything first, so the owner approves what will land, and a skill's archive waits among the room's files. The owner changes any scope directly. Settings shows every scope, and changing it takes the `admin` scope.

**Host skills.** Dyna owns a saved skill: its files are stored in Dyna and no update depends on the machine they were read from. `dyna skill save PATH` takes a local folder, a link, or `HOST:PATH` (owner only), which has the engine copy the folder from a registered host over SSH (`bash` and `tar` there); HOST:PATH is only one way to get the files in. Separately, a skill has *run-on hosts*, the hosts where its commands run, stored as `hosts` in `addons.json`. `--host HOST` sets them and repeats (`dyna skill save ./hypruse --host omarchy --host desktop --host arch`), whatever the source; the source host is not added by itself. A save with no `--host` on a new skill has no run-on hosts. Saving again, from anywhere, replaces the files and keeps the run-on hosts when no `--host` is given, and replaces them when it is. `dyna skill set NAME --host HOST...` (owner only; method `addon.set_hosts`, beside `addon.set_root_only`, with `--host` repeated and none clearing them) changes the run-on hosts without re-saving the files. Every host name is checked once, where the request arrives, to be a registered host; the stored list is typed host names, without repeats, in the order given. Nothing is installed on any of them: the tool the skill drives must already be there, and a host without it just fails the command. A skill stored before this change with one `host` reads as run-on `[host]`: the store converts the old field when it reads `addons.json`, and writes the new form with the next change. At box start the box agent adds ` · runs on <hosts>` to a skill with run-on hosts, and puts one line after the frontmatter, naming every host as "omarchy, desktop or arch" and describing rather than prescribing: `This skill's commands run on a host: <hosts>, through bash with host. The owner's messages say "on <host>" when sent from one of them. Files written to $DYNA_OUT come back to this box.` `dyna skill list` labels it "runs on omarchy, desktop, arch", and a skill's detail in Settings lists them under Runs on and sets them. NAME:REST reads as HOST:PATH, so a local folder with a colon in its name is written ./NAME:REST; a name that is both a local folder and host-like is refused, not guessed. A host name is letters, digits, hyphens and underscores, checked once when the host is added. A copy over SSH, or a skill folder, is cut at 8 MiB and says so.


Added servers are deferred like `dyna`, so a session loads their tools with `tool_search` or calls them from a script. Dyna has no secret store for MCP servers, and `dyna mcp add` takes no headers or environment.

#### Status

The engine supplies a typed waiting reason for a session without a running turn: its own pending question or owner approval first, then background jobs, then direct children with any running turn in their subtree, then a running workflow it started. Counts and names come from the same bulk facts for `session.list`, `dyna_children` and check-ins; a waiting session is not nagged as idle. Descendant activity means an actual running turn, not another session's waiting label, so an idle ancestor chain is not self-sustaining. Ended jobs, stopped children, finished workflows and resolved requests clear their reason. A running turn takes working status; the owner's urgent request presentation and broken/failed priority remain unchanged. The web session list and header show background waiting distinctly from urgent waiting for the owner, with labels such as `Waiting · 2 jobs`, `Waiting · child services-core`, or `Waiting · workflow audit`.

All of this has shipped, and the snapshot is always on. The owner shipped it without the evaluation gate (q68). PR approval through Dyna is deferred (7.6).

### 7.10 Questions

A session with the `ask-owner` grant asks the owner a question with `question.ask`. Root has the grant from room creation. A session without it gets `no_grant`; no action gives it to another session yet. A question is text of at most 4,000 characters, and it does not end the turn.

Asking never stops the work. `question.ask` requires `meanwhile`, text of at most 4,000 characters that says what the session does next while it waits, and refuses a blank one. The optional `blocked` says the session has nothing safe left to do until the answer; `meanwhile` then says why. Both are stored with the question and carried by `question.asked`, and `meanwhile` shows muted with the question wherever it shows. A question from before these fields has an empty `meanwhile` and is not `blocked`.

A question waits until the owner answers or the session closes, with no expiry, and it survives restarts. It shows in Needs you, Requests and the session's DM, not in the room feed. Only the owner answers, with `operate` scope, since an answer is a message to the session. The answer is one delivery in the DM channel (7.5): it wakes the session, starting its box if it stopped, and carries the question and the answer. The session's reply goes to the owner in the DM.

A close withdraws its sessions' waiting questions in the transaction that starts it, as does a room delete, so nothing waits on a session that can no longer use an answer. `question.asked`, `question.answered` and `question.withdrawn` record each step and have the session's DM as their home. `question.list` gives a room's waiting questions and its 20 newest answered ones; a session may read its own room's.

A waiting question means the session is not finished. It is on the session's list (7.4), which keeps the session from dormant close and disk eviction, and `dyna_children` says so to the parent. Its box may still stop while quiet.

Only a `blocked` question excuses a session from check-ins, and only such a session counts as moving for its ancestors' stalls. A session with any other open question stalls like any session, and the report says it has an open question.

### 8.5 Hooks as typed subscriptions

A subscription has machine, room or session scope; exactly one of event types (`On`) and schedule (`Every`); any filters; and exactly one of `Wake` and `Run`. A `Run` carries command, image, size and files, runs in a small box, never on a host, and ends in typed `hook.finished`. Store subscriptions, event types, filters, arguments and files in their tables.

`Every` is a duration string as Go's `time.ParseDuration` reads one, such as `1h`, `15m` or `90s`, of at least `1m`; a number is refused, and the table keeps it in milliseconds. `Wake` is the session to wake: a session may wake itself, its parent and any session under its parent, root any session under it, and the owner any session. It and a session scope's `Session` each take a session's name in the request's room, in the caller's own room when the request names none, or a session ID, and the engine stores the ID. An hourly wake is `{scope: session, session: upstream-sync, every: 1h, wake: upstream-sync}`.

`Where` filters the `github.*` and `git.*` events of `On`. Each entry is `key=value`, `key!=value` or `text~value`, and all must hold of one thing in the event. Keys are `repo`, `author`, `actor`, `label`, `kind` and `number`, matched exactly. `kind` is a change kind of a `github.pr.changed` or `github.issue.changed` pass, such as `pushed`, `ci_failed` or `merged`, and on `git.main_ci_finished` it is the result, `success` or `failure`. `git.main_ci_finished` is one event for each default-branch head sha when that head's own CI finishes, even after the branch has moved on, and never twice for a sha (7.7). **When a head's CI has finished:** only when every context of its rollup is terminal, whatever GitHub's rollup `state` says: a check run is terminal when its `status` is `COMPLETED` (not `QUEUED`, `IN_PROGRESS`, `WAITING`, `PENDING` or `REQUESTED`), and a status context when its `state` is not `PENDING` or `EXPECTED`. The rollup `state` turns `FAILURE` as soon as one check fails or is cancelled while others still run, so it never decides when. A head with no context keeps the no-checks rule (10 minutes from its first read, then settled with no event). A head with more contexts than one read lists (the first 100, `runsTruncated`) cannot be proven all terminal, so it settles only when the rollup `state` is `SUCCESS` (every context then passed, and none can still be running) and otherwise stays unsettled until it falls off the list of recent heads, with no event. **The result:** `failure` when any context ended `FAILURE`, `TIMED_OUT`, `STARTUP_FAILURE`, `ACTION_REQUIRED` or `STALE` (a status context `FAILURE` or `ERROR`); otherwise `success` when every context ended `SUCCESS`, `SKIPPED` or `NEUTRAL` (a status context `SUCCESS`) or `CANCELLED`, because a cancelled run on a default branch is usually one a newer push superseded, so it alone is not a failure; and `failure` when every context was cancelled, since nothing ran and passed. A real failure still waits for every other context to finish, so a subscriber that starts work on `failure` starts after CI is done. Each entry of `runs` carries the context's own conclusion or state, `CANCELLED` included, so a subscriber sees which were cancelled. `github.ci.finished` for a tracked PR follows the same rule, with the same result and the same wait: it is one event for each head when every check of the PR's head is terminal, a real failure is told once the run is complete (later than a rollup `state` of `FAILURE` would, on a long CI) and a cancelled run alone is not one; only a PR with more than 50 contexts follows the rollup `state` (7.7). `text~` is a plain substring of a comment or a body, as far as the 2,000 characters an event keeps. A field the event does not have meets neither `=` nor `!=`. The engine checks a filter at dispatch, before anything starts, so an event that fails it starts no box and wakes nobody. `dyna subscription events` lists each event with one line from its type's doc comment, and an unknown name in `On` is refused.

A subscription fires only on news: a change with no change kinds fires nothing. A `Run` fired by an event gets that event as JSON on stdin, with `DYNA_EVENT` set to its type. Each event has its own `Run`, and a subscription's Runs go one at a time, oldest first, from `subscription_queue`, which holds at most 256; a burst past that stays in the room log and starts no `Run`. A failed `Run` is not repeated for its event, and the next waits out the failure's backoff. A scheduled `Run` gets empty stdin and no `DYNA_EVENT`. GitHub text in the JSON sits beside an `outside` flag, `true` for anyone but the owner's account, and a script treats it as outside text, as `watch_post` does.

Engine timers remain scheduled tasks. The updater replaces the self-update hook. Librarian hooks did not carry over. The horizon upstream-watch becomes a `Run` on `git.main_updated` with its script as a `RunFile`. A default room subscription wakes root on `notice.posted` and `git.main_updated`.

### 9.2 Workflows

A **crew** is one Dyna session with one box. The agents inside it are PiG sessions in the box agent's process, not Dyna sessions, so `boxes.session`, the box socket's identity, the reconciler, dormancy, restart and admission work as they do for any session. A crew has one identity: its workers share its push rights, so third-party PR review stays in normal child sessions. A script coordinates the fan-out, on PiG's codemode sandbox (QuickJS) in the box agent's process; scripts never run in the engine. Stages: (1) crew, script host and journal, (2) worktrees, `merge()` and the build lock, (3) the run page, all built, (4) `team()`, `ask()`, budgets and quota pause. Budget 1,000–1,500 product lines per stage.

**Start.** `dyna workflow run FILE [--args JSON] [--resume RUN]` (`workflow.run`). Any session may start one, and the owner, unless the room's workflow settings say otherwise (below). A script begins with `export const meta = {...}`, a pure literal that the engine reads without running it: `name` and `profiles` are required, and `description`, `size` and `repo` are optional. Unknown keys, unknown profiles, unknown sizes and repositories the room does not list all fail here, before a box exists. The run becomes a child session of the caller in one transaction, on a host chosen by normal admission, on the room's default repository unless `repo` names one. The owner has no session, so the owner's crew sits under root and its reply is the owner's. Its first profile is the session's. A script that leaves `size` out runs at the settings' default size, and one that names a profile the settings do not allow fails here too.

**Workflow settings.** The owner decides who may start workflows, how many, with what, and which features a script may use, for every room and for each room alone. A setting has a global value and a room may override it: a room's own value wins, else the global value, else the built-in default. A room's row holds only what the owner set for it, so changing the global value moves every room that has not overridden it. `workflow.settings` reads the built-in defaults, the global values and every open room's overrides with the values in force; `workflow.set` changes one scope, the global one or one room's, setting some values and clearing others back to inheriting. Both are the owner's alone, through the API and `dyna workflow settings` and `dyna workflow set` (`--room ROOM`, or none for the global scope); a session's call is refused. A value is checked once, at `workflow.set`: a starter that is not one of the four, a negative limit, a size the engine has no name for, a profile it does not know, an empty profile list and a timeout under one second are refused, and nothing changes. The settings, each with the one line the CLI and the page share (the engine returns them with the values):

| Setting | Built-in default | Where it holds |
|---|---|---|
| `start`: who may start a workflow: `any` session, `leads` (the room's root and sessions that have ever started a child), `root` or `off` | `any` | `workflow.run` |
| `maxRuns`: the most runs going at once in the room; 0 is no limit, at most 10000 | 0 | `workflow.run`, counted inside the transaction that starts the crew, so two starts at the limit let one in |
| `maxWorkers`: the most workers one run has at once, on top of its box's memory and each profile's `maxConcurrent`; 0 is no limit, at most 10000 | 0 | the crew's box, when its box starts (it takes the value its hello carries) |
| `profiles`: the profiles a script's `meta.profiles` may name; none set is every profile, in the API and in the CLI (`--clear profiles` returns to it; an empty name is refused) | every profile | `workflow.run`, `workflow.reload` |
| `size`: the box size of a run whose script sets no `meta.size`; empty is the engine's choice | the engine's choice | `workflow.run` |
| `timeout`: seconds a worker or command may run when `agent()` or `run()` sets no `timeout`, from 1 to 2592000 (30 days) | 18000 (5 hours) | the crew's box (its hello and each reload carry it) |
| `worktree`: `agent()` with `worktree: true` | on | each step's start |
| `merge`: `merge()` | on | each step's start |
| `run`: `run()` shell commands | on | each step's start |
| `workflow`: `workflow()` nesting | on | each step's start |
| `post`: `post()` to the parent | on | each step's start |
| `resume`: `workflow.run` with `resume` | on | `workflow.run` |

`start` binds sessions: the owner always starts a run, and so can read and change the settings, so no setting locks the owner out. `leads` lets root start one before it has a child, since root is the room's top of the tree. Starting from a session makes the run that session's child. A session that hosts a run starts none of its own, since a script nests another with `workflow()`. A refused call states the setting that refused it as a typed cause, `error.workflow.setting`, with the setting's name from the table, and its message states that fact, what the setting does and what happens to the call; the engine never reads a message to decide. A switch is read at each step's start, so a change reaches a running script at its next call: a call that is refused throws in the script like any failed step. A run, a reload and a resume read the rest when they start. `maxWorkers` and `timeout` reach a crew's box in `BoxWorkflow`, so `maxWorkers` waits for the box's next start, and `timeout` follows a reload. A setting is offered only where it gates something. The agents learn of them in three places, each fact in one: the `dyna_workflows` section (7.9) says the rule and the features that are off; a refused call names its setting; and the `workflow` tool's description and the `dyna-workflows` skill say that any session may start a run and what the settings can take away. Settings > Workflows (5.13) shows and changes them from the same two methods, the global default and each room as a list and detail, with each setting's line of help from `workflow.settings`.

**Fixed at start.** The script, its profile list and its size never change. The box reports the commit its checkout started on and a later box starts there, unless the crew has pushed its branch. The first image choice stands too, while the host holds that tag; a host without it builds what the repository holds now.

**Script.** Plain JavaScript with top-level `await` and `return`, in its own QuickJS VM, with no modules, files or network, that PiG's `codemode.Sandbox` starts for each run of a script and each child. The VM has no timers and no overall deadline, since a script waits hours for its workers; the steps carry the timeouts, and the VM's memory is bounded at 256 MiB. `Date.now()`, `Math.random()` and argless `new Date()` throw, with the same words as before: the script does not run on the sandbox's virtual clock, which would hand a resumed script other values. The script API reaches the box agent through two sandbox globals, and a small prelude in the VM turns them into the calls below.

| Call | What it does |
|---|---|
| `agent(prompt, opts)` | starts one worker and returns its final text, or with `schema` the JSON it submits as a file (below). It throws on failure. Options: `profile` (default the first), `schema`, `label`, `phase`, `lane`, `timeout` in seconds (default 5 hours), `worktree`. A profile outside the list fails. With `worktree: true` it returns `{step, text or output, branch, commit, files}` |
| `parallel(thunks)` | runs all and keeps input order |
| `pipeline(items, ...stages)` | runs each item through the stages with no barrier between stages, and keeps input order. A stage gets `(previous, item, index)` |
| `workflow(path, args)` | runs a script from the checkout in its own VM, under the run's profiles. Nesting is one level |
| `run(command, opts)` | runs a string in `sh -c`, or a list directly, in the box, under the build lock because builds must not fan out. It returns `{code, stdout, stderr, durationMs}`, 64 KiB of each stream, and throws on a nonzero exit unless `check: false`. Options: `cwd`, `env`, `timeout`, `check`, `label`, `phase`, `lane` |
| `merge(results, opts)` | merges worktree steps in order into one run branch and pushes it, with plain git and no model. It returns `{branch, commit, merged, conflicts}` and a conflict does not throw. Options: `base` (default the pinned commit), `label`, `phase` |
| `post(to, text, data, opts)` | posts as the crew to its parent, once however often the script replays. A crew reports only to its parent, the session that started it or root when the owner did, so `to` is `parent` or that session's name or ID, and the engine refuses any other. Options: `lane` |
| `phase(title)`, `log(...values)`, `args` | set the stage of later steps, add a line to the journal, and read `--args`. `log` joins its values with spaces: strings as they are, arrays and objects as JSON (`[]`, `{"a":1}`), as `console.log` shows them |
| `status(text)` | sets the run's one-line status, which the run page shows under its name and the Runs list beside it (`workflow.set_status`) |

`parallel` and `pipeline` turn a failure into an entry `{failed: true, step, reason}`, and a failed pipeline item skips its later stages. An error no step recorded joins the journal there too, so the run's end counts it. There is no silent `null`.

**Post data and result delivery.** A workflow post keeps its optional JSON value separately from text, in the post request and stored event, feed and transcript contracts. Absence differs from explicit `null`; objects, arrays and scalars are valid. Internal request, event and transcript data fields carry encoded JSON text, so normal API JSON decoding cannot round a number or rewrite an exponent. For example, the wire field is `"data":"{\"n\":9007199254740993}"`. The public workflow `post()` still takes a JSON value, and its box adapter handles this transport encoding. Existing text, including JSON fences, is never reinterpreted. Forwarding preserves data in the same room. The owning post boundary rejects invalid literal UTF-8 and compacts valid JSON into UTF-8 (without a trailing newline, with HTML-sensitive characters escaped as JSON Unicode sequences); encoded bytes determine size. Above 1024 bytes it saves an immutable room-scoped `application/json` blob named `data.json`, before recording the post, through the existing attachment store. The boundary records that file's attachment index as typed post/final-event metadata; it is not inferred from a filename. Normal box file delivery downloads it before exposing the input. The recipient's frame lists the attachment and the input says `data: <actual attachment path> (<size>)`, never repeats the JSON wall; at or below 1024 bytes it pretty-prints inline. Idempotent replay returns the same post and file. A workflow's explicitly typed final result uses the same rule for its final reply; ordinary final text and failure/stop status remain text. The complete result remains in the workflow journal.

The web renders typed post data separately from its text. At or below 300 UTF-8 encoded bytes it shows one quiet monospace `data: <JSON>` line, with Copy revealed on hover or keyboard focus and no Download. A non-string inline value may ellipsize to fit, without changing its complete text or copied value. Above that a collapsed `data · size · keys/items/type` chip opens a foldable JSON tree, with Copy and Download inside the expanded view. The feed suppresses only the attachment identified by the typed data-file index, leaving unrelated files (even another `data.json`) visible and preserving their media-viewer positions; agents still receive every attachment normally. Objects and arrays initially show counts, with children created only on expansion and paged for wide collections; no recursive initial expansion. The web keeps the canonical source text for size, Copy, Download and forwarding. An iterative range scanner counts immediate children and indexes only a requested page; it neither converts number tokens to JavaScript numbers nor recursively parses or reserializes a folded value. Valid JSON nested 7,000 levels deep remains folded without a stack overflow. Array positions are unquoted and muted; object keys retain their quoted styling. Single strings start capped at three lines, with keyboard-accessible Show all/Show less controls. Copy and a safe `data.json` JSON download preserve the complete encoded value independently of clipping; a fetched reference preserves its original bytes. Controls work with keyboard and screen readers, in light/dark themes and narrow layouts. The owning data-file index survives transcript items, inputs, post and steer adapters, and the transcript UI. The transcript uses that index for file references and duplicate-card suppression, preserving unrelated same-name files and their original media positions. Transcript pages carry values over 32 KiB as a typed file reference with size and root summary, so a complete JSON value cannot consume the page budget and make its post disappear. Expanding it fetches the complete JSON through the existing authenticated file route, with loading, failure and Retry states. Feed events retain their typed value. Older untyped posts and JSON-looking final strings remain text; neither fences nor text are parsed to decide whether to hide or retype a post. The workflow tool points to the versioned workflow skill for the agent-facing delivery details and exact thresholds.

**Phases, lanes and status.** A step's `phase` is its stage, from `phase()` or the option, and its `lane` names the subject it is about, such as `lane: g.id`. Both are stored on the step, and nothing is parsed from a step's name. The host takes `lane` out of the options before the key is hashed, so tagging a script's steps keeps their stored results, and a kept step takes the lane its script now gives it. `status(text)` is not a step and never replays: the engine keeps the latest line as one line of at most 200 characters, with the 19 before it, in `workflow_runs.status_lines`, and `workflow.status_changed` carries each new line live, like `workflow.step_changed`. A resumed run starts with no line and its script writes them again as it reaches them. `workflow.status` returns the lines, and `workflow.list` gives each run its latest line and its running count.

**Workers.** Each `agent()` is a PiG session in the box agent's process, opened as the session's is, with `box/dynaext`, its profile's model and compaction trigger, the session's instructions plus one paragraph on being a worker, the box's agent folder, and a new session file of its own in `/box/pi/sessions`, which it never confuses with the newest file there. Its models.json is its own, because it carries the worker's header (below). Workers share the box's tools, and those without a worktree share its main tree. The box's memory bounds them, at one worker per 512 MiB of `memory.high`, and a profile's `maxConcurrent` bounds its own; zero is unlimited. A crew's turn ends when the script does, and a step the script did not wait for is cancelled and fails. Workers share the agent's process, so a worker that crashes it takes the box down with it, and the run resumes from the journal. The VM is not a security boundary: `globalThis.Date` and `globalThis.Math` are the frozen built-ins, so `globalThis.Date.now()` works where Node threw. Its transcripts carry the crew's input, so `transcript_turns` files every worker under the crew's one turn, by path. A shell job's end still wakes the session, which has no PiG to hear it, so a worker reads a long job with `job output` until it ends.

**Schema steps submit a file.** A worker started with a `schema` has one more tool, `submit({path})`, and a worker without one does not. The path names a JSON file the worker wrote in its working folder, its worktree or the main tree, and cannot leave it: a path outside, a symlink out, a missing file or one that is not a regular file is refused with an error. The box agent reads the file and checks it against the step's schema. A valid file is the step's result and ends the worker's turn; an invalid one (not JSON, or schema errors) goes back as the tool's result, with the errors, for the worker to fix and submit again. A file over 1 MiB (the limit of what one step stores) counts as an invalid submit, so the box agent never reads more than that. Three submits are allowed, and a third invalid one ends the turn and fails the step. A worker whose turn ends without a valid submit fails the step with the typed cause `no_submit` (`contract.CauseNoSubmit`, on the step's outcome in the box agent; the journal keeps the reason only). The final text of a schema step is not read, so a large result lives in the file and is not typed out again in the answer. A step without a `schema` is unchanged: its final text is its result. The `submit` tool's description is the one place that tells a worker how it behaves.

**Worktrees.** `worktree: true` runs a worker in its own git worktree beside the main tree, in `<repo>.worktrees/`, on its own branch `<session branch>-<key>` from the pinned commit (the crew session's recorded branch, 5.7). The git route lets a session push that prefix, and worktrees share one repository copy, so no worker clones. Its shell and PiG start there, and it is told to stay there; nothing enforces that. When it finishes, the box agent commits what it left, except ignored files, without running hooks, and pushes the branch, with up to three tries. Only then is the step stored as done, so a stored step always has its work on the remote, and its result names the branch, the commit and the files changed. A push that fails fails the step with the reason, and a worker that fails saves nothing. The tree goes when its step ends, so a script finds the same thing in the first box as in a replacement: a branch and a commit, not a folder. When a stored step replays, the box fetches its branch, and a branch that is gone fails that call and counts at the run's end. A rerun of a step that never stored replaces whatever its lost attempt pushed. Give every worker that writes a worktree, and give writers separate files. Workers without one keep sharing the main tree, and their uncommitted files do not survive a lost box.

**Merge.** `merge()` runs in a temporary tree of its own, because workers may be writing in the main one. From `base` it merges each result in order, each with its own merge commit, and pushes `<session branch>-run`, which only ever holds clean merges. `merged` names the steps that went in. `conflicts` lists each step that did not, with its `files` and `branch`, or with the `reason` of a failed entry from `parallel`, which has no work to merge. A conflict aborts that one merge, the next goes on from the last clean state, and nothing throws. Each conflict also joins the journal as a failed entry named `merge conflict: <step>`, so the run's count, its final reply and `workflow.ended` report it, and a stored merge writes those entries again on resume. It throws only on a misuse or a git failure. A merge is a `run` step in the journal, keyed on the results it takes, so a worker that reran merges again. A later `merge()` starts from `base` again and replaces the run branch, so a script builds on an earlier one with `{base: earlier.commit}`. There are no octopus merges, no rebase and no repair. A script hands a conflict to `agent()`, whose worker merges both branches by hand in its worktree. The main tree does not move, so a script tests a merge by fetching its branch inside `run()`.

**Build lock.** One lock in the box serializes `run()`, which always takes it, and workers' builds. The box agent keeps the queue, in order. A crew's box puts a shim ahead of `PATH` for each of `cargo`, `go`, `npm`, `npx`, `pnpm`, `yarn`, `bun`, `make`, `ninja`, `cmake`, `gradle`, `mvn` and `bazel` that it finds at start, so a worker has nothing to remember. `cargo` locks for `build`, `check`, `test`, `bench`, `run`, `clippy`, `doc`, `fix`, `install`, `rustc`, `rustdoc`, `nextest` and their short forms; `go` for `build`, `test`, `run`, `install`, `vet` and `generate`; the JavaScript managers for everything but reads such as `ls`, `view` and `config`; the others for everything. The first argument that is not a flag names the subcommand, and `--version` or `--help` first never locks. Whatever else a worker runs, `grep`, `git` and `ls` among them, never touches the lock, and whatever a build or `run()` starts does not wait for the lock its parent holds. The lock does not see a tool called by a path, such as `./gradlew`, a tool the box did not have at start, a direct `rustc`, `gcc`, `tsc` or `pytest`, or a command that replaces `PATH`. A waiting build says so in its output and may become a background job. Time that anything spends queued does not count against a worker's `timeout`, for any worker of the box, so none fails for its place in the queue. A holder keeps the lock for at most an hour, because a server started with `npm run dev` looks like a build and a job outlives its worker.

**Rust.** A box of a repository has `CARGO_TARGET_DIR` at the main tree's `target` (5.6), and a crew sets it there if it is unset, so all trees share one, and each dependency builds once. Cargo gives a workspace crate the same identity in every tree and judges it by file times, so a tree whose files predate the last build would get that build's binary. The shim therefore records which tree built last, and when the tree changes it refreshes that tree's file times, inside the lock. A workspace crate rebuilds on each change of tree, with rustc's incremental cache behind it. A worker finds a binary with `cargo run` or through `CARGO_TARGET_DIR`, not `./target`.

**Model route.** The route allows every model of the run's profiles. Each worker's PiG sends `X-Dyna-Worker`, which a crew's route adds to the session's affinity ID and then drops, so each worker keeps its own account while the room's accounts and the owner's choice apply as for any session. The journal totals usage, and that total is the crew's turn.

**Journal and resume.** The engine stores each step's start and result in `workflow_steps`, through the box socket. A step key is the SHA-256 of the kind, the prompt or command, the options as written without `lane`, the effective profile and the parent step's key, which is the enclosing `workflow()` call; only a true duplicate adds an ordinal. Order plays no part, so parallel steps replay safely. A new box starts the script again: stored steps return at once, stored failures throw again, and a step that was running reruns. A `workflow()` step always reruns, so an edited child script takes effect while its unchanged steps return. An engine restart does not touch the script, which is running in its box and waits for the socket as a turn does. A step that stopped with the run stores nothing. `--resume RUN` starts a new crew on the same repository from an ended run: it keeps that run's finished steps, commit and image, so a changed step alone reruns, and failed steps run again. Usage counts only what the new run spends. A worktree step's work comes back from its branch, in the first run's name. A resumed run is a new session and owns those branches: `workflow_runs.resumes` links it to the run it resumes, and the git route lets it push the recorded branches (5.7), with their topics, of every run along that chain, in its room and repository. No other branch of another session opens to it, and a refused push reads the rule. The main tree is the new box's own: what workers without a worktree left there is in the diff the old crew's close saved (5.9), not here. The same holds for a box replaced with its volume gone.

**Reload.** `dyna workflow reload RUN FILE` (`workflow.reload`) gives a running run a new script; resume is for an ended one. Only the run's starter, the starter's ancestors and the owner reload a run. The meta is checked as at a start, and its `name`, `repo` and `size` must stay the run's, since its session and box were made for them; `profiles` and `description` may change, and the models the crew's route allows follow the new profiles. The run keeps every version in `workflow_scripts`, and each step records in `workflow_steps.version` the version that started it; a step a resumed run kept has none. The crew's channel carries the new version to its box, and again on each new connection, which a box already on it ignores; a replacement box's hello carries the newest. The same crew, box, main tree, branches and journal carry on: the crew stops the old script's VM and runs the new script from its start in the same turn. Each call goes by its step key: a finished key returns its stored result, a key whose step is still running in the box waits for that step's worker and starts no second one, and a new key starts fresh. A running step the new script does not call runs on until the run ends, then stops and fails with `the run ended first`.

**End.** The script's return value is the run's result and the caller's normal final reply, which adds a line naming any failed steps and merge conflicts. No post of the crew stands in for that reply. `workflow.ended` records the state, the count and names of the failed steps, and the usage. Then the crew closes, which saves a diff of what its tree did not push (5.9). A script that throws fails the run the same way, with the reason in the turn's error, and nothing retries it. A run stops if its turn is stopped or its session closes. A box that cannot set up or cannot start is a failed session, and `session.failed` tells the parent, who may restart it; the run waits. `workflow.status` and `workflow.list` read runs and their steps.

**Run page.** A crew's session page is its run, at the session's own address, and it takes no messages: a script has no input once it runs. Its header has the run's name, state, elapsed time, step count and tokens, then its status line: the script's latest `status()`, with how long ago it wrote it and, on a click, the lines before it, or with none the counts, as `75 of 76 steps · 1 running`. Then why the script threw, then a Flow or Timeline switch, which each viewer's browser remembers. Flow draws a node per phase, in the order each first ran, with its done, running and failed counts and its running step named; an edge for each move a lane made from one phase to the next, counted, so a loop such as review and fix and a skip such as write to land show as the run made them; phases without lanes joined in the order they first ran; and a failed node, only when a step failed, naming it. A row of nodes arches skips above and loops below; a narrow page stacks them in a column. Timeline draws worker slots as rows, packed in the browser from each step's start and end, with each bar in its phase's colour and labelled by its lane or label, commands and posts on a row of their own, the steps a resumed run kept folded into a band on the left, and a now line on a live run; under it the running steps, then worker time with its split by phase, the longest step, the wall time and the tokens. It needs no lanes or phases, and on a narrow page it scrolls sideways in its own box. Each phase takes one of six stage colours from the theme in that order; a running step is the one thing drawn green. A node opens its steps under the chart, and a bar opens its step: a worker's transcript, or the step unfolded. Then the text result, the newest `merge()` with its branch, commit and conflicts, linked to GitHub, then a JSON result. Each listed step shows its profile, state, duration, tokens and when it ran within the run, and a child step sits under the `workflow` step that ran it; a failed count filters the list to the failed steps with their reasons. No raw JSON shows: a JSON result or step output reads as labelled fields, leaving out what Merge and Steps already show, and a value too deep or too long says how much there is. A step that holds more than its row (`more`) opens in place, with what it ran and left from `workflow.step`, which reads a step's `detail` and `result` for the owner; one with nothing more does not open. All of it reads from `workflow.status`, which takes a run or its crew session, so a closed crew's page shows the same, and a run that threw keeps its reason as its result. `workflow.step_changed` carries each journal row to open pages as it changes. It is live like `turn.activity`, never stored and delivered to nobody, so workers' work stays out of the feed and out of every session's context, and a page that may have missed one reads `workflow.status` again on each new stream. A worker names its session file as it starts (`workflow.step_transcript`), so a running worker opens too, in the session thread, at `?step=<key>`. `transcript.read` with `step` reads that one file under the crew's turn, with the step's times and its prompt as the input; a resumed run's kept step reads from the crew that wrote it. A worker with no file yet shows as Waiting, for its place among the box's workers. A crew has no row in the sessions panel: `session.started` marks it with `workflow`, and its run stands for it in Runs, a tool in the room's header beside Jobs and Requests that shows once the room has a run. Runs lists the running runs first, each with a green dot and its status line, then the rest with their state, step count, failures and latest line or description, each linked to its page; the button has a green dot while a run is going, and on a phone the room menu opens it. `workflow.list` fills it, and `workflow.step_changed` and `workflow.status_changed` keep a running run's counts and line current. `workflow.ended` leaves one line in the room feed with the run's state and step count, linked to its page. A crew's text reply stays a post in the feed. A typed JSON reply shows its completion text and the same foldable data control as a workflow post, and the run's line links to its complete journal. Session search leads to the page too. A reloaded run names its script version among its facts, and each step shows the version that started it. Stop is `session.stop` on the crew. Steering one worker is not built.

Workflows have no per-run call limit; the owner removed it.

## 10. Test strategy

Room rules govern test quality, placement and execution. The owner permits one or two fast integration tests per important owner-facing feature and no repository end-to-end tests.

### 10.1 Owner policy

Tests cover observable behavior, not snapshots or internals. SSH, socket forwarding, reconnect and Podman are the priority integration boundaries. Real harness, GitHub and browser checks are manual.

### 10.2 Boundaries and their fakes

Keep one interface and fake together at each boundary: `box/podman` and `box/fakehost`; `harness/pig` and `harness/fakeharness`; CLIProxyAPI and an `httptest` upstream; GitHub and a fake client; system time and an injected clock. Store tests use SQLite in `t.TempDir()`.

### 10.3 What the unit tests cover

Tests live with their packages. CI checks generated types, dependency direction and strict web types.

### 10.4 Where tests run

Builders run tests in their own box. CI runs Go vet and tests, generated-file and dependency checks, and `pnpm check`. The Go suite targets under 60 seconds; fix slow tests at once.
